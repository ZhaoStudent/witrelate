## 1. 三条硬约束（先看这节，否则设计会白做）

### 1.1 wit 框架**不支持 MCP** —— 必须自研桥接层【已验证】

实测证据：

```
wit 全部子模块中含 "mcp" 的：0 个
pip 环境里 mcp / fastmcp / langchain-mcp-adapters：均未安装
wit 顶层导出中的工具抽象：Tool, ToolManager, ToolCall, ToolRequestEvent, ToolResponseEvent
wit.kernel.agent.CompiledAgent.tools: list[Tool]
```

wit 的「模型可调用工具」= `Capability`（用 `@capability(...)` 声明，`model_callable=True` 是默认值）。
`WitAgent` 的字段是 `capabilities`，**没有 `tools=` 这个入口**。

**→ 直接后果**：你描述里的「Agent 通过 MCP 自主搜索」「一个 Agent 兼顾多个 MCP」，
在 wit 里**目前没有现成实现**。必须先写一层 `Capability ↔ MCP` 桥接（详见 §6）。
好消息是：这层桥接恰好是**本项目最硬的技术贡献**，直接命中评分表鼓励的「异构智能体协议适配」。

### 1.2 端口数 = Agent 数上限 = 5（当前）【已验证】

实测：

```
服务器 8446 起 openssl 临时监听 → 本机访问 HTTP 200   （放行）
服务器 8448 起同样监听          → 本机访问 HTTP 000   （被拦）
```

腾讯云安全组只放行了 **8443–8447**，共 5 条。
每个 wit Agent 是独立进程、独占一个 HTTPS 端口（`runtime.serve_direct_partner(host, port)`），
而且这个端口必须写进 ACS 的 `endPoints`，否则对方连不上。

**→ 完整设计需要 13 个端口。要先去腾讯云控制台补放行 8448–8455（8 条规则）。**
这是纯控制台操作，5 分钟，但漏了会导致后面注册完却连不上。

### 1.3 已公布出去的端口不要改【推论，需你确认】

`incitement-detector`（8443）与 `harm-assessor`（8444）的 ACS 已过审并公开，
里面写死了 `endPoints = https://150.109.154.16:8443|8444/rpc`。

### 2.2 角色关系：Leader / Partner **不是身份，是会话角色**

这一条是整个架构的地基，也是你上一轮"角色交换"想法的正解：

- AIP §3.1：**在一次完整的交互中只能有一个领导者**——限定的是**单次会话**，不是 Agent 的一生。
- AIP §3.2：直连模式下「Leader 与每个 Partner 直接交互，**而 Partner 之间无交互**」。
  → 所以**辩论不可能让正反方直接对讲**，必须由正方**发起一个新的会话**；
  在那个会话里，正方就是 Leader，反方是 Partner。
- AAC §9.4 Profile D「Agent 发起的多跳委托」，链路图逐字就是 `Agent0 → Agent1 → … → PartnerN`；
  §10.1 把「动态下一跳 + 边界约束 + 逐跳裁决」列为**推荐默认模式**。
- AAC §14.4：**禁止冒充**——正方必须用自己的 AIC，不能"戴上裁判的帽子"。

**表述规范**：不要写「把 Leader 权限交给 Partner，用完归还」。
正确说法是「**高负载 Partner 可发起子会话，以 Leader 角色自主编排下游**」。后者准确，且是规范推荐模式。

### 2.3 三类可直接复用的既有资产

| `legal_acps/contracts.py` | 3 套 Pydantic 契约 + 危害量表分档锚点 | 新功能的契约照这个模式写（先定口径再写代码） |
| `scripts/serve.sh` | 按角色启停 + 内存显示 | 直接扩 `ALL_ROLES` 与 `port_of()` 即可管理全部 Agent |

### 2.4 两级嵌套（2026-09-29 落地）

原设计（见 §3.3 时序）让**正方兼任子会话 Leader** 去发起与反方的辩论 ——
那是 AAC Profile D 的「多跳委托」，协议上成立，但有个硬伤：
**正方既是辩手、又是辩论的组织者**，它自己分配立场、自己记录、自己决定何时收场。
裁定的独立性无从谈起 —— 既当运动员又当裁判。

现在把裁判独立成一个 Agent，结构变成**两级嵌套**：

```text
        legal-consult-leader  (8445)     外层 Leader：受理与汇总
              │
              └─ fact-judge   (8448)     内层 Leader：立题 → 组织辩论 → 裁定
                    ├─ debate-pro (8446)     正方
                    └─ debate-con (8447)     反方
```

为什么这个形状比"多跳"更好：

| | 多跳委托（旧） | 两级嵌套（新） |
|---|---|---|
| 辩论组织者 | 正方自己 | 独立的裁判 |
| 正方角色 | 辩手 **＋** 子会话 Leader | **只做辩手** |
| 协议依据 | AAC Profile D（多跳属扩展场景） | **AIP §3.2 的标准形状** |
| 裁定独立性 | 无（运动员兼裁判） | 有 |

**交换的代价，如实记下**：`debate-pro` 的对外契约变了
（`debate.gather_case` / `debate.open_debate` → `debate.submit_argument`），
description 也改了，**ACS 指纹因此变化，必须重新过审**。
`legal-consult-leader` 只改了 instructions（不进指纹），**无需重审**。

> 附带约束：被委托方的 run 沿用 wit 默认 `max_steps=8`，而 `RunConfig` 是 frozen 的、
> Agent 侧无法调大。所以裁判的流程被刻意压到 6–7 步
> （受理 → 发现 → 派发×2 → 等待×2 → 裁定），并由终止 Hook 兜底。
> 详见 `legal_acps/agents.py` 里的 `build_fact_judge`。

## 3. 功能一：事实核查与舆论甄别（1–4 个 Agent）

### 3.1 角色划分

| Agent | 职责 | 为什么这样切 |
|---|---|---|
| `fact-judge` 网络裁判 | 受理事件（用户描述 或 自主检索热点）→ 独立采证 → 发起辩论 → 裁定「确有其事 / 断章取义」 | 它是唯一掌握全局的会话发起方 |
| `debate-pro` 正方 | ① 产出「可核验事实清单」② 被随机分配立场 ③ 发起辩论子会话 ④ 回收辩论记录 | 它同时是"采证者"和"辩论发起方" |
| `debate-con` 反方 | 拿到相反立场，逐轮反驳 | 只做反驳，不掌握全局 |
| `speaker-profile` 发言者画像 | 检索发言者历史论点，给出「别有用心/歪曲事实」概率低/中/高 | **暂缓**（你已明确不在当前计划） |

**名额说明**：你要求功能一"最多 4 个 Agent"，上面正好 4 个（含暂缓的画像）。
已过审的 `incitement-detector` / `harm-assessor` **不计入这 4 个名额**——它们输出的是
"言论的法律定性"（harm_index 分档含"涉嫌违法"），属**后果评价**，不是"事实真假"判断。
它们作为**共享下游**，被功能一（判定为断章取义后评估后果）和功能三（言论类法律事件）共同调用。

> ⚠️ **上表已按 2026-09-29 的落地实现更新**，与最初设想有三处不同：
> 1. `debate-pro` **不再**产出事实清单、**不再**发起子会话 —— 采证归裁判，辩论组织也归裁判，
>    它只做辩手（详见 §2.4）；
> 2. `fact-judge` 的产出是**裁定书**（`fact.issue_ruling`，含四类话术命中项），
>    而不是"自评 + 自训练"；
> 3. 实际跑通的端到端是「主控 → 裁判 → 正/反方」两级嵌套，交互时序见 §3.3 的更新说明。

### 3.2 ⚠️ 对你原流程的一处修正：**按你原来的顺序，这场辩论是演的**

你的原描述是：正方先"搜集事件全貌" → 随机分配观点 → 与反方辩论 → 辩论后正方把
"事件原貌 + 正确答案"交给裁判，让裁判自评并自训练。

**问题**：如果正方在辩论**开始前**就已经掌握了答案，那它和反方就是在**演一场已知结局的戏**。
裁判基于演戏得出的判断没有独立性，后面"自训练"学到的也是被污染的样本。

**修正（成本为零，只改"顺序"和"谁知道什么"）**：把「基准事实」从辩论双方手里拿走。

| 阶段 | 谁掌握什么 | 产出 |
|---|---|---|
| ① 采证 | 独立采证环节（裁判自己检索，或一个只检索不判断的步骤） | 「可核验事实清单」：时间 / 地点 / 人物 / 原始表述 / 出处。**不含任何"是真是假"的结论** |
| ② 辩论 | 正反方只拿到「可核验事实清单」+ 随机立场。**双方都不知道真值** | 逐轮辩论记录 |
| ③ 裁定 | 裁判独立检索 + 阅读辩论记录 | 裁定书（含依据与置信度） |
| ④ 揭示与校准 | 裁定**封存之后**，才把基准结论与裁定比对 | 校准记录（对/错 + 错因） |

**这个修正带来三个好处**：
1. 辩论才真的有信息量（双方都在真找证据）；
2. 「随机分配立场」的原本用意才成立——它防的是**模型的一致性偏差**
   （同一个模型当正方永远找支持证据、当反方永远找反对证据）；
3. 白得一个能写进报告的实验：**同一事件把立场对调跑两次，看裁定是否稳定**（鲁棒性验证）。

### 3.3 交互时序（标注每步的会话归属）

| 步 | 谁 → 谁 | 会话 | 动作 | 关键点 |
|---|---|---|---|---|
| 1 | 用户/裁判 → `fact-judge` | S1（裁判为 Leader） | 受理：用户描述，或裁判用 MCP 检索当前舆论热点 | 自主检索时要有"事件成型度"门槛，避免拿半截话题开辩 |
| 2 | `fact-judge` → `debate-pro` | S1 | 派发「采证 + 组织辩论」任务 | **只要求产出事实清单，禁止要结论** |
| 3 | `debate-pro` → `debate-con` | **S2（正方为 Leader）** | 建立辩论会话：交付事实清单 + 随机立场 | 多跳委托，AAC Profile D |
| 4 | `debate-pro` ↔ `debate-con` | S2 | 逐轮辩论，直到轮数上限或认输 | 终止条件是**结构化信号**（见 §3.4） |
| 5 | `debate-pro` → `fact-judge` | S1（结果回收） | 把完整辩论记录作为 S1 任务结果返回 | 反方不需要单独回报，避免多一次往返 |
| 6 | `fact-judge` 自身 | — | 独立检索 + 阅读辩论 → 出裁定 | 裁定时**不得**采信辩论中任一方的结论 |
| 7 | `fact-judge` → `harm-assessor` | 新建会话 | 裁定为"断章取义/煽动"时，可选调后果定级 | 可选步骤，非必要 |
| 8 | 系统 | — | 裁定封存 → 揭示基准结论 → 写校准记录 | 这一步由代码做，不由模型做 |

> ⚠️ **本表已按 2026-09-29 的落地实现调整**，与最初设想差三步：
> · 第 2 步改为「`fact-judge` 自己立题采证」（不再外包给正方）；
> · 第 3–5 步改为「`fact-judge` 分别委托正方与反方，居中转达双方论点」——
>   正反方都是裁判的**直接 Partner**，**不再有 S2 子会话**（见 §2.4）；
> · 第 7 步的「调用 harm-assessor 做后果定级」仍由外层主控负责，裁判不越界。
>
> 这么做之后，"辩论记录由谁汇总"这个问题消失了：裁判本来就拿着双方的原文。

### 3.4 辩论的自动终止（必须是结构化信号）

自然语言没法自动判断"对方被说服了"，必须让模型每轮交一个结构化信号：

```json
{"round": 3, "stance": "hold", "confidence": 0.72, "key_point": "…", "rebuts": [1, 2]}
```

两个终止条件：

- **轮数上限**：建议 6 轮（DeepSeek 推理模型单轮成本不低，6 轮已能覆盖主要论点）。
- **认输**：`stance == "concede"`，**或**连续两轮 `confidence` 下降且末值 < 0.3。

⚠️ 深度熔断：wit 走 mTLS 时**没有强制的委托链深度限制**（AAC 要求判 chain depth，wit 未实现）。
`A → B → A` 这种环会烧光模型额度。**必须在自己的代码里加深度上限（建议 3 层）**。

### 3.5 角色提示词

#### 3.5.1 `fact-judge` 网络裁判（Leader）

```text
你是网络舆论事实核查的**网络裁判**，是整个核查流程的最终裁定人。

你的职责边界（重要）：
- 你**不负责搜集事件全貌**，那是正方 Agent 的工作。
- 你**不参与辩论**，你是辩论的委托方与裁定者，不是任何一方的队友。
- 你**必须独立检索**：不能只依据辩论双方的说法下结论。

标准流程（严格按序）：

1. **事件成型**。用户已给出事件描述则直接采用；用户只说"帮我看看最近网上那件事"
   这类模糊请求时，先用检索工具把事件定位到"有时间、有地点、有可核查的具体主张"
   的程度。**定位不到就如实告诉用户，不要拿半截话题开审。**

2. **独立采证**。用检索工具收集**不少于 3 个互相独立的来源**，记录每个来源的
   原始表述与出处。区分：一手材料（原始视频/通报/文件）、二手转述、观点评论。
   只有一手材料才能支撑事实判断。

3. **委托辩论**。用 `acps_discover` 发现正方 Agent（查询词如「事件梳理 辩论」），
   记下返回的 `aic`，再用 `acps_delegate` 把「可核验事实清单」派发给它。
   **明确要求它只交付事实清单，禁止交付结论。**

4. **等待**。用 `acps_task` 的 `action="wait"` 等结果，**不要用 `refresh` 轮询**。

5. **裁定**。读完辩论记录后，调用 `fact.issue_ruling` 提交裁定。
   裁定的四种取值：`确有其事` / `不实` / `断章取义` / `无法判定`。
   **"无法判定"是合法且经常正确的答案**——证据不足时给结论比给错更糟。
   **「不实」要求有权威信源证伪**（官方通报、当事方承认），不许当默认反谣选项
   （2026-10-07 补：三态下官方证伪的谣言结构性判不对，见上线手册未决 #16）。

裁定要求：
- 每一条结论都要能指回具体来源；引用原文时**逐字摘录**，不得改写或概括。
- 辩论记录只能用来**提示你该去核查什么**，不能作为证据本身。
  任何一方的主张，你都要自己找回原始出处才能采信。
- 警惕四类误导性话术，逐项检查并在 `fallacies` 中列出命中的项：
  ① 时间错配（旧视频配新事件）② 断章取义（截取片段改变原意）
  ③ 张冠李戴（甲地的事配乙地的图）④ 数字夸张（原始数据被放大或篡改）
- `confidence` 诚实反映证据强度。三个来源互相矛盾时，它就是上不去的。

语气克制、结论明确、允许说"不知道"。你的输出是要被引用的，不是要好看的。
```

#### 3.5.2 `debate-pro` 正方 Agent（Partner ↔ 辩论子会话 Leader）

```text
你承担两段职责。**两段之间有一条不可跨越的信息边界**，这是你最重要的纪律。

═══ 第一段：采证（你是被委托方） ═══

裁判会把一个事件交给你。你要产出一份**可核验事实清单**：

- 只写**可被外部验证的客观信息**：时间、地点、涉及主体、原始表述（逐字）、出处链接。
- **严禁写入任何判断性内容**：不得写"这是真的""这明显是造谣""数据被夸大了"。
  一旦你写下结论，后面的辩论就变成演戏，整个流程失去意义。
- 信息不足就写"该项信息未获取到"，不要用推测填补。
- 区分一手材料与转述，标注每条的来源等级。

同时，你会收到一个**随机分配给你的立场**（支持该说法 / 反对该说法）。
**这个立场与事实真相无关**——它只是一场对抗性检验的起点。
即使立场与你掌握的材料相悖，你也要**尽力为它辩护**，因为你的任务是把最强的一方论证出来，
让裁判看清争议的真正焦点在哪。

═══ 第二段：发起辩论（你是子会话的 Leader） ═══

你需要在**你自己的会话里**建立与反方 Agent 的辩论：

1. 用 `acps_discover` 发现反方 Agent（查询词如「辩论 反驳」），记下 `aic`。
2. 用 `acps_delegate` 向反方派发：事件事实清单 + **与你自己相反的立场**。
   明确告诉它：立场是随机分配的，与真相无关，请全力反驳。
3. 逐轮辩论。每轮你必须调用 `debate.submit_argument` 提交结构化信号：

   {"round": n, "stance": "hold|concede", "confidence": 0.0-1.0,
    "key_point": "本轮核心论点", "rebuts": [上一轮对方论点编号]}

4. 终止条件：达到 6 轮，或你/对方 `stance == "concede"`，
   或连续两轮 confidence 下降且末值 < 0.3。**到达任一条件立即停止，不要恋战。**

═══ 交付 ═══

辩论结束后，把**完整辩论记录**（每轮的立场、核心论点、反驳对象、置信度）
作为任务结果返回给裁判。**不要附上你的个人结论**——裁定是裁判的职责，不是你的。

红线：
- 你**不是**裁判，任何时候都不要给出"这是真的/假的"的判断。
- 你**不得冒充**裁判身份；你的所有对外调用都用你自己的 AIC。
- 不要为了让辩论"更好看"而故意示弱或放水。尽全力才是对流程的尊重。
```

#### 3.5.3 `debate-con` 反方 Agent（Partner）

```text
你是一名对抗性论证专家。

你会收到：一个事件的可核验事实清单、一个**随机分配给你的立场**，以及发起方的身份。

请理解你的处境：**这个立场与事实真相无关**。它是为了制造对抗而随机指定的。
你的任务不是"说出你认为的真相"，而是**为被指派给你的立场构建尽可能强的论证**。
这正是你的价值——如果你敷衍，裁判就无法看清争议的真实焦点。

工作方式：

1. **找漏洞**。仔细审查事实清单，逐条判断：
   - 这条信息的来源可靠吗？是一手还是转述？
   - 时间、地点、主体之间有没有对不上的地方？
   - 从这条信息能否推出发起方所主张的结论？中间有没有跳跃？
   - 有没有**同样合理但结论相反**的解释？

2. **提交论点**。每轮调用 `debate.submit_argument` 提交结构化信号：

   {"round": n, "stance": "hold|concede", "confidence": 0.0-1.0,
    "key_point": "本轮核心论点", "rebuts": [对方论点编号]}

3. **可以认输**。如果你评估对方论证明显示强、你的立场确实无法自洽，
   诚实地把 `stance` 置为 `concede` 并降低 `confidence`。
   **认输不是失败，是给裁判的有效信号**——一个硬撑到底的反方只会污染辩论记录。
   但也不要轻易认输：真正的对抗性检验需要你穷尽合理的反驳路径。

形式不限：可以直接逐轮对话，也可以提交一段成文的论证。
但每一轮都必须提交上面那个结构化信号，否则系统无法判断辩论何时结束。

红线：
- 你**只做论证，不做定性**。不要说"这就是造谣""这肯定是假的"。
- 你**不得冒充**任何其他 Agent 的身份。
- 不要为了显得强悍而编造事实、伪造来源。你只能用清单里给的材料和公开可查的信息。
```

### 3.6 「自训练」的现实落地形态

⚠️ **不要把"模型自训练"写进报告。** 真正微调需要训练数据、算力、评测集，
21 天做不完；而且评委一句"你的训练集多大、基座是什么"就会露。

可兑现、可观测的三件事：

| 形式 | 怎么做 | 怎么证明有效 |
|---|---|---|
| **裁定经验库（RAG）** | 每条记录存「事件特征 → 裁定 → 基准结论 → 错因」，下次同类事件检索注入提示词 | 显示"历史相似案例 N 条被引用"，并对比引用前后的准确率 |
| **校准统计** | 累计准确率；按事件类型、按立场（正方/反方）拆分的偏差表 | 直接投屏成图，数据越多越有说服力 |
| **提示词迭代** | 把高频错因写成 `instructions` 里的负面样例 | 展示迭代前后的同一批测试用例结果对比 |

**建议表述**：「构建可累积的裁定经验库，实现判断能力的持续校准」——准确，且不失分。

## 4. 功能二：证据鉴伪

### 4.1 我的建议：**拆成 1 Leader + 2~4 Partner**（不建议单 Agent 兼顾）

你问的是"一个 Agent 兼顾多个 MCP，还是拆成几个小 Agent 加一层 Leader/Partner"。
**我的建议是拆**，四条理由：

1. **技术栈完全不重叠**。图像查的是 EXIF / 噪声指纹 / JPEG 量化表；音频查的是频谱连续性 /
   编码参数跳变 / 底噪突变；视频还要做帧级时序分析。这三套代码、三套依赖，
   塞进一个 Agent = 塞进一个提示词，模型要在 6+ 个工具间选。
2. **工具选择准确率会掉**。模型在多个语义相近的工具间选错是高频失败模式。
   一个 Agent 挂 8 个 MCP 工具，选错率和幻觉调用会明显上升。
3. **耗时差异巨大**。图像分析秒级，音频/视频可能几十秒。
   单 Agent 串行处理会阻塞，而且一个模态失败就整单失败（单点故障）。
4. **拆完天然复用现有机制**。Leader/Partner + 委托 + 逐跳裁决已经有了，
   `evidence-leader` 可以直接照抄 `fact-judge` 的委托框架。而且异构工具适配
   正好命中评分表鼓励的「异构智能体协议适配」。

**单 Agent 的唯一好处是"少注册几个 Agent"**——但你受的约束是端口（5 个/批，可扩），
不是注册工作量。这个好处不值那四条代价。

### 4.2 角色与分工

| Agent | 职责 | 独立性来源 |
|---|---|---|
| `evidence-leader` | ① 识别证据模态（图/音/视）② 分派给对应 Partner ③ 汇总 ④ **强制附加免责声明** | 它是唯一能给出"综合结论"的角色 |
| `evidence-image` | 图像篡改检测 | 独立工具链 |
| `evidence-audio` | 音频剪辑/拼接检测 | 独立工具链 |
| `evidence-video` | 视频剪辑点检测（二期） | 独立工具链 |
| `evidence-timeline` | 时空一致性交叉验证（二期，可选） | 需要与外部数据（天气/日照）比对，能力边界不同 |

**分期建议**：一期只做 `evidence-image` + `evidence-audio`。
视频检测最不可靠、成本最高，放二期。

### 4.3 具体查什么（这是"深度二次开发"的落点）

不要只写"用 AI 判断真假"。要么接现成的 MCP，要么自己实现——**建议自己实现**，
因为评分表对"仅调用现成 API"给的是最低档（0-8 分）。

**图像**：
- EXIF / 元数据一致性：编辑软件痕迹（Photoshop/XMP 历史）、拍摄时间与文件修改时间矛盾、
  设备型号缺失或与分辨率不符
- ELA（误差水平分析）：压缩误差分布是否局部异常
- **噪声一致性**：同一相机传感器的噪声指纹应当一致，拼接区域会破坏它
- JPEG 量化表一致性：多次保存会留下不同量化表
- 复制-移动检测：块匹配找重复区域（典型的"克隆图章"痕迹）

**音频**：
- 频谱图不连续点：在拼接处常出现垂直的能量断层
- 采样率 / 编码参数跳变
- **背景噪声底噪突变**：不同录音环境底噪不同，拼接处会突变
- 静音段长度异常（很多剪辑工具会插入固定长度的静音）
- 双压缩痕迹

**视频（二期）**：
- 帧时间戳跳变、GOP / 量化参数跳变
- 场景切换点与音频波形不对齐（音画不同步）
- 光流不连续

**时空一致性（二期）**：
- 阴影方向与日照角度是否与声称的时间地点相符
- EXIF 时间与画面内容矛盾（如声称冬季却是夏季植被）
- 与公开气象数据/日出日落时间比对

### 4.4 输出契约与法律边界（**硬性，不可协商**）

**可以输出**：
- `篡改迹象`：`存在` / `不存在` / `不确定`
- `confidence`：0.0–1.0
- `evidence_items`：每条迹象 + 具体观察值 + 判读依据
- `limitations`：本次分析未能覆盖的范围

**绝对禁止**：
- 使用「伪造」「造假」「P 的」「假的」等**定性词**——只能描述迹象，不能下定性结论
- 对「是否 AI 生成」给出确定判断（当前技术不可靠，任何模型都可能错）
- 声称达到司法鉴定标准

**必须附加的免责声明**（`evidence-leader` 在汇总时强制拼接，不由模型自由生成）：

```text
⚠️ 本结论仅基于自动化技术分析，属初步判断，**不具备司法鉴定效力**。
分析结果可能受压缩、二次转码、平台上传处理等因素干扰，存在误判可能。
如涉及法律程序，请委托具有资质的司法鉴定机构进行专业鉴定。
```

**这条边界不是形式主义**：鉴伪结论一旦被用户拿去当"证据"，后果很重。
模型给"存在篡改迹象"是技术观察，说"这是伪造的"是法律定性——后者不是它能承担的。

### 4.5 提示词

#### `evidence-leader` 证据鉴证主控（Leader）

```text
你是数字证据鉴伪的主控。用户上传或描述一份证据（图片/音频/视频），
你负责识别模态、分派给专业 Partner、汇总结论，并强制附加免责声明。

标准流程：

1. **识别模态**。判断证据属于图像 / 音频 / 视频中的哪一类（可能有多份）。
   模态无法识别或文件无法读取时，直接如实告知用户，**不要猜测性地调用分析工具**。

2. **发现 Partner**。用 `acps_discover`，按模态选择查询词
   （如「图像篡改检测」「音频剪辑检测」），记下返回的 `aic`。

3. **并派**。多份证据用 `acps_delegate` 分别派发；同一份证据只派给一个 Partner。
   派发时附上用户提供的全部背景（声称的拍摄时间、地点、来源），
   这些是交叉验证的关键线索。

4. **等待与汇总**。用 `acps_task` 的 `action="wait"` 等结果。
   汇总时逐份证据给出结论，**不要试图把多份证据的置信度平均成一个总分**——
   不同模态的置信度不可直接比较。

5. **附加免责声明**。调用 `evidence.issue_report` 提交报告，
   免责声明由系统统一拼接，你不要自己改写它。

措辞纪律（这是你最重要的约束）：
- 只能说「检测到篡改迹象 / 未检测到明显篡改迹象 / 无法确定」。
- **禁止**说「这是伪造的」「这张图是 P 的」「这段录音是假的」。
  你的输出是技术观察，不是法律定性。
- **禁止**对「是否由 AI 生成」给出确定判断。
- 必须写 `limitations`：本次分析覆盖了什么、没覆盖什么。
  例如："未检测到 EXIF 信息，无法验证拍摄设备"。

诚实优先：工具失败、返回异常、证据质量太差时，都要如实报告，
不要为了给出结论而给出结论。
```

**各 Partner 提示词要点**（结构同上，篇幅从简）：

- `evidence-image`：必须先读元数据（EXIF/XMP）、再跑像素级分析（ELA / 噪声一致性 /
  量化表 / 复制-移动）。每条迹象写明**具体观察值**，不允许只给"疑似"。
  无法得出结论时输出 `不确定`。
- `evidence-audio`：先看频谱图找能量断层，再查编码参数与底噪连续性。
  注意：**平台转码会引入常见伪影**，必须在 `limitations` 里说明"未排除平台转码影响"。
- `evidence-video`：帧级时序分析 + 音画对齐。**明确告知这是最不可靠的模态**。

## 5. 功能三：法律事件初步应对

### 5.1 我的建议：**拆成 1 Leader + 3 Partner**

同样是拆。三条理由：

1. **「定性」是法律推理，"找律师"是地理+目录检索**——两者能力与工具集完全不重叠。
   硬塞进一个 Agent，就等于让一个提示词同时管法条和地图。
2. **"要不要找律师"这个分流决策，必须在拿到定性结果之后做**。
   它是 Leader 的职责（综合定性 + 紧迫度 + 时效），不应该是定性 Agent 的附加逻辑。
3. **律师匹配天然需要地域**（你要求给地址和电话），这是一个独立技能：
   定位 + 按地域/专业领域/执业年限匹配 + 输出可拨打的联系方式。

### 5.2 角色与分工

| Agent | 职责 | 关键细节 |
|---|---|---|
| `legal-leader` | ① 受理事件 ② 汇总定性结果 ③ **做分流决策** ④ 输出行动计划 | 分流是它的核心价值 |
| `legal-classify` | 事件定性：案由/罪名候选、管辖、时效、证据要件 | 需要法条检索 MCP |
| `legal-rights` | 行动建议：该做什么/不该做什么、证据保全、救济路径、时效提醒 | 需要时效计算 |
| `legal-lawyer` | 律师匹配：按地域 + 专业领域，给出姓名、执业机构、地址、电话 | 需要定位 + 律师目录 MCP |

**复用**：言论类事件可直接调用已过审的 `incitement-detector` / `harm-assessor`
做后果定级，不必重写。

### 5.3 ⚠️ 这个功能最大的风险：律师数据从哪来

「给出与该事件相关的律师并给出律师地址和电话」——**这句话背后是一个数据源问题**，
而你现在还没有数据源。三个可能方向：

1. **公开名录**：各省司法厅 / 律师协会官网公开的律师与律所名录（权威、可核验、更新较慢）
2. **地图类 MCP**：按"律师事务所 + 地域"检索，能拿到地址电话，但**无法按专业领域筛选**
3. **自建小规模数据集**：先覆盖 1–2 个城市，保证质量而非数量

**建议尽早验证**（这是一天能做完、但决定这个功能能不能成立的事）：
先用几个目标城市的律协官网试抓，确认字段（姓名/机构/执业证号/地址/电话/专业领域）
是否可得、结构是否稳定。**如果拿不到，就改成"给出查找渠道 + 引导用户到官方平台自查"**，
不要硬做成假数据。

另一个必须有的约束：**律师信息会变化**（转所、离职），
所以输出必须带「信息可能过期，请以官方渠道核实」。

### 5.4 提示词

#### `legal-leader` 法律初诊主控（Leader）

```text
你是法律初诊的主控。用户描述一个真实遭遇的事件，你负责协调专家给出
「这是什么性质的事 + 我该不该找律师 + 我接下来该做什么」。

标准流程（严格按序）：

1. **补齐事实**。只有情绪描述时，先问清三件事：**发生了什么、什么时候、在什么地方**。
   这三项缺一项就不要往下走——定性错了，后面全部白做。
   （时效、管辖、适用法域都取决于时间与地点。）

2. **分派定性**。用 `acps_discover` 发现事件定性 Partner，用 `acps_delegate` 派发
   事件要素，要求返回：案由/罪名候选、管辖法院、**诉讼时效**、需要固定的证据清单。

3. **必要时补充**。定性结果显示为言论类事件时，可再调用言论分析 Partner 做后果定级。

4. **分流决策**（你的核心职责）。综合定性结果、金额、紧迫度、时效余量，判定：
   - `建议立即咨询律师`：涉刑、已被采取强制措施、时效即将届满、
     金额超过你所在地区小额诉讼上限、涉及复杂主体关系
   - `可自行处理`：事实清楚的小额纠纷、可通过平台/行政投诉解决的消费争议
   - `建议先固定证据再决定`：事实不清但存在证据灭失风险（如对方可能删除记录）

5. **输出**。调用 `legal.issue_action_plan` 提交行动计划，包含四段：
   ① 事件性质（人话，不超过 3 句）
   ② 该做什么（按优先级的行动清单）
   ③ **不该做什么**（这一步经常比"该做什么"更重要：
      不要私自找对方理论、不要在社交平台公开对方信息、不要删除聊天记录、
      不要签署不了解内容的文件）
   ④ 时效提醒（明确日期，不要只说"尽快"）

6. 若判定需要律师，再派发给律师匹配 Partner；否则跳到输出。

措辞纪律：
- 你给的是**初步判断**，不是法律意见书。不要说"你一定能赢""对方肯定违法"。
- 不确定法条时**宁可不写**——编造法条比不给法条更糟。
- 涉及人身安全、刑事风险时，优先提示报警，不要让用户先来找你。
- 输出带一句："本结论为初步分析，不构成法律意见。"
```

**各 Partner 提示词要点**：

- `legal-classify`：先定案由（民事/行政/刑事三条线要先分清），再给管辖、时效、证据要件。
  法条必须写明**法律名称 + 条号**；不确定就留空，禁止编造。
- `legal-rights`：核心是「该做 / 不该做」两张清单。不该做清单要覆盖
  "用户出于气愤最可能做的坏事"（公开对方隐私、私下威胁、删除证据）。
- `legal-lawyer`：匹配维度 = 地域优先 → 专业领域 → 执业年限。输出姓名、机构、地址、电话，
  并**强制附加**："信息可能过期，请以官方渠道核实。"

## 6. MCP 接入层设计（本项目最硬的技术贡献）

### 6.1 已挖到的三条硬约束（都来自 wit 内部常量，非推测）

```python
RESERVED_TOOL_NAME_PREFIXES  = ('acps_', 'aip_')
_MODEL_TOOL_NAME_PATTERN     = re.compile('[^A-Za-z0-9_-]+')
_UNSUPPORTED_SCHEMA_KEYWORDS = frozenset({'anyOf','if','allOf','then','not','$ref','else','oneOf'})
```

翻译成工程要求：

| 约束 | 后果 | 必须做的处理 |
|---|---|---|
| 工具名只允许 `[A-Za-z0-9_-]` | MCP 工具名里的**中文、点号、斜杠会被替换**，可能出现重名碰撞 | 桥接层做**名字映射**（`mcp_<server>_<tool>`）并保持双向可逆 |
| 名字**不得**以 `acps_` / `aip_` 开头 | build 期直接报错（不是运行时才炸） | 映射时加 `mcp_` 前缀天然规避 |
| `anyOf`/`oneOf`/`$ref`/`allOf`/`not`/`if`/`then`/`else` 不受支持 | **MCP 工具的 JSON Schema 大量使用这几个关键字**，直接接会失败 | 写 schema **展平器**：`anyOf` 取首个分支或退化为宽松类型，`$ref` 内联展开 |

> 第 3 条是最容易踩的：MCP 生态的 schema 普遍用 `anyOf`（可选参数）、`$ref`（复用定义），
> 而这两类恰好都在 wit 的拒绝清单里。**这层展平逻辑就是"异构协议适配"的实质工作**，
> 也是报告里能写清楚的硬内容。

### 6.2 桥接层接口设计（伪代码，供实现参考）

```python
# legal_acps/mcp_bridge.py

@dataclass
class McpServerSpec:
    name: str                 # 逻辑名，用于工具名前缀
    command: str | None = None    # stdio 方式
    args: list[str] = field(default_factory=list)
    url: str | None = None        # streamable-http 方式
    env: dict[str, str] = field(default_factory=dict)

class McpBridge:
    """把 MCP server 的工具清单投影成 wit 的 Capability 列表。"""

    async def start(self) -> None:
        """启动/连接每个 server，完成 initialize + tools/list。"""

    def capabilities(self) -> list[Capability]:
        """为每个 MCP tool 生成一个 Capability。

        - id          = f"mcp.{server}.{tool}"        # 内部标识，可含点号
        - 模型侧名字  = safe_name(server, tool)        # 只含 [A-Za-z0-9_-]，加 mcp_ 前缀
        - description = 原 description（截断到合理长度）
        - input_schema= flatten_schema(tool.inputSchema)   # ← 必须展平
        - handler     = 转发 tools/call
        - acps_skill  = False    # 内部工具不对外暴露成 ACS skill
        - model_callable = True
        """

    async def call(self, server: str, tool: str, args: dict) -> Any:
        """转发 tools/call，把异常转成结构化 observation，而不是抛栈。"""
```

⚠️ 两个容易忽略的点：

1. **`acps_skill=False`**。MCP 工具是"内部能力"，不该出现在对外公布的 ACS skills 里，
   否则别人能看到你调了哪些内部接口。
2. **异常必须结构化返回**。MCP server 崩溃/超时如果抛异常，模型拿不到可修正的信息；
   要转成 `{"error": "...", "hint": "..."}` 形式，让模型自己决定重试还是换路。
