## 五、验证过程中发现并修掉的三个缺陷

这一节是本文最有价值的部分：**如果不做真实端到端，前两个缺陷会让"跨端互联"实际为空，
但表面上一切正常**（Leader 照样输出一份像模像样的结论）。

### 5.1 Discovery 400 —— `acps_discover` 全部失败（已修）

**现象**：首次真实端到端运行时，`acps.discover` 连续 8 次 `error`，
Leader 只能"独立研判"，两个专家**一次都没被调用**。而 Leader 输出的结论看起来完全正常，
只有末尾一句"专家发现服务持续返回 400"泄露了真相。

**根因**（curl 二分定位）：

| 请求体 | 结果 |
|---|---|
| `{"query":"煽动性识别","limit":5}` | 200 |
| `{"query":"煽动性识别","limit":5,"include_unavailable":true}` | 200 |
| `{"query":"煽动性识别","limit":5,"filter":{"includeUnavailable":true}}` | **400 `40004 FilterInvalid`：`filter 条件不合法：空节点（conditions 与 groups 皆空）`** |

wit SDK 的 discovery 默认 `include_unavailable=True`，`discovery_filter()` 会生成
`{"conditions":[{"field":"onlyAvailable","op":"eq","value":false}]}`，
而 wt 侧的 filter 解析器不认这个形态，判为空节点直接 400。
`include_unavailable=False` 时 `discovery_filter()` 返回 `None`，请求不带 `filter`，正常 200。

`AcpsConfig` 没有任何字段能控制这个行为，因此只能在调用层强制。

**修法**：新增 `legal_acps/wt_compat.py`，把 `AcpsDiscoveryClient.discover` 的
`include_unavailable` 一律强制为 `False`；在 `legal_acps/__init__.py` 里 import 即生效（幂等）。
语义上也更正确 —— Leader 派发任务本来就只要**当前可用**的 Partner。

### 5.2 三进程并发登录互相顶掉会话（已修）

**现象**：`bash scripts/serve.sh start` 一次性起三角色时，**最后一个**（leader）报：

```
[leader] 注册状态：blocked
Error (review_status/RegistryClientError): Could not validate credentials
```

单独 `bash scripts/serve.sh start leader` 则完全正常。

**根因**：三个进程同时用同一账号登录 Registry，后登录的会把先前会话顶掉。

**修法**：`scripts/serve.sh` 新增 `start_roles()`，角色之间串行 + 间隔 6 秒。
实测改完后三角色一次启动全部 serving。

#### 5.3.2 ⚠️ 但 Discovery 索引仍在返回它们（**已复现的平台侧不一致**）

| 侧 | 状态 |
|---|---|
| registry (`/api/v1/agent/client`) | `is_deleted=True`、`is_active=False` ✅ 删除生效 |
| discovery (`/acps-adp-v2/discover`) | 仍返回，且 **`active=True`、无任何删除标记** ❌ |

删除后 3 / 6 / 8 分钟三次复查，**结果一致，未见自动收敛**。
发现结果里这三条的字段列表为：
`['active','aic','capabilities','certificate',…]` —— **完全没有** `is_deleted`/`deleted_at` 之类的标记位。

**结论：平台的发现索引未跟随软删除更新。** 我们这边无解除手段：

- `DELETE /api/v1/agent/client/{agent_id}` 是**软删除**，`openapi.json` 里**没有硬删除接口**；
- `POST /api/v1/agent/staff/{agent_id}/disable` 是 **STAFF 专属**，CLIENT 账号用不了。
