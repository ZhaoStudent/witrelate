## 0 一句话

把一次研判从**输入原文**到**最终结论**之间的**每一跳跨智能体交互**，落成一份
**第三方拿着任务库就能独立复算**的表 —— 它是「可审计」这个卖点的物证，
不是我们自己的日志。

**它和现有 `output/verdict-*.json` 的根本区别**：
verdict 只说「结论是什么」，溯源表要说「结论**凭什么**、**经谁的手**、**每一步在哪条记录里**」。

### 它服务的三类读者

| 读者 | 要回答的问题 | 对应产物 |
|---|---|---|
| 评委 / 答辩 | 「这个 -25 分凭什么？谁给的？」 | HTML 单页（可截图）+ 技术方案里的 Markdown 表 |
| 我们自己 | 出问题时「是哪一跳、哪个 Partner、哪一步」 | 终端树 + JSON |
| 附加分③（互联存证） | 「平台上的访问与交互记录」 | 「复算指引」一节：给出一条命令，任何人可自行重现 |

## 1 事实基线（实测，2026-10-02）

### 1.1 权威来源 = 任务库

6 个已注册角色各有一个由 wit 框架落盘的 SQLite：

```
.wit/<role>/acps/aip-tasks.sqlite3
```

实测数据量表（截至 2026-10-02 02:27Z）：

| 角色 | tasks | events |
|---|---|---|
| leader | 44 | 528 |
| fact-judge | 25 | 200 |
| incitement | 20 | 93 |
| harm | 15 | 63 |
| debate-pro | 10 | 40 |
| debate-con | 7 | 28 |

**这两张表就够重建整条链**（下面 1.3 证明产物也在里面）。

`aip_tasks` 的 17 列中，溯源用得上的：

| 列 | 用途 |
|---|---|
| `task_ref` | 本端这条任务的唯一标识（**下游事件按它索引**） |
| `task_id` | AIP 协议级任务号（**一跳两端配对用的硬键**，见 1.2） |
| `session_id` | 局级分组（**只在本层有效**，见 1.2） |
| `direction` | `outbound`=我发起的委托 / `inbound`=别人委托我 |
| `local_aic` / `remote_aic` | 谁 → 谁（**这是链路的边**） |
| `state` | 生命周期终态（`completed` / `failed` / `awaiting-completion` …） |
| `command_history` | **我发出去的每一条命令**（JSON 数组） |
| `products` | **对端回传的产物**（JSON） |
| `created_at` / `updated_at` | 该跳的起止（**推算耗时的唯一依据**） |

`aip_task_events`：`event_seq` / `event_type` / `event_data`(JSON) / `created_at` —— 对端每一次回执。

### 1.2 ★ 关联键的实测结论（本设计的核心约束）

这是整份设计里唯一必须先弄清的事，实测结果如下：

| 候选键 | 能否跨层级 | 实测证据 |
|---|---|---|
| `session_id` | ❌ **只在本层内** | leader 的 3 条 outbound 同属 `session-…4075e4a6bb98`；但 fact-judge 给辩手发委派时用的是**另一个** session `…1e24e1f191d2`。⇒ 拿 session_id 去辩手库里查是 **0 条**。 |
| `task_id` | ⚠️ **一跳之内配对**（硬键） | leader outbound `task_id=2a5d6bc65822` ↔ fact-judge inbound `task_id=2a5d6bc65822`，**完全一致**；`…047a7f522fc5`（→煽动识别）、`…40bcf8e0493b`（→危害评估）同样一致。 |
| 时间包含 | ✅ 可用但**是推断** | fact-judge 内层 outbound session 起于 `02:26:58`，落在 leader 那条 task（`02:26:32` 起、`state=working`）的**生命周期之内**。 |

**结论：没有任何一个键能贯穿三级。**

⇒ 这直接决定了两条设计纪律：

1. 溯源表**分层呈现**：每一条边（A→B）都是硬事实；**跨层的归属必须显式标注为推断**。
2. 输出里每条关联都要带 `evidence` 字段（`hard` / `derived` / `inferred`），
   **绝不让推断长得跟硬事实一样** —— 这是本项目对「静默给出错误结论」的一贯态度。

### 1.3 产物也在任务库里（⇒ 溯源表可以自足）

`aip_tasks.products` 实测内容：

```json
[{"id":"report_incitement","name":"煽动性言论判定",
  "dataItems":[{"type":"data","data":{"is_incitement":true,"kinds":[...],
  "severity":50,"evidence_spans":["最近治安这么差", ...]}}]}]
```

⇒ **Partner 交回的完整产物，逐字在任务库里**。溯源表因此**不需要读任何中间文件**，
只靠 `.wit/*/aip-tasks.sqlite3` + 一个指向最终 verdict 的指针即可。

### 1.4 唯一的缺口：`verdict-*.json` 里没有 session_id

实测 `output/verdict-20261001T145351Z.json` 的 9 个字段（`subject` / `harm_index` /
`band` / `is_incitement` / `truth_score` / `consistency_note` / `conclusion` /
`action_advice` / `disclaimer`）—— **没有任何一个指向本次运行的会话**。

⇒ 一份 verdict 和它对应的任务记录**无法自动关联**，只能靠时间戳近似。
**这是必须补的一处**，补法见 §3.3。

> ⚠️ **不能靠改 `FinalVerdict` 加字段** —— 它是对外契约。稳妥做法是落盘时
> **在 verdict 旁边写一个 sidecar**，用**同一个时间戳**做文件名配对
> （`verdict-20261001T145351Z.json` ↔ `verdict-20261001T145351Z.meta.json`）。
> 这样零契约改动、零 ACS 风险。

## 2 输入

### 2.1 主输入（平台落盘，权威，只读）

```
.wit/<role>/acps/aip-tasks.sqlite3   × 6 个角色
```

只读取 §1.1 列出的列。**不写入、不迁移、不加索引**（任务库是平台的，我们只是读者）。

### 2.2 辅输入（我方落盘）

| 文件 | 内容 | 必需性 |
|---|---|---|
| `output/verdict-<TS>.json` | 最终结论九字段 | **必需**（溯源的终点） |
| `output/verdict-<TS>.meta.json` | **新增 sidecar**：`{session_id, role, started_at, finished_at, input_text, aics: {...}}` | **必需**（关联用的握手） |
| `output/ruling-<TS>.json` | 内层裁判裁定书 | 可选（有则附在裁判节点下） |

### 2.3 明确**不采用**的输入（重要）

| 不采用 | 理由 |
|---|---|
| `DebateChainGuardHooks.dispatched` | **进程内内存态**：重启即失，且第三方无法验证。它是给运行期护栏用的，**不得作为溯源依据**。 |
| 任何运行期的 `print` 日志 | 同上；且日志可被编辑，不构成证据。 |
| 我们自己算的耗时 | 必须来自 `aip_tasks.created_at/updated_at`，否则又是"同一事实算两遍"。 |

> **一句话原则**：溯源表里出现的每一个事实，都要能回答"它写在平台哪个文件的哪一行"。
> 回答不了的，就不该进来。

## 3 输出（三件套，同一份数据）

### 3.1 `output/trace-<TS>.json` —— 机读

```jsonc
{
  "schema": "legal-acps/trace@1",
  "generated_at": "2026-10-02T02:31:00+00:00",   // 生成时刻（不是运行时刻）
  "source_files": [                               // ★ 复算指引：用了哪些文件
    ".wit/leader/acps/aip-tasks.sqlite3",
    ".wit/fact-judge/acps/aip-tasks.sqlite3",
    "..."
  ],
  "run": {                                        // 本局（由 sidecar 给出）
    "session_id": "session-171b50d5-…-4075e4a6bb98",
    "verdict_file": "output/verdict-20261001T145351Z.json",
    "subject": "网传某学校食堂使用过期食材，……",
    "started_at": "2026-10-02T02:26:32+00:00",
    "finished_at": "2026-10-02T02:27:47+00:00",
    "wall_ms": 75130
  },
  "hops": [                                       // ★ 链路：一跳一条，全部是硬事实
    {
      "seq": 1,
      "from": {"role": "leader",   "aic": "…HKBBAM.018M"},
      "to":   {"role": "incitement","aic": "…F9XC6K.0J6D"},
      "task_ref": "task_d8e1d12f1473",
      "task_id": "task-4465f1e7-…",
      "session_id": "session-…4075e4a6bb98",
      "state": "awaiting-completion",
      "sent_at": "2026-10-02T02:26:32.283948+00:00",
      "last_event_at": "2026-10-02T02:27:47.100000+00:00",  // 末条事件时刻
      "latency_ms": 74816,
      "request_excerpt": "请对以下待研判文本同时给出两项结论：…",  // 截断，全文在证据里
      "product_ids": ["report_incitement"],
      "events": 12,
      "health": "ok"                              // ok | slow | failed | pending
    }
    // … 主控的 3 条 + 内层的 N 条
  ],
  "chain_edges": [                                // ★ 跨层归属：显式带证据强度
    {"from_task_ref": "task_acb78b3c7d82", "to_session_id": "session-…1e24e1f191d2",
     "relation": "parent-child", "evidence": "inferred",
     "why": "内层 session 起止时间落在外层 task 生命周期内；无协议级硬键"}
  ],
  "verdict_fields": [                             // ★ 逐字段溯源
    {"field": "harm_index", "value": -25,
     "source": {"kind": "partner_product", "role": "harm",
                "task_ref": "task_3242ae82425f", "product_id": "report_harm"},
     "evidence": "hard"},
    {"field": "is_incitement", "value": false,
     "source": {"kind": "partner_product", "role": "incitement",
                "task_ref": "task_d8e1d12f1473", "product_id": "report_incitement"},
     "evidence": "hard"},
    {"field": "conclusion", "value": "这条信息属…",
     "source": {"kind": "leader_synthesis",
                "based_on": ["report_incitement", "report_harm", "ruling"],
                "note": "consistency_note 已说明取舍理由"},
     "evidence": "derived"}
  ],
  "gaps": [                                       // ★ 诚实清单：找不到来源的字段
    {"field": "action_advice", "reason": "主控综合判断，无对应 Partner 产物"}
  ]
}
```

**三条设计纪律写在这个 schema 里**：

1. 每条跳都带 `task_ref` + `session_id` ⇒ 任何人可回任务库**逐字复核**。
2. `chain_edges` 必带 `evidence`，且**不许出现没有 `why` 的 `inferred`**。
3. `gaps` 是**必需字段**：宁可列出"这一项找不到来源"，也不许静默留空 ——
   空着会被读成"没问题"。

### 3.3 `output/verdict-<TS>.meta.json` —— sidecar（唯一需要动代码的地方）

```jsonc
{
  "session_id": "session-171b50d5-12e3-46a5-91fb-4075e4a6bb98",
  "role": "leader",
  "aic": "1.2.156.3088.1.M3FX.X1J5R5.HKBBAM.018M",
  "started_at": "2026-10-02T02:26:32+00:00",
  "finished_at": "2026-10-02T02:27:47+00:00"
}
```

- **落点**：`run_agent.py` 里 leader 落盘 verdict 的那一处（与 verdict 同时间戳、同目录）。
- **不动 `FinalVerdict`**：对外契约字段一字不改 ⇒ **ACS 指纹不变 ⇒ 不需重审**
  （仍会用 `tools/acs_fingerprint.py` 实测确认，不靠推断）。
- **缺了会怎样**：生成器回退到"按时间戳在任务库里找最近一个 session"，
  并在输出里把 `chain_edges` 全标成 `inferred` + 顶部打一条 `WARNING`。
  **能降级，但必须让你看得见**。

## 11 缺陷排查与加固（2026-10-03 第二轮）

### 11.1 为什么还要做这一轮

§10 证明的是「它能跑通、能在真机上重建出正确的链路」。但**跑通不等于没有静默缺陷**。
这一轮按项目既定口径专找**那一类**缺陷：产出看起来完全正常、其实是另一回事。

方法两条：① 逐个去看**交付出去的值**（三种渲染 + 机读 JSON），不看源码"看起来对不对"；
② 对每个可疑点先想清楚"它会以什么形态失败"，再造一个**能咬住它**的形态。

| `hops[].request_excerpt` 去掉了开头的字面 `text`，并恢复了被截断的正文 | **第 1 处的实证据**：旧样本里那一行本来就是假的 |

| **跳数、跨层边数、硬溯源字段的命中片段** | **完全没变** ⇒ 链路重建逻辑在真机上行为一致 |
| HTML 单页里**我们自己文案**的 `**` 归零 | 见 §12.7（旧/新样本对照 + 渲染层实测） |

> ⚠️ **本表原先写的"HTML 单页里 `**` 从 7 处降到 4 处"作废。** 那是在两个**不可比**的
> 批次之间数的：当天 19:55 那批重跑用的命令参数与原生成流程不同（样本 1 单页 7281 字节，
> 而原流程产物是 18035 字节 —— 差了一倍多，说明产物形态就不是同一种），
> 拿它跟原样本做前后对照不成立。第三轮改用**同一流程**重跑，并给出渲染层实测判据。
> 教训：**"前后对比"必须先用一个可核对的量证明两批同质**（这里是产物字节量级与字段数），
> 否则数字看着精确，其实在比两样东西。

> 最后一行是本轮一个重要的口径决定：**不能**一刀切要求"整页没有 `**`" ——
> 那会把真人数据判成失败，也会诱使人去改**证据**。断言的范围必须只圈
> **我们自己的文案**（用例 N 的 `_own_md`）。

### 11.8 四条经验

1. **「说了但没做」比不说更危险**：`_field_span` 的 docstring 早就要求"渲染时写明它
   不是平台级认证"，渲染层却一直没做 —— 代码里留着"已经处理过"的印象。
2. **断言的范围要圈对**：整页判"没有 `**`"会误伤证据；只判"我们自己写的"才对。
3. **依赖"字典序恰好等于时间序"就是依赖巧合**：平台换一种偏移写法就会静静取错端点。
4. **元验证自己的恢复机制也会静默失效** ⇒ 必须有一条**不依赖信号**的落盘兜底。

## 12 第三轮：并发事故，与"检查器自己的缺陷"（2026-10-03 深夜）

这一轮的起因不是新功能，是**上一轮修完之后的收尾过程中，元验证自己出了事故**。

### 12.1 事故：两个元验证并发跑，把源文件停在旧形态

发现时（20:04）机器上有 **4 个** `python -m run.meta_verify_trace` 进程、4 个
`-m tools.verify_trace` 子进程。它们是 **20:01 与 20:02 两次逻辑运行**（见 §12.2）。

后果不是"报错"，而是**静默**：

| 现象 | 实质 |
|---|---|
| `tools/trace.py` 少了 `_verdict_files()` 里 `if not p.endswith(".meta.json")` 那一行 | **T2 的旧形态真的落到盘上了** —— sidecar 会被当成 verdict 捞进去，"最新一局"变成 sidecar，**整局定不出来**。这不是探针构造的假想形态，是真实留下的一份错代码 |
| `heal_from_backup()` 报"检测到上次被掐断的残留，已自愈" | 一个实例把**另一个实例正在用的 revert 修了回去**，还顺手**删掉了对方的 `.metaorig` 备份** —— 于是对方在"文件其实已是新形态"的前提下继续跑探针 |
| 双方日志都**没有** `❌` | 两边都可能打印"21 处旧形态全部被逮到 ✅"，而盘上的文件停在中间形态 |

**一个能静默并发、并给出可信外观的元验证，比它要验的那些缺陷更危险** ——
它是其它所有验证的认证者。

### 12.2 必须先澄清的事实：Windows 上 venv 的 `python.exe` 会派生两个进程

实测（同一个 `--` 参数，`Win32_Process` 抓的父子关系）：

```
PID=9460  PPID=38716  CMD=...\.venv\Scripts\python.exe -c "import time; time.sleep(90)"
PID=18888 PPID= 9460  CMD=...\.venv\Scripts\python.exe -c "import time; time.sleep(90)"
```

一次 `./.venv/Scripts/python.exe …` = **启动器 + 真解释器两个进程**（argv 完全相同）。
机制是 Python 3.7.2+ 在 Windows 上的 `venvlauncher`：venv 里那个 `python.exe` 通过
`pyvenv.cfg` 找到基座解释器后**派生一个子进程**并等它。

于是有两条推论，一条纠正了上一轮的判断、一条解释了"残留进程"从哪来：

1. **纠正**：上一轮我写"四个元验证在并发跑"**不准确** —— 那 4 个 PID 是 **2 次逻辑运行**。
   （危险性不变：2 个就足够互相踩。）
2. **来源**：**父启动器被杀掉后，子解释器会变成孤儿继续跑**。所以"上一轮那个进程其实还活着"
   完全是可能的 —— `.metaorig` 自愈机制这次就是这么被触发的。

### 12.3 修：单实例锁 —— 拿不到就**大声拒绝启动**

| 决策 | 理由 |
|---|---|
| 锁文件放**系统临时目录**（`%TEMP%/acps_meta_verify_trace.lock`），不放仓库 | 它是运行期产物；放进 `run/` 会让 `tools/tree_diff.py` 每次 diff 都多一条"内容总在变"的文件 |
| 用 `os.open(..., O_CREAT \| O_EXCL)` 原子创建 | 两侧平台都有；**不能用 `fcntl`**（Windows 没有），**也不能用 `os.kill(pid, 0)`**（Windows 上不支持 sig=0） |
| 存活判断用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess` | 与 `os.kill` 不同，它**不会误杀**任何东西 |
| **陈旧锁自动回收** | 否则上次被 SIGKILL 之后，元验证会**永远拒绝启动**，而且拒绝的理由看起来还挺合理 |

加锁的**位置**和加锁本身一样要紧：`加锁 → 自愈 → 快照`。位置错了锁就等于没装
（自愈会删掉对方的备份、快照会把"别人 revert 到一半的内容"当原始内容存下来）。
这条用**关系断言**钉住（只断先后，不断言行号）。

### 12.4 锁的自检与反证

锁每次运行都自检两项，**并且两项都有反证**（证明它不是空转的）：

| 判据 | 正向 | 反证 |
|---|---|---|
| ① 已持有时**再拿必须被拒** | ✅ 被拒 | 把 `_acquire_lock` 换成"永远成功" ⇒ 自检当场报"这把锁挡不住并发，「拒绝并发」是句空话" |
| ② **死 PID 的陈旧锁必须能回收** | ✅ 回收 | 把 `_pid_alive` 换成"永远活着" ⇒ 自检报"自检前提不成立：PID 999999999 居然被判成活着" |
| ③ 真进程持有的锁**抢不走** | ✅ 返回"另一个 `run.meta_verify_trace` 正在跑（pid=…）" | —— |
| ④ 正常结束**要还锁** | ✅ 跑完锁文件消失 | —— |
| ⑤ 启动次序必须是 `加锁 → 自愈 → 快照` | ✅ | 把"加锁"挪到"快照"之后 ⇒ 断言报"启动次序不对" |
| ⑥ 次序断言的三个标记必须**唯一** | ✅ | 抹掉标记 / 复制成两处 ⇒ 断言分别报"定位不到唯一的…" |

### 12.5 ⚠️ 自检自己的两个缺陷（同一类：**判据匹配到了它自己的实现**）

这一轮最有价值的收获不是修好了锁，而是**新写的自检立刻抓出了它自己的两处缺陷**
（两处都是"三处标记全报 2 处"这种**恒假**的判据 —— 一个恒假的判据比没有判据更坏）：

| # | 缺陷 | 根因 |
|---|---|---|
| 1 | `_startup_order_problems` 的 `marks` 字典里**写着标记字面量** ⇒ 全文件计数把"自己"也数进去，3 处全报 2 处 | 判据匹配到了它自己的源码 |
| 2 | 改成按 `def main(` 定扫描起点后**依旧全报 2 处** —— 因为 `def main(` 的**第一个**匹配点是本函数里那行 `anchor = "def main() -> int:"`（它比真正的 `def main` 更靠前） | 同一个跟头，换了个位置栽 |

修法：标记一律**用相邻字面量拼**出来（`"_acquire_lock(" "LOCK_PATH)"` —— Python 编译期
接成完整串，而**源码文本里不含**完整标记）。这样**结构上不可能**自匹配，不必再依赖
扫描边界这类脆弱假设。

> **判据不许匹配到它自己的实现。**

### 12.9 五条经验

1. **认证者自己的失效最危险**：元验证若能并发并给出"全部通过"，它就把其它所有验证一起

2. **"装了"≠"会响"，位置也算"装"**：锁装在自愈/快照之后等于没装 ⇒ 只能靠**关系断言**钉。
3. **判据不许匹配到它自己的实现**：判据自己也是一个字符串常量，它会被自己的计数数进去。
4. **覆盖的分支集合是手挑的，手挑就会漏掉恰好出问题的那一条** ⇒ 要么**现场派生**分支集合，
   要么补一条"证明这条分支确实被走到了"的正向判据。
5. **前后对比必须先证明两批同质**（§11.7 那个作废的"7 处→4 处"就是反例）。

## 13 第四轮：让"基线过期"这件事**判得出来**（2026-10-04 上午）

第三轮留下的唯一已知缺口是 §12.7.1：全树 md5 diff **用不了**，因为基线过期了。
本轮只做这一件事 —— 不是"再记一次基线"（那治的是症状），而是**把这个缺口变成机器判据**。

### 13.1 要害：判据自己变成了误导

10-03 那次的现象是 `diff` 报"改动 240 个文件（基线只有 199 个）"。
单看这句话**毫无异常感** —— 它长得像"改动多了一点"，而真相是那份清单里
**混着当天别的几轮改动**。也就是说：**判据没坏，它只是失去了资格，却照常给结论。**

所以修法不是"记得重记基线"（那是纪律，纪律已经失守过一次），而是：
**让工具在没资格的时候，拒绝给结论。**

### 13.2 试过但**不成立**的判据：mtime

直觉方案是"文件 mtime 比基线时间新 ⇒ 基线过期"。**不成立**，理由要说清楚：

元验证**每跑一个探针都会无条件回写**它的 CASES 文件（`[3] 复原` 那一步）。
于是一次**完全干净**的元验证跑完，这些文件的 mtime 也**一定**比基线新。
⇒ "mtime 比基线新"会在**每一次干净运行**上响，而**一个永远在响的警报与没有警报等价**
（本仓已两次踩过同型坑：`SNAP` 没排除自己 ⇒ 恒报"改动 1 个"；`.workbuddy` 没排除 ⇒
恒报一条"新增"）。

更彻底地说：**mtime 只能证明"被写过"，证明不了"被谁写的、属于哪一轮"。**
两句话的区别，正是"看起来在验证"与"真的在验证"的区别。

### 13.3 成立且可靠的判据：`--expect-cases`

**「本轮只该动哪些文件」是可以由调用方声明的。** 元验证的 `CASES` 里本来就写着
它要动哪些文件；传进来即可：

```
python -m tools.tree_diff diff --expect-cases run.meta_verify_trace
```

```
改动里出现任何**不属于本轮**的文件
  ⇒ 那些改动**不可能由本轮产生**
  ⇒ 基线是更早留下的、跨了别的轮次
  ⇒ 本次 diff **不能用来判「本轮有没有残留」**    （exit 3）
```

这正好是"逐条核对每个改动是不是你自己有意改的"那条纪律的**可执行版本** ——
原先它只能靠人眼，而人眼恰好是 10-03 那次失守的地方。
预期集合是**现场派生**的（`importlib` 导入各模块、取 `CASES[i]["file"]`），
不是手写清单 ⇒ 元验证加用例时它自动跟上，**不会各自漂移**。

### 13.4 退出码：`1` 与 `2` 的区别是**本质的**

| 码 | 含义 |
|---|---|
| 0 | 全树与基线逐字节一致 |
| 1 | **跑出了结果**，清单在下面 |
| 2 | **没有资格给结论**（用法错 / 没有基线 / 指定模块导不进来） |
| 3 | **有差异落在本轮预期清单之外** ⇒ 基线不可用于判本轮 |

修的过程中撞到一个真缺陷，值得单记：`raise SystemExit("……")`（字符串参数）的退出码是
**1**，不是 2。于是"你把模块名写错了"与"树里确实有一点差异"在退出码上**一模一样** ——
**闸门失效得不声不响**，调用方会拿着那份不该信的清单继续往下判。
同类的还有一处：本文件顶部承诺 `2 = 没有基线`，而**代码里给的是 1**。
⇒ **文档里承诺的闸门、代码里没有，比两处都没有更危险。**

现统一走 `bail()`：信息打到 stderr、退出码显式传参。

### 13.5 ★非空洞性★：证明 `3` 不是"只要有改动就响"

`exit 3` 这个判据有个致命疑点：它完全可能只是"检测到差异"的同义词。
若如此，`--expect-cases` 那套声明就是个摆设 —— 而它在外表上与"装好了"一模一样。

所以探针里专门有一对**同一个改动、只换声明**：

| 步 | 输入 | 声明 | 期望 | 含义 |
|---|---|---|---|---|
| C | 改 `run/_tree_diff_probe.txt` | `run.meta_verify_trace`（不含它） | **3** | 落在预期外 ⇒ 拒绝 |
| D | **同一个文件、同一个改动** | 一个临时模块，CASES 里**正好是它** | **1** | 落在预期内 ⇒ 放行 |

C=3 / D=1 才说明这是一道**在分辨的**闸门。少了 D，"3"什么都不能证明。

### 13.6 实测：真基线确实被判成"不可用"

拿**那份真的过期基线**（`run/.tree_snapshot.json`，老格式裸 dict、199 个文件、
mtime 2026-10-03 15:07）实跑：

```
[diff] 比对 241 个文件（基线 199）
[diff] 基线时间：2026-10-03T15:07:42+08:00（距今 19h38m）
       来源：基线文件的 mtime（老格式没有 _saved_at，只能顶一下）
[diff] 本轮预期改动清单（2 个，来自 run.meta_verify_trace（21 条用例））：
          tools/aip_sessions.py
          tools/trace.py
[diff] ❌ 有 54 处改动**不在本轮预期清单内**
[diff] ⇒ 本次 diff **不能用来判「本轮有没有残留」**
EXIT=3
```

对照第三轮那次"混着别轮改动、看起来只是多了一点"的 240 个 —— 现在是**明确的 3**，
且**点名**了越界文件。**这就是本轮要的那个区别。**

顺带确认了两件事：
* **老格式照样能读**（不许因为升级工具就逼人重记基线 —— 重记基线恰恰是 10-03 被忘的那一步），
  且**如实标明**"时间是从 mtime 顶的"。
* 执行顺序：**先解析 `--expect-cases`、再判树**。反过来的话，树干净时会**在解析之前**
  就 `return 0`，写错的模块名**根本没被求值** —— "你以为装了闸门，其实它没跑"。
  这个 bug 探针**真的逮到过**（F 步第一次跑：exit 0）。
  ⇒ **声明的闸门必须无条件求值**，与"这次有没有差异"无关。

### 13.7 顺带清掉"恒报噪音"（**不许靠加排除项解决**）

仓库根目录有三个上一轮留下的临时文件（`_ag.tmp`、`_b64.txt`、`_remote_cmd3.sh`）。
它们**不在同步集里**（不影响部署），但**在 `walk()` 的树里** ⇒ 每一次 `diff` 都会
恒报"新增 3 个"。这与 §13.2 那条是**同一个病**：恒报 = 不报。

处理方式：**移到临时目录归档**（`%TEMP%/witrelate-scratch-2026-10-04/`），**不是**加进
`EXCLUDE_DIRS`。理由：加排除项会把"**真的**多出一个根目录文件"这件事一起挡掉 ——
用致盲换安静。**噪音要从根上消掉，不能用扩大盲区来消掉。**

### 13.9 新基线与其判据

清完噪音后重建基线（格式 v2，带 `_saved_at`）。此后每一轮的纪律变成**三步**：

```
① python -m tools.tree_diff save                          # 跑之前
② python -m run.meta_verify_xxx                           # 跑
③ python -m tools.tree_diff diff --expect-cases run.meta_verify_xxx
```

第③步只有在 **exit 0** 时才等价于"零残留"；
**exit 3 = 基线不可用，本轮结论作废**（不是"有点差异"，是"没有结论"）。

⚠️ 还有一个计数上的**已知错位**（不是 bug）：用 `TREE_SNAPSHOT` 把基线指到临时目录时，
真基线 `run/.tree_snapshot.json` 就不再被 `walk()` 排除，会被算成一个普通文件。
实测：真跑 **238**、探针跑 **240**（多出探针自己那个临时文件 + 真基线）。
自洽性不受影响，但**跨两种跑法的绝对数不可直接比**。

### 13.10 经验（承接 §12.9）

1. **判据会失去资格，但不会自己知道** ⇒ 每个判据都要回答"**什么情况下我拒绝给结论**"。
   只会输出"有点差异"的判据，在基线过期时是**误导源**。
2. **一个永远在响的警报与没有警报等价** —— 第三次踩到了（SNAP 自身 / `.workbuddy` / mtime）。
   凡是"每次都会响"的方案，先当它没响。
3. **噪音要从根上消，不能用扩大盲区来消**（§13.7）。
4. **"分得开"要比"会响"更强**：必须构造一对**只差一个变量**的输入，让闸门给出**不同**的结论
   （C=3 / D=1）。只会响的闸门，与 `exit 0` 没区别。
5. **文档承诺而代码没实现的闸门，比不承诺更危险**（§13.4 的两处：字符串 `SystemExit`、
   "没有基线 ⇒ 2"）。**承诺必须由本文件自己兑现。**
6. **退出码 `1` 与 `2` 混用，等于没有退出码**：`1` 是"有结论"、`2` 是"没资格"。撞车之后，
   调用方**没有任何办法**区分"你要小心看这份清单"和"这份清单别信"。
