## 3 缺口清单（按"值多少分"排）

### 3.1 ⚠️ 发现环节还差一口气（影响 AI 技术应用满分档）

实测：`limit=10/20/50` → **本账号恒 2 条**，而全局 12→13 条。

- 这说明 **8 个已注册 Agent 里只有 2 个能被 discovery 召回**，其余 6 个检索不到。
- 平台的 ADP 索引是最终一致性（分钟~小时级），且**我们无解除手段**（ACS 无可见性字段，已实测）。
- **判断口径**：不认"列表里有"，只认**重查 discover 的返回条数**。

**能做的**：
1. 把「一条命令重查 discover + 打印本账号召回条数」做成**可重复的存证脚本**（现在 `probe_discovery_limit` 已经能跑，缺的是"按角色逐条点名"）。
2. 演示视频里**必须录到 discover 返回自己人的那一刻**，否则"设备自动发现"这一项只有口头声明。

### 3.2 🔴 "跨端"两个字目前是空的（影响必要验证场景的成色）

评分表满分档的措辞是 **「设备自动发现、跨智能体双向通信」**，
必要验证场景的措辞是 **「跨端互联访问全流程验证」**。

**实测现状：8 个 Agent 全部部署在同一台服务器的不同端口**（`ss -ltnp` 四个端口同 IP）。
⇒ 现在证明的是**同机跨进程**，不是**跨端**。

**这是目前"名实最不符"的一处**，也是最容易被评委一句话问穿的地方。
**建议**：把 2–4 个证据链 Agent 迁移到**第二台机器**（或至少另一个公网出口），
让"跨端"成为可截图的事实。成本：半天到一天；收益：直接坐实满分档措辞。

## 6 本轮顺带修掉的一处真缺陷（诊断脚本假阴性）

`run/e2e_video_live.py` 的工具回执提取**认错了部件类**：

- wit（v2.1.0）**没有** `ToolResultPart` / `ToolCallPart` 这两个类（已内省确认），
  工具回执是 `role="tool"` 消息里的 **`TextPart`**；
- 原实现只认 `ToolResultPart` ⇒ 三次全真模拟里工具**各返回了 5000+ 字**，
  脚本却在"工具返回全文"段打印「**模型没调工具，这一跳等于没干活**」。

**危害**：这正是本项目反复警告的「**诊断报假阴性**」——复核方会据此得出与事实
完全相反的意见（"视频工具根本没被调用"）。已修为**以 `role == "tool"` 为准**
（兼容他版），并把"最终答复"从 `output_parts` 里筛掉 `ReasoningPart`
（否则会把模型的内部思考当结论打出来，另起一段标明"这是思考、不是结论"）。

## 8 2026-10-05 增补：访问量从「靠人记得」变成「每天自动一轮真链路」（#27）

> 本节只写**相对上面那份 10-03 快照变了什么**，不改上面的数字（它是带日期的快照）。

**问题**：上面 §2 的「附加分」里写着「③ 访问量仍极低」—— 而访问量是**时间的函数**：
停一天就**永久**少一天，事后补不回来。之前它挂在一条**每 2 小时跑一次完整轮**的
自动化上，问题有三：① 频次高到**会与常驻服务抢 Registry 会话**（并发登录会顶掉彼此）；
② 它跑的是"复验网络裁判能不能被检索到"，属**另一件事**，产物没有专门判据；
③ 靠自动化本身"记着跑"，没有任何东西能证明"今天到底跑没跑成"。

**现在**：新增**每天一次**的真实案例定期研判。

| 维度 | 做法 |
|---|---|
| 频次 | `OnCalendar=09:17` + `RandomizedDelaySec=600`（躲开整点与半夜 logrotate）；`Persistent=true` 补跑 |
| 材料 | `legal_acps/case_library.py`：**13 条公开可溯源案例 / 9 类**（食品安全 / 饮用水 / 自然灾害 / 安全生产 / 公共秩序 / 金融秩序 / 民生服务 / 深度伪造 / 网络摆拍），每条**点名发布方 + 日期** |
| 轮换 | **无游标文件** —— 每次从**台账现场算**"哪个案子跑得最少"（游标文件就是第二份事实源，必然漂移） |
| 与常驻服务错开 | **不用 `sleep`**（那是猜的），改用**偏移闸门**：量最年轻常驻进程的年龄，< 180s 就今天不跑；**量不出来 ⇒ 不拦但报原因**（开发机没有 systemd，拦下等于功能永远不跑） |
| 通过判据 | **唯一硬判据 = `output/` 新增 `verdict-*.json`**；`status=completed` 不算；退出码 **2 = 跳过（≠ 通过）**，真相在 `case_rounds.jsonl` 的 `outcome` 字段 |
| 工程强度 | `check_local` §3d + 离线探针（闸门/四项体检逐个造）+ **13 条退回用例的元验证** + 残留核对登记（锚点 129 → 142） |

**对分数的直接作用**：把"访问量低"这件事从**不可控**变成**可排期、可举证**的
——「连续 N 天每天跑通一轮完整链路」本身就是"稳定完成"的证据，而不是一次性的演示。

**本轮顺带抓出并修掉的三处真缺陷**（都在"看起来全绿"的地方，详见当日工作日志）：

1. 🔴 **新元验证模块的 13 个锚点从来没被残留核对过**：`check_meta_residue.py` 的
   `SOURCES` 是**写死的登记表**，而用例必须是 `{file, new, old, name}` 形态；第一版写成
   "函数式退回 + 4 元组" ⇒ 接口不兼容 ⇒ **既没登记、也没法登记**，「129 处全部通过」
   看着一切正常。
2. 🔴 **同步清单按扩展名白名单收文件，第三次踩**：`("deploy","**/*.service")` 收不到
   仓库里**第一个 `.timer`**（不推 ⇒ 服务器装不了定时任务）；同一次查出
   `deploy/systemd/acps.logrotate` 也一直不在清单里，而 `systemd-install.sh` 要
   `install "$UNIT_SRC/acps.logrotate"` —— 那句在服务器上**从来找不到源文件**。
3. 🔴 **第 4 处同类漏项**：`docs/` 顶层的材料不在清单里，而
   `acps-case-round.service` 的注释**点名**了 `docs/上线操作手册.md`（一直是靠手工另外推的）。

⇒ 两处都改成**按目录收**，判据改成**现场派生**（磁盘上有什么，清单里就必须有什么），
清单 170 → **181**；并给清单元验证补了第 3、4 条退回用例（4/4 有效）。

**同日另一件事**：把那条每 2 小时的自动化**收窄成"只复查 discovery 索引"**，
把"跑完整一轮"那半去掉 —— 定时任务的职责**只能有一件**，否则双排期 + 抢会话。
