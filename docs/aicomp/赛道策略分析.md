## 一、结论先行：这个问题问歪了

你问"创意优先还是技术优先"。评分表给出的答案是：**这不是一道二选一的题，因为两者的性质完全不同。**

| | 性质 | 后果 |
|---|---|---|
| **技术**（此处官方定义＝**标准化接入深度**，不是算法花哨度） | **入场券** | 不达标直接出局，其余分数全部作废 |
| **创意**（协同交互方案的自主创新） | **分水岭** | 决定创新性拿 8 分还是 25 分 |

两句话就能锁死：

1. 规则原文——「**未完成平台验证的作品视为未通过比赛必要验证场景**」→ 技术不落地＝一票否决。
2. 评分细则创新性最低档——「**仅简单复用开源示例代码，无自主创新改造，方案同质化严重，得 0-8 分**」→ 纯复现＝最高单项只能拿 8/25。

**正确提法：标准先达标（保命），创新定名次（拿奖）。**

## 四、官方开源代码长什么样（这决定"复用"与"创新"的分界）

配套代码来自 **开放原子开源社区 AIP-PUB**（北京邮电大学牵头 + 中国电子技术标准化研究院，依据 **GB/Z 185《人工智能 智能体互联》** 国家标准，2026-05-22 正式发布）：

```
ACPs-community/
├── acps-specs/        ACPs 协议体系定义（AIP/AAC/ATR/ADP/AMP/ACS…）
├── acps-sdk/          SDK（我们项目已在用）
├── acps-cli/          统一命令行工具集
├── acps-docs/         GettingStarted + Tutorials（含智能体接入指南）
├── acps-infra/        基础设施与交付编排（Ansible 部署）
├── ca-server/         智能体 CA 认证服务
├── registry-server/   智能体注册服务（= wt 平台）
├── discovery-server/  ADP 发现服务实现
├── mq-auth-server/    群组模式 MQ 鉴权与 ACL 服务
├── monitor-server/    AMP 监控服务（心跳/指标/**访问记录**/审计日志）
├── demo-leader/       官方示例：主智能体
└── demo-partner/      官方示例：5 个专职 Partner
```

**⚠️ 最需要警惕的一件事**：官方 demo 的场景是 **"北京旅行行程安排"（1 leader + 5 partner）**。

所以——**如果把"北京旅行"换成"法律咨询"，其余照搬，那正好落在评分表那句"方案同质化严重，得 0-8 分"**。场景换了不算创新，**协同交互机制的设计才是创新性 25 分的考察对象**。

## 六、创意方向：把"换个场景"升级成"机制创新"

### 诊断：你的项目缺的不是场景，是**一项自主设计的协作机制**

### 推荐主线 🎯 **可审计的法律智能体协作链**

**创新点＝把"协作过程"本身变成可追溯、可审计的证据链。**

为什么这个方向好：

- 法律场景的**天然痛点**就是"AI 意见不可信、不可追责"——而 AIP/AAC 恰好提供了身份绑定（AIC + mTLS）、委托链、权限收窄、冒充禁止所必需的原材料；
- 同时命中**鼓励方向③交互安全管控** + **鼓励方向④垂直行业场景创新**，是双方向交叉；
- 对评委而言是**"行业突破性"**叙事：法律 AI 的可信协作是真实的产业空白，不是硬凑；
- 技术上落在我们已验证的范围内，风险可控。

**具体可实现的"自主创新模块"（这些都不是官方 demo 做的事）**：

1. **委托链证据留存**——每次跨 Agent 委托记录 `发起方 AIC / 接收方 AIC / 链深度 / 委托内容摘要 / 时间戳`，最终输出的法律意见附带"结论溯源表"（这条结论由哪几个 Agent、依据哪些条文、经过几跳得出）。
2. **权限收窄 enforcement**——利用 AAC §10.5「下级权限不得大于上级」，把法律场景的"咨询级 / 建议级 / 定稿级"做成真实生效的权限层。
3. **链深度熔断**——AAC 要求判 chain depth，但 wit 走 mTLS 并未强制限制；**自己实现深度上限与循环检测**，这是"补上协议空缺"的亮点，也是防 API 额度被烧光的护栏。
4. **冒充检测落地点**——AIP v2.2.0 新增"消息里声称的发送方必须与 TLS 证书身份一致"，把它做成一个显式校验并在演示中展示拦截效果。

### 技术亮点 ⚡ **动态多跳委托（呼应你上一轮的"角色交换"想法）**

你上轮的想法不用丢掉，换个准确的说法即可：

> ❌ "Partner 暂时成为 Leader，用完后归还权限"
> ✅ "**高负载 Partner 可自主发起子交互，动态编排下游智能体**"

后者正是 **AAC §10.1 列为"推荐默认模式"** 的多跳委托（Profile D），也正是赛题鼓励方向 **②多智能体协同调度**。而实现它，在你的代码里**只是给那个 Partner 挂上 `AipDelegationHooks`** ——它现在是 Partner，只是因为我们没给它这个工具。

配套加分动作：用 **AMP 监控（monitor-server）** 做伙伴在线状态感知，让"发现→调度"形成闭环，同时产出评分表点名要的**量化指标**（接入响应速度、通信时延、并发协同数量、累计访问次数）。

### 备选（不推荐 21 天内碰）⚠️
- **异构协议适配网关**（ACPs ↔ MCP/A2A）——命中鼓励方向①，但需要另一套协议的真实实现，3 周内风险过高，**建议写进"未来工作"**。
- **群组交互模式**——基础设施 `mq-auth-server` 虽在开源社区里有实现，但官方 `AcpsConfig.ioa_pub()` 的 `mq_url` 实测为 `None`，且平台侧无对应接口，**不建议在比赛窗口内自建**。
