### 1.4 演示级单项风险：Leader 终止不确定性（**已于 9/29 修掉**）

**这是唯一会让演示当场翻车的问题**，所以单独列出来。

同一输入跑两次，Leader 的终止行为不一样（工具轨迹几乎相同）：

| 形态 | status | `output/` 新 verdict |
|---|---|---|
| (a) 两位专家都返回了，模型直接自然语言收尾 | `completed` | **无** ❌ |
| (b) 模型反复调工具烧完 8 轮预算 | `budget_exhausted` | **无** ❌ |

**根因**：要不要调 `legal_issue_verdict`，完全由模型自己决定。

**修法**（`legal_acps/termination.py`，5 层，都不依赖模型自觉）：

1. 两位专家交回结论后，把本步 `request.tools` **收敛到只剩 `legal_issue_verdict`** ——
   模型没有 `acps_delegate`/`acps_task` 可调，**不可能**再委派或轮询，只能交出结论
2. 同一时机往 system 提示插"强制指令"，让被强制的调用有内容可填
3. 剩余步数 ≤ 1 时同样强制（专家没回也兜底，并明令如实标注"信息不完整"）
4. 结论提交后**清空 `request.tools`** → 模型只能输出文本 → `completed` + 非空 final_text
5. 整轮仍无结论 → 在 `wrap_run` 里用专家载荷**程序化补齐**一份并标注"程序兜底生成"

> 🔴 **实测教训（2026-09-29）：第 1 层不能用 `tool_choice`。**
> wit 确实把 `ModelRequest.settings` 里的 `tool_choice` 原样透传给 SDK，但**透传成功 ≠ 对方接受**：
> 生产模型 `deepseek-v4-pro` 是推理模型，thinking 模式直接 `HTTP 400`
> `"Thinking mode does not support this tool_choice"`，**整轮 run 崩掉**（比原 bug 更糟）。
> 改用"收敛工具列表"后效果等价，且纯本地、不经网关、零兼容风险。
> 需要时可用 `force_tool_choice=True` 叠加，Hook 遇 provider 拒绝会自动降级。
>
> 同时：**Hook 不进 ACS**（ACS 只由 name/description/version/skills/provider/endPoints 决定），
> 所以给已过审的 Leader 加护栏，**不会**改变注册指纹、**不需要**重新过审。

**可复现验证**（离线、无 key）：`./.venv/bin/python -m tools.verify_termination`
—— 用假模型 + 假委派工具在真实 wit run 循环里复现
lazy / loopy / starved / halfdead / refuse 五种失范（共 11 个用例），
证明"不挂 Hook → 无 verdict；挂 Hook → 必出 verdict；正常流程不受影响"。
`legal_acps/check_local` 的护栏自检里也加了**行为级**探针（见下）。

**真模型端到端已复验**（服务器，`deepseek-v4-pro`）：
初版用 `tool_choice` → HTTP 400 崩；改为收敛工具列表后 → `completed`、**迭代 5 轮**（原 8 轮）、
`legal.issue_verdict` success、写出 verdict JSON（模型亲笔，非兜底）。
后续 3 次真机复验也都是 `completed` + 模型亲笔结论（`consistency_note` 里无"兜底"字样）。

#### 1.4.1 事后审计又修掉 4 个缺陷（9/29 晚）

5 层跑通之后做了一次逐行审计，又找出 4 个**离线验证与自检都没覆盖**的缺陷。
共同点：**"参数接对了"≠"参数被用上了"**。

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `survey()` 把交付物工具名写死成 `legal_issue_verdict`，`conclusion_tool` 没传进判定 | 辩论正方交了辩论记录也判不出"已交付" → 第 4 层收尾/retry/跳过兜底全失效，开完辩论后空转到预算耗尽 | `survey(messages, *, verdict_tool=...)` |
| 2 | 委托链熔断在 `await handler()` **之前**记链 | 一次网络抖动后**重试同一目标被误判成"委托环"**、该目标本轮永久封禁 → **辩论发不起来** | 只在派发成功后记链；链尾重复按"重试"放行 |
| 3 | `verdict_errors >= max` 的"放弃"排在 `partners-ready` **之前** | 模型连错两次表单后，**专家都回齐了也不再强制** → 只剩第 5 层兜底 | `partners-ready` 提前；"放弃"与 `retry` 都要求 `pending_tasks == 0` |
| 4 | 就绪判定只数"成功返回"，不算**明确失败** | 一位专家 `failed`（真机日志 `verdict-20260929T085340Z.json` 就是这个场景）→ 第 1 层永不触发，干等到预算见底 | 新增 `LeaderProgress.dead_tasks / .resolved`，改用 `resolved` 判定 |

顺带：第 5 层兜底按 `conclusion_tool` 显式限定为 **Leader 专属**
（否则辩论正方会往 `output/` 塞"像结论的东西"，污染唯一的演示判据 ——
而判据恰恰就是"`output/` 里有没有 `verdict-*.json`"）；兜底产物改为先过
`FinalVerdict.model_validate()`，保证与模型亲笔文件的字段完全一致（原先漏 `disclaimer`）。

**纪律（写给下一次）**：护栏逻辑的自检必须写成**行为断言**
（喂一段消息历史 → 断言 `_decide()` 的 `reason`），不能只断言"Hook 挂没挂、参数对不对" ——
这轮 4 个缺陷里有 2 个正是因此逃过全绿自检。新探针都验证过"退回旧代码即报失败"。
→ 教训：**离线假模型测不出 provider 拒绝 `tool_choice`**，改完必须真模型跑一次。

这条不只解决演示风险，本身就是**「结构化终止」**这一机制项的落地证据
（阶段 1 的清单里原本就有它）。

## 2. 对 14 Agent 计划的判断：方向对，剂量错

### 2.1 先算时间账

今天 9/29 → 截止 10/15 20:00 = **16 天**。  
你自己说「学习时间会很长」→ 保守假设学习占 5 天，**有效交付只剩 11 天**。

14 个 Agent 意味着：

| 成本项  | 具体                                               |
| ---- | ------------------------------------------------ |
| 注册审核 | **11 次**新增注册 + 平台审核，**wall-clock 不可控、你无法催**      |
| 端口依赖 | 8 个端口（8448–8455）需开防火墙，漏一个 → 该 Agent「注册了但连不上」     |
| 内存   | 14 × ~95 MiB ≈ **1.33 GiB**（机器可用 3.0 GiB，能跑但无余量） |
| 演示   | 3–5 分钟讲完 14 个 Agent → 讲不透，等于没讲                   |
| 失败面  | **×14**。录像时任何一个挂了，素材就废                           |

**结论：14 个，你的时间装不下。这不是保守，是算术。**

### 2.2 真正的问题：创新性这 25 分**不从数量来**

评分细则满分档原文：

> 基于智能体互联开源代码**深度二次开发**，**创新设计多智能体协同交互方案**，适配 AIP 国标，  
> **具备行业突破性**，得 18-25 分。

**考察对象是「协同交互方案」，不是「智能体个数」。**

官方 demo 是 1 Leader + 5 Partner（北京旅行场景）。你做成 14 个浅层 fan-out，在评委眼里仍然是「把 demo 换了个场景铺大」→ 落最低档 0-8。

**反过来成立**：3–5 个 Agent，但把**协作机制**设计到官方 demo 都没到的深度 —— 这才是满分档的样子。
