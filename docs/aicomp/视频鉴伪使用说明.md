# 视频鉴伪 —— 怎么用

面向**使用者**：想把一段视频送进来做一次编辑痕迹初检的人或 Agent。
每一条结论都标了来源，与 `音频鉴伪使用说明.md` / `调用说明.md` 保持同一套口径：

- **实测** —— 本机跑出来的行为，不是推断
- **规范** —— MCP / ACPs / AIP 规格原文
- **设计** —— 刻意的取舍，附带理由

---

## 0 一句话

**给一段视频的字节，拿回七项技术线索 + 一个综合线索等级 + 一条复检阶梯。**
**拿不到「真 / 假」** —— 这是设计，不是缺陷（见 §7）。

视频进来**只有两种方式**：随任务附件产生的 `inbox:<sha256>` 句柄，或 `data:video/…;base64,…`。
**本能力不出网、也不读本机文件**（见 §3）。

⚠️ **先记住这一条，它决定了怎么读本报告**：服务器上**没有视频解码器**
（没有 ffmpeg / OpenCV / PyAV），所以 H.264 / H.265 的帧**一帧都解不出来** ⇒
「**帧层整项没有执行**」在本链上是**常态**，不是例外。而帧层恰恰是唯一能直接
看到画面改动的那一层。详见 §6。

## 1 你能拿到什么

同一套检测核心，**两个入口**，结论逐字相同（这一点由 `tools/verify_video_mcp.py`
第 3 节直接断言：同一条 uri 两边跑，比对 JSON）：

| 入口 | 谁用 | 需要什么 | 工具 / 能力名 |
|---|---|---|---|
| **MCP server** | 本机的人工使用者 / 通用 AI 客户端（Claude Desktop、WorkBuddy 等） | 一个能跑 Python 的终端 | `video_probe` / `video_forensics_analyze` / `video_sample_table` |
| **ACPs 能力** | 已注册的 ACPs Agent（走 mTLS） | 自己的 AIC + 客户端证书 | `evidence.analyze_video`（角色 `evidence-video`，端口 8452） |

三个工具的分工：

| 工具 | 干什么 | 给结论吗 |
|---|---|---|
| `video_probe` | 第一眼：这段字节是什么容器、声明了哪些轨道、解析到哪一层、**容器里零解码能取到几帧** | ❌ 不给 |
| `video_forensics_analyze` | 七项检查 + 综合线索等级 + 复检阶梯 | ✅ 给等级 |
| `video_sample_table` | 把**逐轨声明的**时间线 / 样本表 / 编辑列表数字摊开，供人工核查 | ❌ 不改判定 |

> 为什么要有 `video_probe`：跑完整检测之前先确认「这份东西我们能不能看、能看到哪一层」。
> 一份 H.264 的 MP4 在**没有解码器**的机器上只能给出容器层结论，`video_probe` 会第一句话就说清楚。
>
> 为什么要有 `video_sample_table`：权重最高的两项检查（`samples` / `timeline`）判的是
> 「容器里的声明**之间**自不自洽」，而人工复核时唯一能拿到的就是那几个数字 ——
> 不摊开，读者只能选择信或不信。⚠️ 它**不解码任何帧**，所以它给出的东西
> **不能用来说明画面里有没有改动**。

⚠️ **帧层没有单独的工具**，这不是漏了：`frames_available` / `frames_note` /
`frames_analyzed` / `frame_source` 以及 `frames` 那一项 finding 都已经在
`video_forensics_analyze` 的报告里。再开一个只会给出第二份措辞。

## 2 怎么接

### 2.1 本机 MCP 客户端（推荐先试这条）

**不需要注册、不需要证书、不需要联网。** server 是本机子进程，用 stdio 通信。

⚠️ **音频与视频是两个 MCP server，配置里要写两项。** 它们共用同一份协议实现
（`legal_acps/mcp/server.py`），但服务标识与开场白各自独立 —— 理由见
`legal_acps/mcp/video_server.py` 开头那段（合并会让音频侧那批已经过审的断言必须改动，
而"改判据让它通过"是本项目最忌讳的那类修法）。

在客户端的 MCP 配置里加（WorkBuddy 是 `~/.workbuddy/mcp.json`；
Claude Desktop 是 `claude_desktop_config.json`；键名都是 `mcpServers`）：

```json
{
  "mcpServers": {
    "legal-acps-audio-forensics": {
      "command": "C:/Users/Zhao5/Desktop/Mycode/witrelate/.venv/Scripts/python.exe",
      "args": ["-m", "legal_acps.mcp.server"],
      "cwd": "C:/Users/Zhao5/Desktop/Mycode/witrelate"
    },
    "legal-acps-video-forensics": {
      "command": "C:/Users/Zhao5/Desktop/Mycode/witrelate/.venv/Scripts/python.exe",
      "args": ["-m", "legal_acps.mcp.video_server"],
      "cwd": "C:/Users/Zhao5/Desktop/Mycode/witrelate"
    }
  }
}
```

三个**必须**照做的地方（每一条都真的踩过）：

1. **`command` 要用绝对路径指向项目的 `.venv`**，不要写裸 `python`。
   用系统 Python 会在 `import pydantic` 那一步就崩（服务器与本机都实测过）。
2. **`cwd` 必须是项目根目录**。`legal_acps` 是相对包名，在别的目录下 `-m` 找不到它。
3. **必须模块方式启动**（`-m legal_acps.mcp.video_server`）。
   写成 `python legal_acps/mcp/video_server.py` 会 `ModuleNotFoundError` ——
   这与本项目"一律模块方式跑"是同一条规矩。

改完配置要**重启客户端**；MCP 连接只在启动时建立。

> ✅ **接线现状与自检**（2026-10-05）：本机已按上面这段接好
> （`~/.workbuddy/mcp.json`，两条都在）。改完配置后跑：
>
> ```bash
> ./.venv/Scripts/python.exe run/verify_mcp_config.py
> ```
>
> 它会 **① 现场从本文件抽上面那段 JSON**，与 `~/.workbuddy/mcp.json` **逐字比对**
> （文档是「同一判定写两处」的第三处，没有锚点盯着它）；**② 真起一次 stdio 握手**
> （`initialize` + `tools/list`），并断言 server **自报的名字**是它自己那一个
> （防两个入口串了）；**③ 负对照**：把 `command` 换成裸 `python` 必须判失败。
> 判据是**退出码**（0 通过 / 1 判据失败 / 3 配置不存在）。
> ⚠️ 只校验"配置写对了"是不够的 —— 少了 `cwd`、模块名写错这些**都不会当场报错**，
> 一直到某次真调用失败为止，所以第 ② 条不可省。
>
> **这条判据已进 `check_local` §3e**（2026-10-05）⇒ 不必再靠"有人记得单独跑它"。
> ⚠️ 客户端配置是**每台机器一份**的（不进仓库、不进同步清单），所以**别的机器上它会
> 「响亮跳过」并单独计数**：跳过 ≠ 通过 —— 看板写的是「1 项跳过未判」，不是算进通过。

> ⚠️ 有些客户端会把 MCP 配置缓存到自己的目录里。改完没生效时，先确认它读的是你改的那个文件。

### 2.2 ACPs 通道（已注册 Agent 之间）

走这条路的是**上游 Agent**，不是人：调用方必须是**已注册的 ACPs Agent**，
因为直连模式在 `identity_binding_enabled=true` 时会从 mTLS 对端证书里取 AIC，
并校验 `senderId == peer AIC`（规范 §6.0）。

- 能力 id：`evidence.analyze_video`（角色 `evidence-video`，端口 8452）
- 入参就是 `VideoEvidenceRequest` 的三个字段：`video_uri` / `declared_mime` / `context_note`
- 正常调用链是**经过「法律咨询主控」**：你在任务文本里说清"要检查随附的视频有没有剪辑痕迹"，
  主控把它派给证据鉴证 Leader，Leader 再派给视频鉴伪专家。
  **不要跨层直接指挥内部专家**（AIP §3.2：Partner 之间不直接交互）。

⚠️ 视频附件现在是**真的会被转给下游**的：`evidence-video` 挂的是
`EvidenceInboxHooks(kinds=("video",), delegate_tool="")`，且「法律咨询主控」与
「证据鉴证 Leader」都收 `image`/`audio`/`video` 三种模态、并各挂了 `VideoFallbackHooks`
（降级 Hook）。这由 `tools/verify_video.py` 第 11 节逐条断言
（"装了 ≠ 会响" —— 收得进视频却没人负责降级的角色会被这条判据点名）。

## 3 怎么把视频交进来 —— **只有两种引用**

```
inbox:<sha256>                          ← 随任务附件进来的字节（**首选**）
data:video/mp4;base64,<载荷>             ← 自带字节（动画 GIF 写 data:image/gif;base64,… 也接受）
```

**没有第三种。** 下面这些**一律被拒绝**（并且会告诉你该怎么改 ——
每条拒绝都带一个机器可读的分类码，见 §3.3）：

| 你给的 | 结果 | 为什么 |
|---|---|---|
| `https://example.com/a.mp4` | ❌ 拒绝 | 视频侧**没有任何出网通道**（见下） |
| `file:///C:/x.mp4` / `C:\x.mp4` | ❌ 拒绝 | 不读本机文件 |
| `ftp://…` / `//server/share/x.mp4` | ❌ 拒绝 | 同上 |
| `inbox:../secret` | ❌ 拒绝 | 句柄是**内容哈希**，不是路径 |
| `data:video/mp4,raw` | ❌ 拒绝 | `data:` URI 必须是 base64 编码 |
| `data:text/plain;base64,…` | ❌ 拒绝 | 声明的类型不是视频（也不是动画 GIF） |
| 一段 PDF / 网页 / 文字的字节 | ❌ 拒绝 | 按**魔术字节**判出来不是视频容器 |

### 为什么视频侧**刻意不做出网通道**（比音频侧更彻底）

图像侧有一条受白名单约束的取图通道（`EVIDENCE_IMAGE_ALLOWED_HOSTS`），因为模型工具层的
schema 只允许传 URL，**看图**的前提就是把图弄进来。

视频侧**不但没有这个不得已，而且比音频侧更没有**：

- 视频证据的正规来路本来就只能是"任务附件"—— 文件动辄几十上百 MB，
  内联 base64 会让请求体膨胀约 1/3，工具调用的参数字符串根本承载不了；
- 而**每开一条出网通道就多一个 SSRF 面**：任何能给我发任务的对象，
  都能驱使本进程去访问任意内网地址。

> **能力做小，比做全更符合这条链的实际。** 调用方要做的是把字节交给我们，
> 而不是把地址交给我们。

### 3.1 体积上限与它的**关系**

| 限制 | 值 | 说明 |
|---|---|---|
| 视频字节上限 | **64 MiB** | 超限**拒绝，不做截断** —— 截断会让「容器声明的长度」与「实际字节数」对不上，而"截断 / 尾部多余数据"**正是本能力的两条判据** |
| 收件箱落点上限 | 64 MiB | 与上面**必须**满足 `落点上限 ≥ 视频上限`（由 `check_local` 现场派生断言） |
| 帧层抽样 | 最多 **4 帧**，单帧 ≤ 4 MiB | 首 / 中 / 末抽样，**不是逐帧检查全片** |
| 模态降级抽帧 | 64 MiB | 超过就不抽帧，只降级成文字说明（见 `video_modality.py`） |

⚠️ **`too_large` 这个分类码在现行配置下够不到**：因为视频上限与落点上限**相等**，
超限的附件在落点那一层就被拒了。它保留下来是**纵深防御**（谁把落点抬上去，它立刻生效），
而 `tools/verify_video.py` 会把上限**临时改小**、把这条路真的走一遍 ——
判据是"这条路真的会响"，不是"代码里有这么一段"。

⚠️ 再大的**不要为了塞进来而重编码**：重编码会重写容器与样本表，
正好抹掉本能力要看的那批证据。出路见下。

### 3.2 体积超限了怎么办（不要压缩）

1. 用本地工具（MediaInfo / `MP4Box -info` / `ffprobe -show_packets`）把容器与
   逐样本时间戳字段导出来自查（复检阶梯第 1 档，**免费**）；
2. 行车记录仪 / 手机通常**按固定时长分段保存** —— 提交**需要核查的那一段原始文件**
   （不是压缩后的拼合件）；
3. 涉及法律责任时直接走声像资料司法鉴定（复检阶梯第 3 档）。

### 3.3 拒绝的分类码（9 个，每个都有专属出路）

取件层**不给"不支持"三个字就完事**：它抛的每个拒绝都带一个分类码，
由 `pipeline.fix_for()` 配一条**可执行**的出路。这就是为什么
「坏 base64」不会被答成「容器结构有问题」—— 两族的建议表**互不设防**，
只要有一个关键词撞上就会静默错配。

| 分类码 | 什么时候出现 |
|---|---|
| `unsupported_scheme` | 不是 `inbox:` / `data:`（含 https / http / file / 裸路径） |
| `data_uri_malformed` | `data:` URI 里没有逗号分隔的载荷段 |
| `data_uri_not_base64` | 声明了 base64 之外的编码 |
| `data_uri_mime` | 声明的类型不是 `video/*`，也不是 `image/gif` |
| `data_uri_too_large` | 解码**之前**按上界判超限 |
| `data_uri_bad_base64` | 载荷本身解不开 |
| `data_uri_empty` | 解码后为空 |
| `inbox_invalid` | 句柄不合法 / 没登记 / 字节不可读 |
| `too_large` | 拿到字节后才发现超限（现行配置下够不到，见 §3.1） |

## 4 三个工具的入参出参

### 4.1 `video_probe`

| 参数 | 必填 | 说明 |
|---|---|---|
| `video_uri` | ✅ | 见 §3 |
| `declared_mime` | — | 调用方声明的类型。⚠️ **本工具只原样回显，不参与任何判定** —— 「声明与真实容器是否一致」由 **`video_forensics_analyze` 的 `container` 一项**报出（在那里比对一次就够了；探针再比一次就是"同一判定写两处"） |

返回：`media_type` / `byte_size` / `sha256` / `fetched_from` /
`container{名称,品牌,声明长度,是否截断,尾部多余字节,时长,顶层盒,moov位置,mdat段数,解析深度}` /
`tracks[{handler,codec,timescale,时长,样本数,宽,高}]` / **`container_frames`** /
`frame_source` / `container_frames_note`。

> ⚠️ 那个数字**叫 `container_frames`，不叫 `frames_available`** —— 这不是命名偏好。
> 它数的是"**容器里零解码能取到几帧**"，而**动画 GIF 的帧要经逐帧光栅化**，
> 那一步在分析里做。若叫 `frames_available`，一份动画 GIF 会被读成
> "帧层跑不了"，而它其实跑得了。这条口径由判据钉住。

### 4.2 `video_forensics_analyze`

| 参数 | 必填 | 说明 |
|---|---|---|
| `video_uri` | ✅ | 见 §3 |
| `declared_mime` | — | 与真实容器不符时会作为一条线索报出 |
| `context_note` | — | 这段视频在案情里的分量（如「据称是行车记录仪导出」）。**仅原样回显，不参与任何判定** |

返回：`### 综合线索等级：…` + 一句话摘要 + 溯源字段 + **七项逐项发现**
（每项都带 依据 与 **它不能证明什么**）+ 证据保全提示 + 复检阶梯 + 免责声明，
末尾附一份**可机读 JSON**（同一份内容，供脚本取结构化字段）。

### 4.3 `video_sample_table`

| 参数 | 必填 | 说明 |
|---|---|---|
| `video_uri` | ✅ | 见 §3 |

返回：容器层（`parse_depth` / `declared_size` / `actual_size` / `truncated` /
`appended_bytes` / 顶层盒 / `moov_before_mdat` / `mdat_count` / 元数据与自报工具）
+ **逐轨**：`timescale` / `mdhd` 与 `tkhd` 两个声明时长 / `sample_count` /
`delta_kinds`（`stts` 间隔种类）/ `delta_min`,`delta_max` / 样本尺寸 / chunk 数与偏移范围 /
编码与展示尺寸 / **`edit_list`**（跳段 / 变速）。

> ⚠️ 以上**全部是容器里的声明值**：改写它们的成本是零。
> 本工具**只摊开数字、不下结论** —— 「声明之间对不上」才是线索，
> 而判断那件事的是 `video_forensics_analyze`。

## 5 七项线索：能发现什么 / 什么时候不适用

每一项都对应一种**公开发表**的视频 / 容器取证手段（本项目自行实现，未调用其代码）。
权重是专家先验，**不是拟合出来的**。

### 容器层（**不需要解码器**，H.264 / H.265 也跑得了）

| 检查项 | 权重 | 能发现什么 | 它**不能**证明什么 |
|---|---|---|---|
| `container` | 0.5 | 容器声明长度与实际字节数是否自洽、尾部是否多出数据、**声明的类型与真实容器是否一致** | 只说明"文件是怎么被写出来的" |
| `structure` | 0.5 | 盒树是否成立、`moov` / `mdat` 布局、分段写入痕迹 | `moov` 在后**不是缺陷**，只说明被重写过一遍 |
| `metadata` | 0.5 | 时间戳与**自报**编码工具里有没有剪辑 / 转码软件署名（ffmpeg、剪映、Premiere……） | 由 `©` 系元数据引发的"尾部多余数据"是**假阳性**（iPhone 视频几乎必然含它们）；署名也能零成本改写 |

### 时间线 / 样本表层（**权重最高的三项**，最值得人工复核）

| 检查项 | 权重 | 能发现什么 | 它**不能**证明什么 |
|---|---|---|---|
| `samples` | **1.5** | 样本表自相矛盾、chunk 偏移越界 —— **正常写入器不可能产出** | 只说明"表被动过"，不直接说明画面变了 |
| `timeline` | 1.0 | **三处时长**（`mvhd` / `tkhd` / `mdhd`）对不上；帧率跳变（差 5 倍以上才报，因为 VFR 是常态） | 不同时间刻度的整除舍入会造成小差（1 秒 / 1% 以内一律不报） |
| `edits` | 0.5 | `elst` 编辑列表里的**跳段 / 变速** | `elst` 是标准做法，很多正常导出也带它 |

### 帧层（**唯一能直接看到画面的一层**，也最常整项没跑）

| 检查项 | 权重 | 能发现什么 | 它**不能**证明什么 |
|---|---|---|---|
| `frames` | 1.0 | 从 MJPEG 逐帧样本 / 内嵌封面帧 / 动画 GIF 里**零解码**取到的帧，接进**已有的图像鉴伪链**逐项跑；还能发现**字节完全相同的重复帧**（同一帧被写两遍） | ⚠️ 只覆盖**抽样的最多 4 帧**，**不是全片**。被剪掉的那几秒大概率不在这几帧上 |

## 6 **弃权的两层** —— 这是本链最关键的一节

视频链的弃权比例**天然极高**（H.264 / H.265 一律解不出帧；TS / FLV / WMV 这类容器
没写解析器）。所以"某一项没跑"是常态。
**如果它能把整份报告压成「无法判定」，那么每一份正常视频都是「无法判定」**，
报告彻底失去信息量 —— 但那也**不等于**可以把它写成"没问题"。
因此弃权被分成两层，**互斥且并集覆盖全部弃权项**：

### 第 1 层：**材料级闸门**（`这段视频不满足帧层检查的前提`）

取不到**任何**可分析的帧（H.264 / H.265、缺解码器、GIF 光栅化失败……）
⇒ **帧层整层没跑** ⇒ 综合等级只能是「无法判定」。

此时摘要**绝不会**出现"均未提示异常"这种话，而会写：

> 「综合线索等级：无法判定。本次**取不到任何可分析的帧**，N 项（抽样帧）**整项没有执行**；
> 其余项目只覆盖容器结构、时间线自洽与元数据，**不能据此认为「没有问题」**。」

### 第 2 层：**逐项不适用**（`本项对这一段视频无从执行`）

某一项因为"这段视频上无从检验"而没跑，例如：

- TS / FLV / WMV 这类容器 ⇒ 谈不了盒结构、时间线、样本表
- 取到帧、但每一帧都被图像链判成「无法判定」（画面以纯色 / 平滑区域为主）⇒ 帧层这一项没给出结论

**其余各项照常跑通，综合等级照常给出**（不改变等级），但摘要会点名缺席的项，
并写一句「**这不等于它们也合格**」。

> **一句话记住区别**：闸门是"整份报告测不了"，逐项是"这一项对这段视频不适用"。
> 把后者写成前者，等于把一份有用的报告变成一句废话。

### 边界情形：闸门与正向触发**同时**出现

比如"`moov` 在 `mdat` 之后" —— `structure` 触发（0.5 ⇒ 低），而帧层整层没跑。
**触发优先**：等级照常给出，但摘要必须**点名缺席的项**，
让读者知道"这个等级是在七项里只有六项参与的情况下算的"。

> 等级不是错的，错的是读者对它的信任。

## 7 怎么读结论

综合线索等级只有四档：**低 / 中 / 高 / 无法判定**。等级由程序按固定权重表算出，
**不是模型给的**（数字与结论不能经手被评价的那一方）。

| 等级 | 读法 |
|---|---|
| **低** | 本次可执行的检查项都没看到异常。**这不代表未经剪辑**，只代表本地这些手段没看到 |
| **中** | 有一项以上提示异常，值得进一步核查 |
| **高** | 多项强线索叠加。**仍不是篡改认定** |
| **无法判定** | 前提不满足或全部弃权。**这是合法且经常正确的答案**，在本链上尤其常见 |

⚠️ 四条必须一起转述的话：

1. 报告里**没有「真 / 假」**。所列「提示异常」**不等于**该视频被篡改 ——
   转码、剪辑软件导出、平台二次压缩、手机边写边录都会产生同类痕迹。
2. 所列「未提示异常」**不等于**该视频未经剪辑。
3. **「无法判定」不要转述成「没问题」**。这两句话在字面上离得很近，在结论上离得最远。
4. ⚠️ **「容器层没发现问题」不等于「这段视频没问题」** ——
   本机解不出 H.264 / H.265 的帧，而帧层才是唯一能直接看到画面改动的那一层。
   报告里的 `frames_note` 会写清这件事，**转述时必须带上它**。

本报告是**技术线索**，不是司法鉴定意见，不能单独作为认定事实的依据。
**涉及法律责任时唯一有证明力的路径**是委托声像资料司法鉴定（复检阶梯的第三档）。

### 复检阶梯（三档，**不随等级裁剪**）

| 档 | 工具 | 成本 | 交付周期 |
|---|---|---|---|
| 1 | **MediaInfo / GPAC（MP4Box）/ ffprobe**（均为免费工具） | 免费 | 取决于人工，通常几十分钟 |
| 2 | Amped Authenticate / VideoForensics 等商用取证软件 | 商业授权，万元级起 | 小时级 |
| 3 | **声像资料司法鉴定**（视频真实性 / 完整性鉴定） | 通常 3000–8000 元/件（以受理机构公示为准） | 一般 30 个工作日左右 |

第一档是**先做这一步**：用 MediaInfo 看一遍容器与轨道的**完整字段**（本报告只摘了一部分），
再用 `MP4Box -info` 或 `ffprobe -show_packets` 把**逐样本时间戳**导出来，
人工核对本报告点出的可疑时间段。⚠️ 这些工具**只读表、不解码**，
所以它们能验证「表是否自洽」，但看不到画面。

> 从「低」里删掉司法鉴定，等于对用户隐藏唯一可用的救济路径 ——
> 所以三档**每一档都返回**，判据里有一条专门钉这件事。

## 8 证据保全（本报告会随附这一段，别忽略）

- 立即保全**原始文件**（原始存储卡 / 手机 / 行车记录仪 / 只读镜像），
  **不要**用微信、QQ、短视频平台转发件代替 —— 转发会重新编码并重写容器，
  时间线与样本表全变，之后再鉴定就失去了比对基准。
- 对原文件计算 SHA-256 并记录时间与操作人；本次报告的 `sha256` 字段即为该值。
- 原始文件与任何转发件**分别保全、分别记录来源**：它们不是同一份材料。
- 记下**这段视频是怎么来的**（哪台设备、什么时间、怎么导出）。容器里的创建时间与
  设备信息很容易被改写，而「当事人陈述的来路」不会 —— 两者对不上本身就是最有用的一条线索。
- 任何后续取证都在**只读副本**上进行，原件封装保存。

## 9 排障与常见问题

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 客户端显示"连不上 / 无响应" | 启动就崩了（`command` 用了系统 Python） | 换成项目 `.venv` 里的 python 绝对路径 |

| 报告说"帧层可用：否" | **正常且常见**：H.264 / H.265 + 本机没有解码器 | 看 `frames_note`。容器层结论仍然有效。要帧层结论得换 MJPEG / 动画 GIF / 内嵌封面帧，或走线下鉴定 |
| 所有项都「无法判定」 | 触发了材料级闸门（帧层整层没跑） | 这是**如实报告**，不是故障 —— 它不会写"没问题" |

| 「不是可识别的视频容器」 | 给的不是视频字节（网页 / PDF / 文字），或容器**本服务确实认不出** | 给**视频文件本身**的字节。⚠️ **认得的容器不必转换**：`.mp4` / `.mov` / `.mkv` / `.webm` / `.avi` / `.gif` 会**逐盒解析**；`.ts` / `.flv` / `.mpg` / `.wmv` / `.ogv` / 非 AVI 的 RIFF 是**只识别容器、不解析内部**（照常出报告，但结构 / 时间线 / 样本表那几项会如实写「没有为这种容器写解析器」，等级一律「无法判定」）。真正认不出的（如 `.rmvb` / RealMedia，按魔术字节会判成 `application/octet-stream`）才需要先转 MP4（⚠️ 转换会重写容器，若可能用于举证请提交**原始文件**） |
| 拒绝理由说"不支持的引用" | 给了网络地址或本地路径 | 见 §3 —— 把**字节**交给它，不是把**地址**交给它 |
| 拒绝理由说"载荷过大" | 超过 64 MiB | **不要压缩**，见 §3.2 |

## 11 已知边界（对外说明时别漏）

1. **本机没有 ffmpeg / OpenCV / PyAV** ⇒ H.264 / H.265 **一律解不出帧**，
   报告只能覆盖容器结构、时间线自洽与元数据。这**不是缺陷**，是必须如实说出的边界。
   （所以 `decode.py` 是**纯标准库**：没装 numpy 也能出容器层结论。）
2. **帧层只覆盖抽样的最多 4 帧**，不是全片 —— 被剪掉的那几秒大概率不在这几帧上。
3. **视频侧不出网、不读本机文件**（刻意收缩，见 §3）。
4. **64 MiB 上限，超限拒绝、不做截断**（因为"截断 / 尾部多余数据"正是两条判据）。
5. **不做「AI 换脸 / AI 生成」检测**：那需要深度模型与 GPU，与"离线可断言"的纪律冲突。
6. **不输出「真 / 假」**（见 §7）。
7. **有六个容器「认得、但没写解析器」**：MPEG-2 传输流（`.ts`）、Flash Video（`.flv`）、
   MPEG 节目流（`.mpg`）、Windows Media（`.wmv` / `.asf`）、Ogg（`.ogv` / `.oga`）、
   不是 AVI 的 RIFF。它们**一律被接纳**、照常出报告，但报告里
   结构 / 时间线 / 样本表那几项会写明「**没有为这种容器写解析器**，本次没有检查」，
   综合等级一律「**无法判定**」—— **不要**把那份报告读成「看过了、没问题」。
   ⚠️ 「谁算视频」这件事只有一个判据（`forensics.is_supported_video`），它**现场读解码层的容器表**
   ⇒ 以后加容器只改解码层那一处，判据自动跟上（`tools/verify_video.py` 第 3c 节按两张表**现场派生**逐容器断言）。
7. **MCP 通道没有身份校验**：它的信任模型是"能在这台机器上启动这个进程的人，
   本来就能读这些文件"。所以本项目**不提供**监听端口的服务器形态 ——
   一个无身份校验的网络服务会把"本机可信"这个前提直接作废。
8. **音频与视频是两个 MCP server**（配置里写两项）。它们共用同一份协议实现，
   但服务标识独立 —— 见 §2.1。
9. **调用方必须是已注册 Agent**（§2.2）：人不能裸调端口，得通过自己的 Agent 或平台前端。
