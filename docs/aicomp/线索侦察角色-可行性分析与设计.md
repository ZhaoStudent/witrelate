# 线索侦察角色 —— 可行性分析与设计

> **触发**：2026-10-04 用户提出「新增一个智能体，由法律咨询主控直辖，同时与网络裁判形成一层
> 新的 Leader/Partner 关系；它去对接具体软件、搜索高热度且有煽动性与争议性的话题，
> 再自动检索资料判断该话题是否建立在断章取义或假信息之上」。
> 用户同时提出三个具体疑问：怎么拿软件授权 / 做通用接口还是逐软件定制 / 怎么保证确实有效。
>
> **本文回答的是「可行性」，不是实现方案。** 结论里带成本量与判据，凡是没有实测支撑的
> 都标成「未验证」。

---

## 0. 一句话结论

1. **判定那一半不用建** —— 「是不是断章取义」在本项目已经是一个跑着的角色
   （`fact-judge` 8448）加一份枚举值（`fact.FallacyKind.OUT_OF_CONTEXT`）加一套证据链
   （`evidence-leader` 8450 下三个模态）。要新建的只有 **线索发现** 与 **出网检索**。
2. **你原话的接线在当前链路上不成立** —— 主控 → 线索 → 裁判 → 辩手 = **depth 4**，
   而 `MAX_CHAIN_DEPTH = 3`。这不是性能问题，是**第 4 次委派根本不会发生**。
   有两条不动上限的替代接线（§2.2）。
3. **授权问题只存在于「主动抓全站」这一种形态里。** 换成「线索由外部递入」，
   授权问题归零，且两个目标（覆盖面 / 合规）里只牺牲覆盖面。**通用接口与逐软件定制是伪二选一**，
   正确形态是「单一契约 + 薄适配器 + 白名单默认空」，本项目已有同形先例（§3.4）。
4. **「确实有效」这件事现在无法证明，也不该假装能证明** —— 项目现有的唯一判据
   （`output/` 有无 `verdict-*.json`）只证明**链路成立**，不证明**结论正确**。
   对一个自动发现并自动判定的系统，「跑通了」和「判对了」是两件事，后者需要
   **带标注的评测集**。没有它，社会效益就是不可验证的（§4）。

## 1. 先把提案拆开：它是「一个智能体」，还是三件事？

用户描述的是一个智能体，但它内部有三件性质完全不同的事，可以独立成立、独立否决：

| # | 事 | 性质 | 现状 |
|---|---|---|---|
| ① | **线索发现** —— 「今天该看什么」从哪来 | 外部**输入面** | 不存在（用户描述是唯一入口） |
| ② | **资料检索** —— 出去取一手材料与权威结论 | **出网面** | 不存在（全项目唯一没有的东西） |
| ③ | **真伪判定** —— 是不是断章取义 / 假信息 | **判定面** | **已有** |

### 1.1 ① 线索发现

今天系统里「受理什么」这件事**完全由调用方决定**：主控的入口是「受理待研判文本」，
裁判的入口是 `fact.arbitrate_claim`「受理待核查事件」。也就是说，
**系统从来没有「选题」这个动作**，它只响应。

有意思的是，**这个形态在设计文档里早就写过了** —— `docs/项目设计提示词.md` 里对裁判的描述是：

> `fact-judge` 网络裁判 | 受理事件（**用户描述 或 自主检索热点**）→ 独立采证 → 发起辩论 → 裁定

也就是说，**「自主检索热点」是这一版设计里被记下来、但没有实现的那一半**。
你现在提的不是新需求，是补一个原设计已经认领的洞。

但要注意一个后果：原设计把这件事**放在了裁判自己身上**。这有问题，见 §2.3。

### 1.2 ② 资料检索 —— 这才是真正的分歧点

用户的原话是「这个 agent 必须有足够充足的资料来判定相关的证据是否是真的」。
**这句话描述的是检索能力，而这个项目从来没有检索能力**，而且不是漏了，是**刻意不要**：

- `legal_acps/video/fetch.py:7` —— 视频侧「与音频侧逐条相同，与图像侧刻意不对称：
  **一条出网通道都没有**」；`legal_acps/audio/fetch.py:7` 同款措辞。
- 图像侧是唯一的例外，而且理由写得很清楚（`legal_acps/evidence/fetch.py:28`）：
  「出网必须显式配置 `EVIDENCE_IMAGE_ALLOWED_HOSTS` 白名单；**白名单为空 = 禁止一切出网取图**，
  而不是允许一切」。
- 拒绝加通道的理由是 SSRF（`video/fetch.py` 原文）：「**每开一条出网通道就多一个 SSRF 面：
  任何能给我发任务的对象，都能驱使本进程去访问任意内网地址**」。

**所以：一个「主动去搜话题、再去搜资料」的角色，是这个项目历史上出网面最大的一次改动** ——
比加任何一个证据模态都大。它不是在现有形态上挂一个叶子，而是引入一类新的角色。
这一点必须先承认，别当成「再加个 agent」来估工作量。

### 1.3 ③ 真伪判定 —— 已经有了，而且分得比提案更细

用户说「要有足够充足的资料来判定相关的证据是否是真的」。这套东西已经是**结构化契约**了：

| 已有的东西 | 位置 | 作用 |
|---|---|---|
| `FactItem` | `contracts.py:292` | 一条**可被外部验证**的客观信息，明确「严禁写入判断性内容」 |
| `SourceLevel` | `contracts.py:283` | 一手材料 / 二手转述 / 观点评论 / 来源不明，注释写着「**只有一手材料能支撑事实判断**」 |
| `FactSheet.missing` | `contracts.py:309` | 「想要但没有获取到的信息项，**如实列出，不要用推测填补**」 |
| `FactRuling.verdict` | 三态 | 确有其事 / **断章取义** / 无法判定（2026-10-07 起补「不实」四态） |
| `FallacyKind` | `contracts.py:399` | `OUT_OF_CONTEXT = "断章取义"`，另三类：时间错配 / 张冠李戴 / 数字夸张 |

**这份契约已经把用户想做的事拆成了可计算的形态**，而且比提案更克制：
它把「是真是假」降级成「哪一类话术 + 三态裁定 + 事实清单 + 来源等级」，
并且**强制允许「无法判定」**。

⇒ **结论：③ 复用，不要重建。** 重建的代价是判定口径出现第二个事实源，
这正是本项目反复踩的坑（「同一事实写两处必然漂移」）。

## 2. 架构可行性：按你原话接线会撞 `MAX_CHAIN_DEPTH`

### 2.1 算术

`MAX_CHAIN_DEPTH = 3`（`contracts.py:804`，注释：「补 wit 未实现的 AAC 约束」）。
链深**按委派链上的角色数算**，不是按层数，这一点项目里有实测记录
（`docs/上线操作手册.md:1236`）：`Leader 派 harm → 链 = (L, incitement, 裁判, harm) depth 4 ❌`。

现状正好卡在上限：

    法律咨询主控(1) → 网络裁判(2) → 辩手(3)              = 3  ✅ 刚好等于上限

你原话的接线（主控直辖 + 新角色与裁判构成 Leader/Partner，即新角色派裁判）：

    法律咨询主控(1) → 线索侦察(2) → 网络裁判(3) → 辩手(4)  = 4  ❌ 越界

拦截点不是模型自觉，是代码：`DebateChainGuardHooks`（挂在主控与裁判上）在委派边界上判
「链深 ≤ `MAX_CHAIN_DEPTH` 且不得成环」⇒ **第 4 次委派会被直接拒绝**。
表现不是「慢」，是「下游一次都没被调用」。

> ⚠️ 这一条必须**实测**才算数，不能只读常量。本项目纪律：「『能调大』这条不是读 stub 得出的」——
> 真要动链深，得先用一个「停不下来的假模型」证明 `max_steps` 那种行为级结论。

### 2.2 三种可行接线

#### B1 · 兄弟式（不动上限，代价在主控预算）

    主控(1) → 线索侦察(2)   ← 叶子，回「候选线索清单」，不派任何人
    主控(1) → 网络裁判(2) → 辩手(3)

线索角色**不碰裁判**，由主控把选定的话题再派给裁判。链深仍是 3 ✅。

代价在主控的步数预算上，而且这个预算**已经紧过一次**：
`acps_config.py:170` 记录了 2026-10-04 的实测 —— 服务模式把 `max_steps` 钉死在 8，
8 步 ≈ 6 次 wait ≈ 180s 窗口，而内层三级嵌套实测 **179s**，「余量约 0.5 秒」。
后来 CLI 路径提到 `LEADER_RESEARCH_MAX_STEPS = 14`（≈450s）才好过。

**「先派线索、再派裁判」= 把两条子链塞进同一个 run** ⇒ 主控要么加步数，要么大概率等不到裁定。
而且主控的三个终止 Hook 常量是**成对**的（`agents.py:551-555`：
`expected_partners=1` / `reserve_steps=0` / `partner_label="网络裁判或证据鉴证 Leader"`），
动它就得同步改注入文案 + 重跑 `verify_termination`。

#### B2 · 队列式（不动上限、不动预算，推荐）

线索角色**不进同步委派链**，它当一个**生产者**：把线索落盘（例如 `.wit/leads/*.json`），
主控（或一条定时自动化——本项目已有这个装置）按需取用。

- 链深：零变化 ✅
- 主控预算：零变化 ✅（取线索是一步读文件，不是一次 `discover + 派发 + N×wait`）
- 授权：零变化 ✅（见 §3.2）
- 平台叙事：**少一层「实时互联」** ← 这是唯一真实的代价，见 §2.3

#### B3 · 提深（可行但连带改动最多，不建议现在做）

把 `MAX_CHAIN_DEPTH` 从 3 提到 4。连锁反应，**至少四处**：

| 位置 | 现状 | 提深后 |
|---|---|---|
| `contracts.py:804` | `MAX_CHAIN_DEPTH = 3` | 改 4 |
| `check_local.py:404` | `if MAX_CHAIN_DEPTH < 3: [失败]` | 断言变成**恒真**（4 < 3 为假）⇒ 判据空转，得改成跟着新上限走 |
| `run/meta_verify_evidence_leader.py:257` | 元验证用例 `new="MAX_CHAIN_DEPTH = 3"` / `old="… = 2"` | **这个用例会被推翻** —— 它的「正确形态」写的就是 3 |
| 环检测 | — | 项目自己写明「必须先改 `MAX_CHAIN_DEPTH` 并**重新评估环检测**」（`acps_config.py:112`） |

后两条是本项目最贵的一类改动：**元验证锚点是跟着实现走的**，改常量就得搬家，
不搬就会「照样通过」但已经和实现对不上。

### 2.3 两个语义冲突，得先解决

**(a)「直辖」与「与裁判成 Leader/Partner」是同一个关系的两种讲法，只能选一个。**

如果新角色派裁判，那它是**裁判的上游（Leader）**，不是与裁判平级的 Partner。
而裁判已经是主控的 Partner。所以「主控直辖新角色 + 新角色辖裁判」这句话，
在链路上的意思只有一种：新角色插在主控与裁判之间（= B3，撞墙）。

**(b) 更值得警惕的：让「选题的人」去派「判定的人」，会污染判定中立性。**

这是 selection bias，而且是本项目已经解决过一次的同一类问题 —— `agents.py:589-592`
对裁判独立性的记录写得很直白：

> 旧结构里由**正方兼任**子会话 Leader，等于**既当运动员又当裁判**……
> 裁判独立之后，正反双方都是它的直接 Partner，辩论由裁判居中转达。

现在这个提案换个位置犯同一个错：**谁挑案子，谁就决定了判定的样本空间**。
一个既要「找高热度、有煽动性、有争议性」的话题、又要「中立判定真假」的角色，
它的两个目标**方向相反** —— 追求话题性会系统性地偏向「能出结论、有戏剧性」的案子。

⇒ **建议：挑案与判案必须是两个角色，而判案那个已经存在。**
这正好把 §1 的拆分从「拆分方便」升级成「不拆就是设计缺陷」。

## 3. 授权问题：三条路，不是一条

用户判断「得到相关的软件授权目前可以说是毫无办法」。
**这个判断我同意，但它推导出的结论应该反过来**（§3.5）。

### 3.1 平台侧授权（拉取模式）—— 走不通，而且不是技术问题

「接入某个软件、拿它的全站热点数据」卡在三层上，一层比一层硬：

1. **接口形态不匹配**：主流平台的开放平台面向的是**内容发布者与运营方**
   （发内容、管账号、看自家数据），**不提供「全站热点话题」的生产级检索**。
   热搜类接口即使存在，通常也要求企业主体 + 明确用途，且不承诺稳定性。
2. **动机不匹配**：平台没有动机把舆情数据接口开放给一个**第三方核查方** ——
   这是本文 §3.5 要单独说的那件事。
3. **责任不匹配**：一旦接了授权，本项目的结论就与平台产生了形式上的关联，
   而本项目所有交付物都带免责声明、且强制允许「无法判定」—— 与平台的内容治理诉求天然冲突。

⇒ **同意用户：这条走不通。** 但「走不通」的范围要说准：**走不通的是「全站/全景检索」**，
不是「任何外部数据」。公开可访问的页面、已发布的权威报道、政府公开通报，
**抓公开页面**与**拿平台数据授权**是两件事，后者才是走不通的那个。

### 3.2 用户侧授权 —— 现在就能做，**授权需求为零**

把方向反过来：不由系统去平台取，而由**用户**把它**有权访问的内容**递进来。

- **授权主体是用户，不是平台** ⇒ 平台授权问题**不存在**。
- 用户转发/粘贴/上传是日常行为，不涉及绕过任何访问控制。
- **本项目已经全副武装在这个形态上了**：
  - 收件箱（`evidence/inbox.py`）+ **内容哈希句柄**（不是路径）
  - 入站附件 hook 已挂主控与 evidence-image（`EvidenceInboxHooks`），
    且已经处理过两种形态（`bytes` → `data=`；`uri` → `uri=`，**uri 形态不自动去取**）
  - 「文字材料贴进 `text`」是对外口径（`FilePart` 无人接手）
- **「热度」这个字段用户侧也能给**：递进来的时候附带「哪个平台、多少转发/评论」即可。

⇒ **代价只有一个：覆盖面**。从「我扫全站」退回「用户给我什么我看什么」。
换来的是：零授权、零 SSRF 面、零反爬对抗、零合规风险。
**第一阶段就该走这条。**

### 3.3 公开数据侧 —— 不需要授权，而且质量更高

用户说「必须有足够充足的资料」。这里有一个反直觉的点要讲清楚：

**判定「是否为真」最可靠的资料，不是「搜到的」，而是「权威方有没有给过结论」。**

- **已公布结论的辟谣库**（中国互联网联合辟谣平台等）—— 这是现成的 ground truth，
  而且是**唯一**能用来量化「有效性」的东西（§4.2）。
- **官方通报 / 一手文件**：对应 `SourceLevel.PRIMARY`，契约里写着「只有一手材料能支撑事实判断」。
- **已发布的权威报道**：`SECONDARY`，只能当辅证。

⚠️ 反过来，**「全网抓一堆二手转述」会降低准确性**：`FactSheet.missing` 的设计意图就是
「拿不到就如实说拿不到，不要用推测填补」。检索能力越强，越容易把
「观点评论」当成事实喂给裁判 —— 那是在帮倒忙。

⇒ **资料策略：权威结论 > 一手材料 > 二手转述，且来源等级必须随结论一起落盘。**
一条判定的 `SourceLevel` 如果全是「观点评论 / 来源不明」，这条判定**不算数**。

### 3.4 「通用接口 vs 逐软件定制」是**伪二选一**

正确形态本项目已经有过三次实践了，看 `evidence/fetch.py` 的形态：

    单一契约（调用方永远只表达一件事：我要这个引用对应的字节）
      + 多条来源（inbox 句柄 / data: URI / 白名单出网）
      + 白名单默认空（fail-closed）⇒ 未配置 = 禁止一切出网，不是允许一切

套到线索上就是：

| 层 | 做法 | 通用还是专用 |
|---|---|---|
| **对外契约** | `线索来源` 一个契约（谁给的 / 在哪 / 原始材料引用 / 热度指标 / 时间） | **通用，一份** |
| **取数适配器** | 每个软件一个**薄**适配器（一个浏览器插件 / 一个已公开的 RSS / 一个官方通报页） | **专用，各写各的** |
| **准入** | 白名单默认空；未列出的来源一律拒绝，且拒绝要带**机器可读的分类码 + 可执行的出路** | 通用 |

⇒ **契约通用、适配器专用。** 不做「一个爬虫打天下」（那是通用接口的坏版本：脆、要对抗反爬、
且每改一次页面就坏一次），也不做「每个软件一套链路」（那是专用定制的坏版本：
判定口径会被复制出第二份，必然漂移）。

⚠️ 附带一条本项目的硬口径：**拒绝也要能指导行动**。参考 `FETCH_REFUSAL_KINDS`
与 `pipeline.fix_for()` —— 拒绝时不能只说「不支持」，得说「该改什么」。

### 3.5 关于「平台不会不吃黑流量」

用户这个判断**大概率对**，但它的推论应该反过来 —— 我认为这才是整个问题里最值钱的一句。

- 平台的动机是流量，核查方的动机是事实。**两者利益不一致。**
  ⇒ **指望平台合作本身就是设计错误**，不是在等一个更好的时机。
- ⇒ 因此这件事**不该做成「平台插件」或「平台内容治理模块」**。
  做成插件，等于把自己的结论交给利益相反的一方去决定要不要用。
- ⇒ 该做的是**独立第三方核查方**，产物是**可引用的结论**：
  `ruling-*.json` + 一份人能读的报告。它的用户不是平台，是
  **转发前想查一句的普通人**、**被断章取义的人**、**被要求回应时需要一个依据的机构**。
- ⇒ 落点也就在这：**报送**通道（网信办举报中心 / 12377 / 联合辟谣平台）是**公开入口**，
  不需要授权。**能建立的是「输出」关系，不是「输入」关系** —— 而输出关系本来就够用。

⚠️ 但必须同时说清代价：**主动抓取这一侧做不成平台合作，就意味着覆盖面永远靠外部递入**，
这个产品的天花板由此决定。诚实地写在设计里，比假装以后能解决要好。

## 4. 有效性：整个提案里最容易自欺的部分

用户问「怎样保证 agent 确实有效」。我的答案是：**现在保证不了，而且必须先把「有效」定义出来，
否则一定退化成自娱自乐** —— 正是用户自己担心的那件事。

### 4.1 现有唯一的判据证明不了这件事

本项目唯一判据是「`output/` 下有没有 `verdict-*.json` / `ruling-*.json`」（`status=completed ≠ 链路成立`）。
它证明的是：**链路成立、产物落盘**。它**不证明结论正确**。

对一个「自动发现 + 自动判定」的角色，这两件事的差距被放到了最大：
一个每次都判「断章取义」的角色，链路 100% 成立，产物 100% 落盘，
**而它是一个纯害**（见 §5 名誉权）。

### 4.2 有效性判据只能是四条（缺一条就会被自己骗过去）

| # | 判据 | 为什么必须单独报 |
|---|---|---|
| a | **一致率**：拿一批**已有公开结论**的历史谣言当 ground truth，跑一遍，算与官方结论的一致率 | 这是唯一的客观分母；没有它，「有效」只是感觉 |
| b | **弃权率**（「无法判定」的占比），**与一致率并列报** | 只报一致率时，一个「全部弃权」的角色能拿 100% —— 这条是防自己骗自己的 |
| c | **负控**：喂**真的、没问题**的话题，看它会不会硬造出「断章取义」 | 「见谁都说有问题」在正向指标上完全看不出来 |
| d | **来源等级约束**：判定依据里 `SourceLevel` 全为「观点评论/来源不明」时，该判定**不计入 a** | 否则「抓一堆转述然后下结论」会被算成有效 |

> ⚠️ 这四条是**照抄检测层既有不变式**的形态：本项目纪律要求新的判据
> 「照抄检测层 `summarize()` 的不变式」，而不是另发明一套 —— 否则判据与实现会一起漂移。

### 4.3 门槛：先离线回测，达标才谈「上线主动发现」

**「有没有社会效益」这个问题的答案 = 离线回测的数字。** 在拿到这组数字之前，
任何「这个系统很有社会价值」的说法都是不可验证的。

因此建议一个**硬门槛**：

    第 1 步：被动受理的线索 + 现有裁判/证据链，先在**离线**回测集上跑出 a/b/c/d 四个数字。
    第 2 步：只有数字达标，才投入去做出网检索与主动发现（那是最贵、风险最高的一段）。

这也是对用户「不要自娱自乐」那句话的**唯一**工程化回应：
**别用「我觉得它有用」来回答，用一组带负控的数字来回答。**

## 5. 必须同时决定的合规边界（不说清就不能做）

一个「自动检索话题 + 判定真假」并且可能对外发布结论的系统，会引入本项目此前没有的风险：

| 风险 | 具体形态 | 必须的处理 |
|---|---|---|
| **名誉权** | 判错就是**新的伤害源**，而且是「以辟谣之名」 | 弃权强制；结论必须带来源等级；对外发布需要人工复核 |
| **系统本身被武器化** | 「话题 X 被提交核查」这件事本身就是一次污名化 | **核查状态不得公开**；内部核查与对外发布必须分离 |
| **对特定主体的负面认定** | 与 `harm` / `incitement` 角色的旧风险同族 | 沿用既有口径：只做法律预防，不做事实定论式的公开指控 |
| **数据留存与展示范围** | 线索里会含普通人的言论与身份线索 | 明确留多久、谁能看、能否引用 |
| **「平台内容治理」角色** | 那需要资质，本项目没有 | **明确不做**；只做第三方核查与报送 |

⇒ 一句话：**判定能力可以直接复用，但「主动发现 + 对外发布」这一段必须单独过合规，
不能因为技术上是同一个 agent 就跟着一起上。**

## 6. 建议的三步走

| 步 | 内容 | 新增出网面 | 新增授权需求 | 可验收的产出 |
|---|---|---|---|---|
| **1** | **队列式线索入口**（B2）：定 `线索来源` 契约，做**用户递入**（复用收件箱），线索落盘，主控/自动化按需取用 | **零** | **零** | 线索落盘 + 能被主控取用 + 链路仍 depth ≤ 3 |
| **2** | **离线回测**：用已有公开结论的历史案例跑现有裁判/证据链，出 §4.2 的 a/b/c/d 四个数字 | 零（用已有案例集） | 零 | 一致率 + 弃权率 + 负控结果；**决定要不要做第 3 步** |
| **3** | **主动发现**（可选、最贵）：白名单出网 + 逐软件薄适配器，**默认关闭** | 大（新开一类出网面） | 需逐来源确认 | 只有第 2 步达标才做；上线前补 SSRF 面复核 |

⚠️ 第 3 步是唯一需要重新论证的一步，而且它的论证**不是技术论证**（技术上可行），
是**授权与合规论证**（§3、§5）。

## 7. 落地细节（若确定要做第 1 步）

- **落点**：新角色挂在**主控下当叶子**（B2 队列式则不挂在链上），
  **不放在裁判与辩手之间** —— 那会撞 `MAX_CHAIN_DEPTH`（§2.1）。
- **端口**：`PORTS` 目前用到 8452。`acps_config.py:74` 的注释写「8443–8454 是安全组已放行的端口」，
  按这条推 **8453 起可用**；⚠️ 但**这是注释，不是实测**，真要用得先去云控制台确认，
  本项目纪律不允许把注释当证据。
- **部署清单**：**不要手工维护第二份**。`acps_config.SOFT_RETIRED` 是单一事实源，
  `DEPLOY_ROLES` 由它派生，`scripts/serve.sh` 与 `scripts/systemd-install.sh` 都从它派生。
  新角色只需加进 `PORTS` 与 `BUILDERS`，两个脚本**不用改**。
- **护栏**：如果它是**叶子 Partner**（不发起委派），按 `evidence-image` / `audio` 的同形处理 ——
  **只挂 Termination**，不挂三件套；如果它要发起委派，才需要 `DebateChainGuardHooks`。
  ⚠️「装了」≠「会响」：挂载位置只能靠**关系断言**验，不能靠读代码。
- **注册**：新角色是要走平台 enroll + **人工审核** + 签证书的（本项目 §2.4 的流程）。
  如果只是做第 1 步的被动受理，**可以先不进链路、不注册**，用本地入口验证；
  等第 2 步的数字出来再决定要不要占一个端口与一次审核名额。
- **命名**：⚠️ 本项目「Leader」一词已经被两个相反的意思占用过
  （见项目记忆的硬规矩）⇒ 任何文档里说清是「调用方」还是「被调用方的上游」。

## 8. 未决问题（需要用户拍板）

1. **第一步走 B1 兄弟式还是 B2 队列式？** 差别在「是否要占主控的步数预算换取平台叙事上的一层实时互联」。
2. **授权策略选哪条？** 我的建议是 §3.2 用户侧递入（零授权）+ §3.3 公开权威源；
   平台侧拉取（§3.1）建议明确放弃，并把这个放弃**写进设计文档**，而不是留一个「以后也许能拿到」。
3. **回测集从哪来？** 需要一批「已有公开结论」的历史案例（成对：原始材料 + 权威结论）。
   这是第 2 步的前置条件，也是目前**唯一**还没着落的东西。
4. **对外发布形态？** 只做内部核查，还是产出可引用的报告 / 报送？
   这一条决定了 §5 里哪些风险必须当天解决。

---

**结论**：判定层已经具备（复用，不要重建）；发现层在「外部递入」形态下**可行且授权成本为零**，
在「主动抓取」形态下技术上可行但授权上走不通、合规上高风险；而「能否产生社会效益」这个问题，
**当前不可知** —— 它的答案只能是第 2 步那一组带负控的数字。
