# 音频（声音）鉴伪 —— 怎么用

面向**使用者**：想把自己的录音送进来做一次编辑痕迹初检的人或 Agent。
每一条结论都标了来源，与 `调用说明.md` 保持同一套口径：

- **实测** —— 本机跑出来的行为，不是推断
- **规范** —— MCP / ACPs / AIP 规格原文
- **设计** —— 刻意的取舍，附带理由

---

## 0 一句话

**给一段音频的字节，拿回九项技术线索 + 一个综合线索等级 + 一条复检阶梯。**
**拿不到「真 / 假」** —— 这是设计，不是缺陷（见 §7）。

音频进来**只有两种方式**：随任务附件产生的 `inbox:<sha256>` 句柄，或 `data:audio/…;base64,…`。
**本能力不出网、也不读本机文件**（见 §3）。

---

## 1 你能拿到什么

同一套检测核心，**两个入口**，结论逐字相同（这一点由 `tools/verify_audio_mcp.py` 直接断言）：

| 入口 | 谁用 | 需要什么 | 工具 / 能力名 |
|---|---|---|---|
| **MCP server** | 本机的人工使用者 / 通用 AI 客户端（Claude Desktop、WorkBuddy 等） | 一个能跑 Python 的终端 | `audio_probe` / `audio_forensics_analyze` / `audio_enf_track` |
| **ACPs 能力** | 已注册的 ACPs Agent（走 mTLS） | 自己的 AIC + 客户端证书 | `evidence.analyze_audio` |

三个工具的分工：

| 工具 | 干什么 | 给结论吗 |
|---|---|---|
| `audio_probe` | 第一眼：这段字节是什么容器、采样参数多少、**能不能解出波形** | ❌ 不给 |
| `audio_forensics_analyze` | 九项检查 + 综合线索等级 + 复检阶梯 | ✅ 给等级 |
| `audio_enf_track` | 把电网频率（ENF）的**逐窗轨迹**摊开，供人工核查 | ❌ 不改判定 |

> 为什么要有 `audio_probe`：跑完整检测之前先确认「这份东西我们能不能看」。
> 一份 MP3 在**没有解码器**的机器上只能给出容器层结论，`audio_probe` 会第一句话就说清楚。

## 2 怎么接

### 2.1 本机 MCP 客户端（推荐先试这条）

**不需要注册、不需要证书、不需要联网。** server 是本机子进程，用 stdio 通信。

在客户端的 MCP 配置里加一项（WorkBuddy 是 `~/.workbuddy/mcp.json`；
Claude Desktop 是 `claude_desktop_config.json`；键名都是 `mcpServers`）：

```json
{
  "mcpServers": {
    "legal-acps-audio-forensics": {
      "command": "C:/Users/Zhao5/Desktop/Mycode/witrelate/.venv/Scripts/python.exe",
      "args": ["-m", "legal_acps.mcp.server"],
      "cwd": "C:/Users/Zhao5/Desktop/Mycode/witrelate"
    }
  }
}
```

三个**必须**照做的地方（每一条都真的踩过）：

1. **`command` 要用绝对路径指向项目的 `.venv`**，不要写裸 `python`。
   用系统 Python 会在 `import pydantic` 那一步就崩（服务器与本机都实测过）。
2. **`cwd` 必须是项目根目录**。`legal_acps` 是相对包名，在别的目录下 `-m` 找不到它。
3. **必须模块方式启动**（`-m legal_acps.mcp.server`）。
   写成 `python legal_acps/mcp/server.py` 会 `ModuleNotFoundError` ——
   这与本项目"一律模块方式跑"是同一条规矩。

改完配置要**重启客户端**；MCP 连接只在启动时建立。

> ✅ **接线现状与自检**（2026-10-05）：本机已按上面这段接好
> （`~/.workbuddy/mcp.json`；音频与视频**两条**都要写，理由见视频侧 §2.1）。
> 改完配置后跑：
>
> ```bash
> ./.venv/Scripts/python.exe run/verify_mcp_config.py
> ```
>
> 它会 **① 现场从使用说明里抽那段 JSON** 与 `~/.workbuddy/mcp.json` **逐字比对**；
> **② 真起一次 stdio 握手**（`initialize` + `tools/list`），断言 server **自报的名字**
> 与它该是的那一个一致（防两个入口串了）；**③ 负对照**：裸 `python` 必须判失败。
> 判据是**退出码**（0 通过 / 1 判据失败 / 3 配置不存在）。
>
> **这条判据已进 `check_local` §3e**（2026-10-05）⇒ 不必再靠"有人记得单独跑它"。
> ⚠️ 客户端配置是**每台机器一份**的（不进仓库、不进同步清单），所以**别的机器上它会
> 「响亮跳过」并单独计数**：跳过 ≠ 通过 —— 看板写的是「1 项跳过未判」，不是算进通过。

> ⚠️ 有些客户端会把 MCP 配置缓存到自己的目录里。改完没生效时，先确认它读的是你改的那个文件。

### 2.2 ACPs 通道（已注册 Agent 之间）

走这条路的是**上游 Agent**，不是人：调用方必须是**已注册的 ACPs Agent**，
因为直连模式在 `identity_binding_enabled=true` 时会从 mTLS 对端证书里取 AIC，
并校验 `senderId == peer AIC`（规范 §6.0）。

- 能力 id：`evidence.analyze_audio`（角色 `evidence-audio`，端口 8451）
- 入参就是 `AudioEvidenceRequest` 的三个字段：`audio_uri` / `declared_mime` / `context_note`
- 正常调用链是**经过「法律咨询主控」**：你在任务文本里说清"要检查随附的录音有没有剪辑痕迹"，
  主控把它派给证据鉴证 Leader，Leader 再派给音频鉴伪专家。
  **不要跨层直接指挥内部专家**（AIP §3.2：Partner 之间不直接交互）。

⚠️ **注册状态（2026-10-02 实测）**：本机 `.wit/evidence-audio/acps/` 里只有 `acs.draft.json`，
没有 `enrollment.json` ⇒ **从这台机器看尚未登记注册信息**，所以 §2.2 这条路目前调不通。
平台侧的真实状态请用 `python -m tools.list_agents` 查
（**别用 `python -m tools.status` 查只读状态** —— 它会顺手 enroll 并提交审核）。

## 3 怎么把音频交进来 —— **只有两种引用**

```
inbox:<sha256>                          ← 随任务附件进来的字节（**首选**）
data:audio/wav;base64,<载荷>             ← 自带字节
```

**没有第三种。** 下面这些**一律被拒绝**（并且会告诉你该怎么改）：

| 你给的 | 结果 | 为什么 |
|---|---|---|
| `https://example.com/a.wav` | ❌ 拒绝 | 音频侧**没有任何出网通道**（见下） |
| `file:///C:/x.wav` / `C:\x.wav` | ❌ 拒绝 | 不读本机文件 |
| `ftp://…` / `//server/share/x.wav` | ❌ 拒绝 | 同上 |
| `inbox:../secret` | ❌ 拒绝 | 句柄是**内容哈希**，不是路径 |
| `data:audio/wav,raw` | ❌ 拒绝 | `data:` URI 必须是 base64 编码 |
| `data:text/plain;base64,…` | ❌ 拒绝 | 声明的类型不是音频 |

### 为什么音频侧**刻意不做出网通道**（与图像侧不同）

图像侧有一条受白名单约束的取图通道（`EVIDENCE_IMAGE_ALLOWED_HOSTS`），因为模型工具层的
schema 只允许传 URL，**看图**的前提就是把图弄进来。

音频侧**没有这个不得已**：证据音频的正规来路是"用户上传的一份文件"，
而**每开一条出网通道就多一个 SSRF 面** —— 任何能给我发任务的对象，
都能驱使本进程去访问任意地址（内网探测）。

> **能力做小，比做全更符合这条链的实际。** 调用方要做的是把字节交给我们，
> 而不是把地址交给我们。

### 体积与时长上限

| 限制 | 值 | 说明 |
|---|---|---|
| 音频字节上限 | **16 MiB** | 超限**拒绝，不做截断** —— 截断会让时长、容器长度、尾部标签全部失真 |
| 收件箱接收上限 | 16 MiB（同量级） | 与上面必须同量级，否则会出现"文件允许通过、一进来就被截断分析" |
| 波形域分析窗 | 8,000,000 帧（44.1 kHz 下约 181 秒） | 超长音轨**只分析开头一段并如实标注**，不静默截断 |

16 MiB 的 16 位单声道 PCM ≈ 190 秒，与 181 秒同量级 —— 这两个数字是**配着定的**。

## 4 三个工具的入参出参

### 4.1 `audio_probe`

| 参数 | 必填 | 说明 |
|---|---|---|
| `audio_uri` | ✅ | 见 §3 |
| `declared_mime` | — | 调用方声明的类型。⚠️ **本工具只原样回显，不参与任何判定** —— 「声明与真实容器是否一致」由 **`audio_forensics_analyze` 的 `container` 一项**报出（在那里比对一次就够了；探针再比一次就是"同一判定写两处"） |

返回：`media_type` / `byte_size` / `sha256` / `fetched_from` / `container{采样率,声道,位深,时长,帧数,是否截断,尾部附加字节}` /
**`pcm_available`** / `pcm_note`。

> `pcm_available` 是这里最重要的一个字段。它是 `false` 时**波形域六项整项跑不了**，
> 后面那份报告只能覆盖容器与编码参数层 —— 这一点必须让调用方第一眼就看到。

### 4.2 `audio_forensics_analyze`

| 参数 | 必填 | 说明 |
|---|---|---|
| `audio_uri` | ✅ | 见 §3 |
| `declared_mime` | — | 与真实容器不符时会作为一条线索报出 |
| `context_note` | — | 这段录音在案情里的分量（如「据称是通话录音」）。**仅原样回显，不参与任何判定** |

返回：`### 综合线索等级：…` + 一句话摘要 + 溯源字段 + **九项逐项发现**
（每项都带 依据 与 **它不能证明什么**）+ 证据保全提示 + 复检阶梯 + 免责声明，
末尾附一份**可机读 JSON**（同一份内容，供脚本取结构化字段）。

### 4.3 `audio_enf_track`

| 参数 | 必填 | 说明 |
|---|---|---|
| `audio_uri` | ✅ | 见 §3 |
| `base_hz` | — | 只允许 `50` 或 `60`；不填按同一套判据自动挑。**其余取值一律被拒**（电网频率只有这两个） |
| `window_seconds` | — | 分析窗长，默认 `1.0`，允许 `0.1–10` |

返回：`available` / `detected` / `base_hz` / `comb_snr_db` / `std_hz` / `points[{t_seconds, freq_hz}]` / `reason` / `note`。

> ⚠️ **轨迹点的意义完全取决于 `detected`**：`detected=true` 时它们才在跟踪真实的电网频率，
> 「相邻点跳变」才有解释力；`detected=false` 时它们只是各窗里**噪声峰的位置**，
> 看这条轨迹**看不出任何东西**。不要拿"抖动大"当剪辑依据。

**成功与失败的边界（这一点按"调用方要不要改点什么"划）**：

| 情形 | 返回 | 为什么 |
|---|---|---|
| 波形正常，只是没检出市电痕迹 | `isError=false`，`detected=false` | ENF 检不出是**常态**，调用方没有任何东西要改 |
| 采样率过低 / 音轨过短 | `isError=false`，`available=false` + `reason` 说明原因 | 同上：这是这段材料的性质 |
| 字节不是音频 | `isError=true`，原因写明按魔术字节判成了什么 | 要改的是**送进来的东西**（与 `audio_forensics_analyze` 的处置同源） |
| 解不出波形（压缩格式 / WAV 头坏了） | `isError=true`，原因来自解码层**原文** | 同上。注意这里会如实区分「本机没有解码器」与「这个文件的头有问题」—— 照着前者去转格式，对后者是白折腾 |

> ⚠️ `base_hz` 的校验**在服务端做**，不依赖客户端执行 schema 里的 `enum`：
> 收下一个 `123` 会让它按 123 Hz 的谐波梳算一通，然后如实报「未检出」——
> 而调用方读到的结论是"没有市电痕迹"。

## 5 九项线索：能发现什么 / 什么时候不适用

每一项都对应一种**公开发表**的音频取证手段。权重是专家先验，不是拟合出来的。

### 容器层（不需要波形，压缩格式也跑得了）

| 检查项 | 权重 | 能发现什么 | 它**不能**证明什么 |
|---|---|---|---|
| `container` | 0.5 | RIFF/data 块长度是否自洽、帧链是否中断、尾部是否多出标签、**声明的类型与真实容器是否一致** | 只说明"文件是怎么被写出来的" |
| `codec_params` | 1.0 | `byte_rate`/`block_align` 是否与采样参数自洽；**MP3 采样率或声道模式跳变** | ⚠️ MP3 **比特率**跳变是 VBR、正常，不算线索 |
| `metadata` | 0.5 | 容器内可见文字标签里有没有编辑/转码软件署名（Audacity、FFmpeg、剪映……） | 很多软件**不留**这个标签；留下也不代表这次动过手 |

### 波形层（需要 PCM 波形）

| 检查项 | 权重 | 能发现什么 | 它**不能**证明什么 |
|---|---|---|---|
| `spectral_cutoff` | 0.5 | 频谱高端**硬截止** —— 有损编码（MP3/AAC）的痕迹，或**重采样**留下的台阶 | 只能说明"曾重编码"，不能说明"被剪过" |
| `noise_floor` | 1.0 | 底噪水平是否**前后恒定**；两段不同环境拼起来会明显不同 | 录音环境本身改变（开门、开窗）也会变 |
| `silence` | 1.0 | **数字静音**（样本恰好为 0）的长段 —— 真实录音的"安静"里总有底噪 | 有些设备/驱动会输出真正的 0 |
| `spectral_flux` | 0.5 | 谱**形状**的不连续（帧间归一化谱的余弦距离尖峰） | 瞬态干扰多（敲击、爆音、音乐），只作辅助 |
| `sample_discontinuity` | 0.5 | 样本级不连续（波形上的"咔哒"） | 同上，是辅助项 |
| `enf` | **1.5** | 电网频率（50/60 Hz）及其谐波的相位是否**连续**；剪辑造成相位跳变 | ⚠️ 检出率本来就不高（**手机在户外录音通常测不到**），检不出即弃权 |

> **ENF 这一项的方法**：市电会给录音引入 50/60 Hz 及其谐波的极微弱哼声，
> 而电网频率在时间上是**连续**的（各地电网自己有一个微小漂移）。
> 剪辑会把两段不同时刻的相位硬接在一起 ⇒ 相位跳变。
> 开源实现可参考：**ENF-Extractor**（BitEU）、**ENFify**、**DF-Audio-Forensics**，
> 以及 Zeng 等人的 CNN-BiLSTM ENF 论文。本项目只用 numpy + 标准库自己实现
> （Goertzel 取梳状谐波能量，判据是谐波梳信噪比 ≥ 12 dB），**不引入 librosa/scipy**。

## 6 **弃权的两层** —— 这是本链最关键的一节

音频链的弃权比例**天然比图像链高**（压缩格式解不出波形、纯音谈不了频谱截止、
ENF 在真实录音里常检不出）。所以"某一项没跑"是常态。
**如果它能把整份报告压成「无法判定」，那么每一段正常录音都是「无法判定」**，
报告彻底失去信息量。因此弃权被分成两层，**互斥且并集覆盖全部弃权项**：

### 第 1 层：**材料级闸门**（`音轨不满足波形域检查的前提`）

只有三种情形，一旦成立 ⇒ **波形域六项会一起失效** ⇒ 整份报告只能说「无法判定」：

1. 根本没有解出波形（压缩格式 + 本机没有解码器）
2. 音轨短于 **0.6 秒**
3. 整段近乎无声

此时摘要**绝不会**出现"均未提示异常"这种话，而会写：
「本音轨不满足波形域检查的前提，N 项整项没有执行；其余项目只覆盖容器与编码参数层，
**不能据此认为「没有问题」**。」

### 第 2 层：**逐项不适用**（`本项对这段音轨无从执行`）

某一项因为"这段音轨上无从检验"而没跑，例如：

- 只有一处安静区 ⇒ 谈不了底噪一致性
- 检不出市电痕迹 ⇒ 谈不了 ENF 相位连续性
- 这段是纯音 ⇒ 谈不了频谱截止

**其余各项照常跑通，综合等级照常给出**（不改变等级），但摘要会点名缺席的项，
并写一句「**这不等于它们也合格**」。

> **一句话记住区别**：闸门是"整份报告测不了"，逐项是"这一项对这段音频不适用"。
> 把后者写成前者，等于把一份有用的报告变成一句废话。

### 边界情形：闸门与正向触发**同时**出现

比如"声明成 WAV 的其实是 MP3" —— `container` 因声明不符触发（0.5 ⇒ 低），
而波形域六项全灭。**触发优先**：等级照常给出，但摘要必须**点名缺席的项**，
让读者知道"这个等级是在六项缺席的情况下得出的"。

> 等级不是错的，错的是读者对它的信任。

## 7 怎么读结论

综合线索等级只有四档：**低 / 中 / 高 / 无法判定**。等级由程序按固定权重表算出，
**不是模型给的**（数字与结论不能经手被评价的那一方）。

| 等级 | 读法 |
|---|---|
| **低** | 本次可执行的检查项都没看到异常。**这不代表未经剪辑**，只代表本地这些手段没看到 |
| **中** | 有一项以上提示异常，值得进一步核查 |
| **高** | 多项强线索叠加。**仍不是篡改认定** |
| **无法判定** | 前提不满足或全部弃权。**这是合法且经常正确的答案** |

⚠️ 三条必须一起转述的话：

1. 报告里**没有「真 / 假」**。所列「提示异常」**不等于**该录音被篡改 ——
   转码、降噪、平台压缩、录音环境变化都会产生同类痕迹。
2. 所列「未提示异常」**不等于**该录音未经剪辑。
3. **「无法判定」不要转述成「没问题」**。这两句话在字面上离得很近，
   在结论上离得最远。

本报告是**技术线索**，不是司法鉴定意见，不能单独作为认定事实的依据。
**涉及法律责任时唯一有证明力的路径**是委托声像资料司法鉴定（复检阶梯的第三档）。

### 复检阶梯（三档，不随等级裁剪）

| 档 | 工具 | 成本 |
|---|---|---|
| 1 | **Audacity / Sonic Visualiser / ENF-Extractor**（均为开源） | 免费 |
| 2 | iZotope RX / Cedar 等专业音频修复取证工具 | 商业授权，万元级 |
| 3 | **声像资料司法鉴定**（录音真实性 / 完整性鉴定） | 通常 2000–5000 元/份，15–30 个工作日 |

第一档是**先做这一步**：把音轨载入 Audacity **放大看波形**，
可疑处的判断往往手一眼就能看出来。

## 8 排障与常见问题

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 客户端显示"连不上 / 无响应" | 启动就崩了（`command` 用了系统 Python） | 换成项目 `.venv` 里的 python 绝对路径 |
| `ModuleNotFoundError: legal_acps` | `cwd` 不是项目根，或没用 `-m` | 两处都改对 |
| `ModuleNotFoundError: No module named 'pydantic' / 'numpy'` | 用错了解释器 | 同上；本机 `numpy` 是 2.5.3 |
| 「本服务缺少运行依赖」 | 依赖确实没装 | 在该环境里装 numpy |
| 报告说"波形可用：否" | 压缩格式（MP3/AAC/FLAC/OGG），**服务器上没有 ffmpeg / sox / librosa** | 先用工具转成 WAV 再提交；容器层结论仍然有效 |
| 所有项都「无法判定」 | 触发了材料级闸门 | 看 `pcm_note` / 时长 / 是否近乎无声 —— 这是**如实报告**，不是故障 |

| 「不是可识别的音频容器」 | 给的不是音频字节（网页 / PDF / 文字） | 给**音频文件本身**的字节；`.caf` / `.silk` 这类非常见容器先转成 WAV |
| 拒绝理由说"不支持的引用" | 给了网络地址或本地路径 | 见 §3 —— 把**字节**交给它，不是把**地址**交给它 |

## 10 已知边界（对外说明时别漏）

1. **本机没有 ffmpeg / sox / librosa / soundfile / scipy** ⇒ MP3/AAC/FLAC/OGG
   **一律解不出波形**，只能给容器与编码参数层结论。这**不是缺陷**，是必须如实说出的边界。
   （所以音频链的检测核心只用 `numpy` + 标准库自己实现。）
2. **ENF 检出率本来就不高**。手机在户外录的音通常测不到市电痕迹，**检不出是常态**。
3. **音频侧不出网、不读本机文件**（刻意收缩，见 §3）。
4. **16 MiB 上限，超限拒绝、不做截断。**
5. **`evidence-audio` 尚未登记注册信息**（本机 `.wit/evidence-audio/acps/` 只有 `acs.draft.json`）
   ⇒ ACPs 通道目前调不通；**MCP 通道不受影响**（不需要注册）。
6. **MCP 通道没有身份校验**：它的信任模型是"能在这台机器上启动这个进程的人，
   本来就能读这些文件"。所以本项目**不提供**监听端口的服务器形态 ——
   一个无身份校验的网络服务会把"本机可信"这个前提直接作废。
7. **音频与视频是两条独立的链，也是两个独立的 MCP server**（MCP 配置里要写两项）。
   视频那条链的使用说明见 `docs/aicomp/视频鉴伪使用说明.md`。
8. **「认得这个容器」≠「看过里面」**（2026-10-05 补）。按魔术字节能认出来的容器里，
   只有 **WAV / MP3 / FLAC** 会被真解析；`Ogg / M4A / AIFF / AMR / WMA / AC-3`
   是**只识别、不解析**，报告照样出，但会写明「没有解析它的内部结构」，
   容器自洽性（声明长度 / 附加数据 / 尾部标签）那几项**本次没有检查**。
   ⚠️ **不要**把"没有提示异常"读成"看过了、没问题"。
   （`.ac3` 是 2026-10-05 才真正接进来的：它早就在容器表里，而嗅探器**没有分支**
   能返回它 ⇒ 真 `.ac3` 曾以「不是可识别的音频容器」被拒 —— 一句假话。）
9. **MP3 / FLAC 的头上**不写文件总长** ⇒ 那份"声明长度 vs 实际字节"的自洽性检查
   对它们**同样没有可比对象**，报告会照实说"没有可比的长度声明"。
   只有 WAV（RIFF）这类在头里写总长的容器才会给这一项下结论。
10. **声明类型请照业界通用写法写**：`.wma` 用 `audio/x-ms-wma`、`.ac3` 用 `audio/ac3`
    —— 别名表已覆盖这些写法。**不要再自行转格式去"对齐"名字**：转换会重写容器，
    而"容器被重写过"本身就是本能力要报的一条线索。
   ⚠️ 本行原先写的是「`video/*` 仍然没有下游通道：视频附件进得了模型请求，
   但系统不登记、也不转给下游」—— **那句话已过期**（视频角色 `evidence-video`
   与 `VideoFallbackHooks` 降级 Hook 都已落地，由 `tools/verify_video.py`
   第 11 节逐条断言）。留着它会让读者按一个不存在的限制去做设计。
8. **调用方必须是已注册 Agent**（§2.2）：人不能裸调端口，得通过自己的 Agent 或平台前端。
