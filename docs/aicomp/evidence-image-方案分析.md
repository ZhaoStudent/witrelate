## 0. 结论先说

**能做，而且与计划书一致 —— 它本来就是 §2.3 里预留的加分项（`evidence-image` 图像鉴伪）。**
端口从原定的 8449 换到已放行区间即可，**不需要再动腾讯云控制台**。

但有 **三个前置结论**，其中第 1 条是全新的、决定性的：

| # | 结论 | 影响 |
|---|---|---|
| 1 | **模型发起的委派只能传「URL」，不能传字节** ⇒ 出路有两条：**由代码层补字节**（`aip_delegate(request=ContentInput)`，**本轮已落地**）或让图先落在公网 URL 上。前者**一步也不用出网** | 这是整条链路的命门。配合"入站附件有两种形态（内联字节 / 仅地址）"，做法是**两种都接、各自说明**，见 §7 |
| 2 | **不要让模型「看」图，让代码「算」图** | 判定可复现、可审计；且绕开生产模型是否支持视觉输入的不确定性 |
| 3 | **检测器必须输出概率+不确定性，不能输出「真/假」** | G2 2026 实测：顶级检测器对确认的 AI 图仍有 15–20% 假阴性，对压缩过的真实照片有同量级假阳性 |

## 1. 命门：图像怎么进得来（实读源码，非推断）

### 1.1 三层结论

| 层 | 事实 | 出处 |
|---|---|---|
| **协议层** | AIP 有 `FileDataItem`，支持 `uri` **或** `bytes`(base64)，二选一 | `07-ACPs-spec-AIP.md:605-641` |
| **wit 代码层** | `AipCoordinator.delegate(..., request: ContentInput)` —— 原生支持多模态；<br>`ImagePart(mime_type, uri, data: bytes \| None, name, detail)` | `wit/acps/direct.pyi:223`、`wit/kernel/content.pyi` |
| **模型工具层** | `TOOL_CONTENT_INPUT_SCHEMA` 只暴露 `uri`（且 `additionalProperties: false`、必填 `uri`+`mime_type`），<br>描述原文 **"Absolute remotely reachable content URI."** | `wit/acps/tool_support.py`（运行时打印） |

### 1.2 由此推出的一条硬规则

> **模型发起的委派 → 只能给 URL；代码发起的委派 → 才能给字节。**

我们的链路是**模型自主协作**（这是比赛要展示的东西），所以走的是 URL 那条路。
⇒ 结论：**图片必须以"URI"的形态进入链路**。wit 没有提供"把本机文件变成 URI"的能力，
这一段得自己补（怎么补见 §1.3 与 §5.2）。

⚠️ **2026-10-01 实测补正（改动 §1.1 协议层那一行的理解）**：`FileDataItem.uri` 有个
上面没说透的约束 —— 它必须是**「远程可达」**的。逐条实跑 `aip.validate_data_items`：

| `uri` 取值 | 结果 |
|---|---|
| `data:image/jpeg;base64,AAAA` | ❌ **拒绝** |
| `file:///tmp/a.jpg`、`/tmp/a.jpg`、`""` | ❌ 拒绝 |
| `https://…` / `http://…` / `ftp://…` | ✅ 放行 |

报错原文：`file data item uri must be remotely reachable; use bytes for inline content`。

⇒ **§1.3 里"`data:` 也是一个合法 URI，所以字节可以内嵌在 URI 里传"这句话，
只在模型工具层（那是自由的 JSON 参数字符串）成立，在 AIP 附件层不成立**：
附件要自带字节，只能走 `bytes` 字段，`uri` 一律要"远程可达"。
这正是第 7 节要补的那条通道的由来。

### 1.3 需要自己补的那一块

> ⚠️ **本节写于方案阶段；落地时的做法与这里不同（更保守，且不需要开公网入口）。
> 以 §5.2 为准。**

方案阶段设想的是一个**取图网关**：

- 路由：`https://<公网IP>:<port>/evidence/<随机token>`
- 要求：① 公网可达；② **不能要求 mTLS**（下载方不一定持证书）；
  ③ token 随机会过期（证据图不应长期公开）；④ 只读、只能取到被登记过的图。
- 为什么不直接用现成对象存储：多一个外部依赖 + 出网成本；我们已有公网 IP 与放行端口。
- ⚠️ 安全红线（方案阶段的担忧）：这个路由会成为本项目**第一个无 mTLS 的对外入口**，
  必须做成 **token 白名单 + 过期 + 只读**，不接受任意路径（否则变成任意文件读取漏洞）。
  → 落地时通过"不建这个路由"直接消除了这条红线，见 §5.2。

**落地时改成了 §5.2 的做法**：`uri` 本身是字符串，`data:image/...;base64,...` **也是一个合法 URI**
⇒ 字节可以直接内嵌在 URI 里传，**既不要公网入口、也不要出网**。
于是做成"分层取图策略"：默认只接受 `data:`（零暴露），出网才需要显式白名单 ——
**结果是本项目依旧没有任何无 mTLS 的入站端口**，风险面比本节的设想更小。

### 1.4 顺带确认的两个次要约束

- **产物大小**：AIP 的 `StartCommandParams.maxProductsBytes` 限制产出物字节数。
  我们的报告是文本 + 结构化数据，量级 KB，**不构成问题**。
  反过来说，**不要**把图像本身当产物回传（会把字节数顶爆）。
- **角色语义**：ACS 规范里 **Leader = mTLS 客户端、Partner = mTLS 服务端**（`03-ACPs-spec-ACS.md:125-126`）。
  所以"谁能被连进来"取决于注册时的角色与端点，而不是我们内部的称呼。

## 2. 接线方案 A/B 对比（重点：技术实现难度）

### 2.1 两个方案是什么

- **方案 A —— 新建一层 `evidence-leader`**
  ```
  legal-consult-leader (8445, 外层 Leader)
     ├─ incitement / harm                     既有 Partner
     ├─ fact-judge                            既有内层 Leader
     └─ evidence-leader  ← 新增（内层 Leader，证据鉴证）
            ├─ evidence-image   ← 新增（图像）
            ├─ evidence-audio   ← 新增（音频）
            └─ evidence-video   ← 新增（视频）
  ```
- **方案 B —— 法律主控直接当聚合者（不新增 Leader 层）**
  ```
  legal-consult-leader (8445)
     ├─ incitement / harm
     ├─ fact-judge
     ├─ evidence-image   ← 新增（Partner）
     ├─ evidence-audio   ← 新增（Partner）
     └─ evidence-video   ← 新增（Partner）
  ```

### 2.2 对比表

| 维度 | 方案 A：新建证据 Leader 层 | 方案 B：主控中继 |
|---|---|---|
| **新增注册次数** | 1（先做 image）+ 1（leader）= **2**；三个模态都上 = **4** | **1**（image）；三个都上 = **3** |
| **平台审核 wall-clock** | ×2～×4（不可控，但到 10/15 还有 15 天） | ×1～×3 |
| **主控 instructions 改动** | ❌ **不必改** —— 主控只需认识 `evidence-leader` 一个入口，<br>后面挂几个模态与它无关 | ⚠️ **必须改** —— 要写"发现 + 派发"逻辑；<br>且**每加一个模态就要再改一次** |
| **主控步数预算（8 步，`RunConfig` frozen）** | **+1 跳**（只多一次派发） | **+N 跳**（每个证据 Agent 一跳），三模态时压力显著 |
| **discovery 依赖面** | **1 个查询词**（"证据鉴证"） | **N 个查询词**（每个证据 Agent 一个） |
| **对当前索引故障的敏感度** | 低（调用点少） | **高**（调用点多，任一查不到就断） |
| **委派链深** | +1 层（需同步核对 `MAX_CHAIN_DEPTH` 配额） | 不加深 |
| **其他 Agent 复用**（"还能被其他智能体调用"） | ✅ **好** —— 任何 Agent 只要发现 `evidence-leader`，<br>就能用上全部模态 | ❌ **差** —— 每个调用方都要自己写一遍发现+派发；<br>模态一变，所有调用方都得跟着改 |
| **横向扩展（audio/video）** | ✅ 挂在证据 Leader 下即可，**主控与其他 Agent 零改动** | ❌ 每加一个模态就要改**所有**调用方的 instructions |
| **代码复用** | ✅ **已有现成范式** —— `fact-judge` 就是"内层 Leader + 外层 Partner" | 无现成范式，需新写"主控多路委派"逻辑 |
| **失败面** | 多 1 个进程（但不影响主链路：挂了只是鉴伪不可用） | 少 1 个进程，但**主控变胖**（一个进程承担全部编排风险） |
| **演示叙事** | ✅ 清晰：「证据鉴证」是独立一层，与「事实裁定」并列 | ⚠️ 含混：主控什么都干，"协同"讲不出来 |
| **综合实现难度** | **中**（有范式可抄，难点在注册次数 + 链深配额 + 新开一层） | **低～中**（不新增层，但改主控有连带，扩展性差） |

### 2.3 判别性论据（不是偏好，是硬约束）

1. **步数预算是真的会撞墙的。** 本项目已经踩过：`RunConfig` 是 frozen 的，
   服务模式下 `max_steps=8` 钉死，Agent 侧改不了。
   主控现在已经有 `incitement` / `harm` / `fact-judge` 三路委派。
   **再让主控自己扛 3 个模态 = 最多 6 路委派**，8 步预算装不下。
   方案 A 把这部分编排移到 `evidence-leader` 的独立 8 步预算里 —— **这是两方案的分水岭**。
2. **"被其他智能体调用"这个需求本身指向方案 A。**
   用户明确要求"这个图像检查 Agent 还可以被其他智能体调用"。
   方案 B 下每个调用方都要复制一遍发现+派发逻辑，且模态一变全部返工；
   方案 A 下调用方只需要认识一个 `evidence-leader`。
3. **方案 A 没有新风险 —— 形状已经被验证过。** `fact-judge` 就是"既是 Partner 又是内层 Leader"，
   已经跑通过真机两级嵌套（18:52 那次 E2E 全链路通过）。
   方案 B 反而需要新写一段没验证过的"主控多路委派"。

### 2.4 推荐

> **走方案 A，但分两步走。**

- **第一步（现在）**：只做 `evidence-image`，**先按 Partner 单独注册**，
  暂时由主控中继 —— 因为只有 1 个模态时，主控多一跳是划算的，
  且这一步能最快验证"图像链路本身通不通"（这才是真风险所在）。
- **第二步（image 跑通后）**：引入 `evidence-leader`，把 image 挂到它下面；
  后续 audio/video 直接加挂，**主控与其他 Agent 一行都不用改**。

这样每一步都可逆，且第二步的收益（零改动扩展）刚好是这张表的结论。

## 3. 检测什么：能力分层

设计原则：**初检在本地零成本跑，复检作为"建议"输出给用户**（这正是用户提的"返回更准但更昂贵的方法"）。

### 3.1 第一层 · 本地初检（CPU、无模型权重、秒级）

这一层是全部价值所在 —— 它给出**可复现的证据**，而不是"一个黑箱分数"。

| 方法 | 检测什么 | 依赖 |
|---|---|---|
| **EXIF / 元数据一致性** | 编辑软件痕迹、时间戳矛盾、设备与尺寸矛盾、GPS 与内容矛盾、缩略图与原图不一致 | Pillow（+ 手写 TIFF/EXIF 解析） |
| **ELA（误差水平分析）** | 重压缩后误差分布异常区 —— 最经典的首轮筛查 | Pillow + numpy |
| **量化表分析（DQT）** | 量化表是否非标准（编辑软件重存）、单张图内是否混用两套表 ⇒ 双压缩线索 | 手写 JPEG 段解析 |
| **JPEG Ghost（多重重压缩）** | 用一组质量因子重压缩，找"最像原始"的因子 ⇒ 编辑历史 | Pillow + numpy |
| **噪声残差一致性** | 高通滤波后各区域噪声方差是否一致 ⇒ 拼接/克隆区 | numpy |
| **块效应网格** | 8×8 DCT 边界的周期性能量，网格错位 ⇒ 拼接 | numpy |
| **重采样检测** | 插值留下的周期性伪影 ⇒ 缩放/旋转/拼接 | numpy (FFT) |
| **复制-移动检测（弱版）** | 相位相关/自相关找重复区域；有 OpenCV 时可升级到 ORB+RANSAC | numpy（可选 opencv） |
| **局部熵一致性** | 自然图局部熵分布有结构；AI 生成图偏"过于均匀" ⇒ 启发式 AI 线索 | numpy |
| **容器/编码线索** | 是否单次 JPEG 编码、是否曾被 PNG↔JPEG 转换、ICC/comment 段异常 | 手写段解析 |

**重要的诚实性要求**：这一层的每一项都要标注 **"能证明什么、不能证明什么"**，例如
- ELA 有异常 ⇏ 一定是篡改（重新保存也会异常）；
- 元数据缺失 ⇏ 是假的（社交平台会剥掉 EXIF）—— **"缺失不等于伪造，但它是缺失的"**。

### 3.2 第二层 · 更准但更贵（作为建议输出，不在本地跑）

按成本从低到高：

**(a) 免费/低成本线上**
- **C2PA Content Credentials Verify** —— 只验签名，有签名即强证据（改图可被检出）；无签名=不确定
- **Google SynthID** —— 只识别 Google 自家生成的水印
- **OpenAI Image Verifier** —— 免费网页版，~85%
- **Deepware Scanner** —— 免费
- **Hive Moderation** —— 1000 图/月免费，其后 $199/月起
- **Optic (AI or Not)** —— $29/月起，100 图/月免费

**(b) 付费 API（企业级）**

| 服务 | 报价口径 | 公开准确率 |
|---|---|---|
| **Truepic** | **$0.02/次**（公开 API 定价） | 97.8%，强 C2PA 签名集成 |
| **deepidv** | $0.50/次，$19/月起 | 自称 99.1% |
| **Hive Moderation** | $199/月起 | 96.5%；可识别具体生成模型（Midjourney/DALL·E/SD） |
| **Reality Defender** | 企业定制，~中五位数/年起（≈1 万文件/月） | 96.9%，多模态 + 审计轨迹 |
| **Sensity AI** | 企业定制 | 98%（ensemble） |
| **Intel FakeCatcher** | 企业 | 96%（视频 PPG 血流，**对静态图无效**） |

⚠️ **必须写进报告的一句**：以上准确率均为**厂商自报**，且
**G2 2026 独立测试显示顶级检测器对确认 AI 图仍有 15–20% 假阴性**、
对高度压缩/缩放的真实照片有同量级**假阳性**。⇒ **任何单一检测器都不是权威。**

**(c) 线下司法鉴定（中国，强证据）**

- 归类：**声像资料司法鉴定**（含录音鉴定 / 图像鉴定 / 电子数据鉴定）
- 依据：《司法鉴定程序通则》（司法部令第 132 号）
- 机构资质：**省级以上司法行政机关登记在册**、持《司法鉴定许可证》、
  业务范围须含「图像鉴定」或「电子数据鉴定」（否则鉴定意见**不得作为认定案件事实的依据**）
- 流程七节点：委托申请 → 样本预检 → 签订协议 → 实验室检验 → 初稿复核 → 出具文书 → 归档
- **收费（发改价格规〔2020〕1632 号）**：
  **静态图像真实性鉴定 2500–4000 元/组**；录像资料真实性完整性鉴定 1500 元/件（每 20 分钟计）；
  录音资料真实性完整性 2000 元/件（每 20 分钟计）
- 时限：一般 **30 个工作日**
- ⚠️ 关键前提：**须提交原始载体**（只读存储设备、保留序列号）。
  ⇒ 我们的 Agent 应当**从第一分钟就提示用户"保全原始文件与哈希"** ——
  `hashlib` 算 SHA-256 是零成本的，但**事后无法补**。

### 3.3 这个分层为什么是"创新点"而不只是"功能"

它把"**证据可信度是有成本函数和不确定性梯度的**"这件事做成了产品形态：

```
本地初检（0 成本，给出线索与不确定度）
   └─ 若线索指向"可能被处理" → 建议廉价线上复核（免费~$0.02/次）
         └─ 若涉及法律责任 → 建议司法鉴定（2500–4000 元/组，30 工作日，需原始载体）
```

⇒ 与项目已有的 **结论溯源表**、**信息隔离**、**结构化终止信号** 是同一套设计哲学：
**不装作确定性，把不确定性显式地传递下去**。

### 5.2 取图策略：为什么"不建网关"反而更安全

| 输入形态 | 处理 | 出网 |
|---|---|---|
| `inbox:<sha256>`（**随任务附件进来的字节**，见 §7） | ✅ **默认接受**。句柄是**内容哈希而不是路径**，只可能命中本进程登记过的那份字节 | 否 |
| `data:image/png;base64,...` | ✅ **默认接受**（字节内嵌，完全可离线断言） | 否 |
| `https://<白名单内主机>/x.jpg` | ✅ 仅在显式配置 `EVIDENCE_IMAGE_ALLOWED_HOSTS` 后接受 | 是 |
| `http://`（明文） | ❌ 拒绝（明文链路上的图无法保证未被中途替换） | — |
| `file://` | ❌ 默认拒绝。**只能由入口代码显式打开**（`fetch.enable_local_file()`）。⚠️ 原先是环境变量 `EVIDENCE_IMAGE_ALLOW_FILE=1`，2026-10-01 改掉了 —— 环境变量会被 systemd / shell rc / 父进程一路继承，"服务模式不该有"这条纪律守不住 | — |
| 相对路径 / 网页链接 / 其它 scheme | ❌ 拒绝 | — |

- **白名单为空 = 禁止一切出网**（不是"允许一切"）。**不跟随重定向**（否则 302 可绕过白名单）；
  连接/读取超时；**下载字节数硬上限 8 MiB 且超限不截断**（截断会让所有统计失真）。
- **与委派护栏 fail-open 的关系**（这是本项最值得写进报告的一处设计判断）：
  `_check_partner_trust` 是**保护自家链路**，误杀会掐断链路 ⇒ fail-open；
  取图是**面向不可信输入的信任边界**，放行一次就是 SSRF ⇒ fail-closed。
  **判据不是"统一风格"，而是放行与拦截各自的最坏后果。**

### 5.3 一个不显眼但必须做的隔离（惰性导入）

`legal_acps/agents.py` 需要 `evidence.contracts` 里的请求模型来生成工具 schema。
但**任何** `import legal_acps.evidence.*` 都会先执行包的 `__init__.py` ——
如果那里在模块级 `from .forensics import analyze`，就会把 numpy / Pillow 拉进主链路。

后果不是"多装两个包"，而是：**服务器上没装 Pillow 时，6 个已过审 Agent 全部起不来**。
⇒ `__init__.py` 改用模块级 `__getattr__`（PEP 562）推迟到真正取用的那一刻；
`agents.py` 也只 `from .evidence.contracts import ...`（**不从 `.evidence` 顶层 import**）。

实测断言（子进程里用 `sys.meta_path` 屏蔽 `PIL`/`numpy`，再 `import legal_acps.agents`）：
7 个角色全部编译通过，`sys.modules` 里没有 PIL/numpy。

### 5.4 检测项与校准结果

最终 **5 个负对照全部零触发、4 个正样本各被预期的检查项抓到**：

| 样本 | 预期 | 实测 |
|---|---|---|
| N1 干净 PNG / N2 干净 JPEG q85 / N3 纯周期纹理 / N4 大图被中心裁剪 / N5 大片纯色 q70 | 不触发任何项 | ✅ 全部零触发 |
| P1 拼接（左半降对比、右半加噪声） | `noise_residual` | ✅ |
| P2 复制-移动（Δ=312px） | `copy_move` | ✅ 25 组 2-D 集中 |
| P3 元数据矛盾（Adobe EXIF 却无编辑痕迹字段） | `exif` | ✅ |
| P4 裁剪错位 4px 后重编码 | `block_grid`（偏移 4 像素） | ✅ 两轴比值 2.02 / 2.12 |

**四轮校准里翻掉的四个坑**（都写进元验证，退回即报失败）：

1. **块网格相位**：偏移量公式是 **`(7-φ)%8`**，不是 `(φ+1)%8`；
   **均值口径会被单个强边带偏**，**中位数/低分位截尾会整体塌成 0**（九成梯度恰好为 0）
   ⇒ 正解是 **`rank`（平均秩，有界）+ `frac`（超基准线占比）+ 要求两轴 argmax 一致**
   ——真网格相位是 **2-D 一致**的，内容噪声不是，这一条把全部假阳性一次清掉。
2. **复制-移动**：只看 argmax 会被周期纹理挡住；"总票数÷包围盒"会被全图碰巧同位移的噪声稀释
   ⇒ 改**最密簇** + **两轴跨度 ≥3**（克隆的是 2-D 面片，长直边沿自相似是 1-D 直线）
   + **特征量化步长 2.0 → 0.5**（粗量化时干净图有 368–835 个碰撞桶，真克隆被淹没）。
3. **适用前提闸门**：`ela`/`noise_residual`/`copy_move` 的前提是**自然摄影内容**。
   大片纯色（截图/拍白墙/拍文件）不满足 ⇒ 必须先判 `flat_fraction > 0.50` → **"无法判定"**。
   实测分离度：7 张自然样本平坦占比 0.000–0.001，纯色图 0.923。
   同理 **JPEG 量化本身抹掉平坦区噪声** ⇒ `check_flat_noise` 必须先过"JPEG 且质量 <95 → 无法判定"。
4. **我们自己的裁剪也是干扰源**：`crop_for_analysis` 的中心起点不是 8 的倍数时，
   我们亲手挪走了 JPEG 块网格相位 ⇒ 大图被报"网格偏移"（自作自受）。
   修法：抽出纯函数 `analysis_crop_box`，**8 像素对齐 + 不越界**（越界会被 Pillow 补黑边 = 亲手塞一道强边）。

### 5.5 三条贯穿全篇的设计纪律

1. **不让模型"看"图，让代码"算"图。** 模型只负责**组织与解释**；所有数值由确定性代码算出。
   ⇒ 判定可复现、可审计，且绕开"生产模型是否支持视觉输入"的不确定性。
2. **不给"真/假"，只给"线索 + 不确定度"。** 每个 Finding 自带 `caveat`（它**不能**证明什么）；
   报告固定带免责声明；`verdict` 取值域只有 `正常 / 提示异常 / 无法判定` 三种。
   `evidence-image` 的 instructions 里写死措辞铁律：**输出里不允许出现"真""假""伪造""P 过"**。
3. **参数归属纪律：能由代码填的一律不给模型。** `suspicion` / `upgrades` / `sha256` / 尺寸
   全部由代码填或复算，模型只转述。（同"轮次号必须由服务端账本决定"。）

### 5.6 两处**只有把输出打出来才看见**的缺陷（已修）

`evidence-image-样例输出.md` 是顺手生成的（本意只是留个样例），结果它当场暴露了两个
**断言全绿、代码跑得通、但结论是错的**缺陷。记在这里，因为它们是这一项里最值得复盘的教训：

**缺陷 1（严重）：「测不了」被说成了「没问题」。**
一张 92% 纯色（截图 / 拍白墙）的图，报告头行写的是 **「综合线索等级：低」**。
而真相是：`ela` / `noise_residual` / `copy_move` 三项因"非自然摄影内容"**整项没跑** ——
它们是**唯一**能发现内容层拼接 / 克隆的项目；剩下还能出结论的只有
`container` / `quantization` / `exif` 这类**封装层**检查，而封装层从来就不检测画面内容。

> 根因：`summarize()` 是"数异常项 + 算权重"，**只在每一项都弃权时才说「无法判定」**。
> 只要容器/量化表正常，就落入 `else: level = "低"`。
> 这是纯粹的**计数口径缺陷**：它把"没发现问题"和"根本没检查"当成了同一件事。

修法：加一条**排在算分数之前**的规则 —— 没有任何正向触发、且存在因"非自然摄影内容"
而弃权的检查项时，综合等级必须是「无法判定」，并在理由里点名是哪几项没跑。
断言**成对**：纯色图 → `无法判定`；干净自然图 → 仍然是 `低`（防止矫枉过正，
把正常图也说成"测不了"）。

**缺陷 2：唯一的法律救济路径被静默删掉了。**
`plan_upgrades(level)` 原本按等级裁剪条数（低 2 / 中 3 / 高 4），
于是**「线下司法鉴定」这一档在最常见的「低」里根本不出现**。
而它恰恰是：① 唯一有法律证明力的路径；② 本方案 §3.2(c) 花大篇幅调研的对象；
③ 用户提"返回更贵的方法"时真正想要的那条信息（2500–4000 元 / 组、约 30 个工作日、
必须保全原始载体）。

修法：**每一档都返回完整阶梯**，`level` 参数只留给将来做措辞分级，**绝不用来删条目**。
新增断言：四种等级条数完全一致、末档必是 `offline_forensic`、
且报价与时限确实写在里面。

> 两个缺陷的共同点：**它们都不是"跑不起来"，而是"跑起来了、还全绿，但话说错了"。**
> 前者靠"把真实输出打出来看一眼"发现，后者靠"拿需求逐条对照输出"发现 ——
> 两者都不是断言脚本能自动抓到的。**断言守的是"我想到的性质"，输出守的是"我没想到的"。**

## 6. 复查记录（2026-10-01）：逐行重读代码，修掉 9 处缺陷

用户要求"重新审视一下代码，修复 bug，仔细地检查"。这一轮**没有加功能**，
只做一件事：把已经"全绿"的东西重新读一遍，看它有没有在**没说谎的前提下**其实做错了。

结论是**有，而且不少**。9 处缺陷里有 3 处属于同一类——**"全绿"掩盖了错误答案**：

### 6.1 三类严重缺陷

| # | 缺陷 | 为什么"全绿"看不出来 | 后果 |
|---|---|---|---|
| ① | **`pipeline.outcome()` 会把异常漏给调用方** | 原断言只测了"取图被**策略**拒绝"那条路径，而**输入本身不合法**走的是另一条路 | 畸形字节 / 截断图像会让工具抛 `ValueError` / `OSError`。而这一层存在的唯一理由就是"不要让调用方收到不透明的异常"；它一旦失效，模型最可能的反应是**换个路子把图弄进来** —— 正好绕过刚设的边界 |
| ② | **`summary_line()` 与 `summarize()` 判据不同源** | §5.6 修的是**报告内部**那条规则，而**照抄给主控的那一句话**没有跟着改 | 纯色图的摘要会输出「综合线索等级：无法判定。4 项可执行检查均未提示异常。」—— 前半句测不了、后半句没问题。而这一句正是被原样转述给用户的那一句 |
| ③ | **`image/jpg` 被当成"容器不符"** | 检查逻辑本身没错，错在"声明"与"容器"的**取值域没有对齐** | `image/jpg` 是浏览器与不少客户端的常规写法。不归一化时**每一张这样的正常图**都会被报「提示异常」—— 纯假阳性，正是本能力最怕的失败形态 |

### 6.2 其余六处

| # | 缺陷 | 影响 |
|---|---|---|
| ④ | 未声明类型时 `container` 说「与声明一致」 | 跟一个**不存在的声明**比对，输出一句让人放心的假话；改为「无法判定」 |
| ⑤ | `file://` 的来源被标注成 `network` | `fetched_from` 是**溯源字段**，报告要回答"这份字节从哪来"；写成"网络"而实际来自本机磁盘，是一条会误导复核的假信息。取值域加 `local_file` |
| ⑥ | `context_note` 收下了却没往下传 | 调用方以为"案情说明"被用上了。**一个收下却不用的参数，比没有这个参数更坏** |
| ⑦ | `data:` URI 先解码、后查大小 | "判它超限"本身就要先把整段载荷解进内存，上限形同虚设。改成**解码前**按 base64 长度预判（用上界，方向 fail-closed） |
| ⑧ | 超大图没有闸门 | Pillow 会把整幅图解压进内存（RGB ≈ 3 字节/像素）。服务器 3.6 GB 内存、可用约 2.5 GB，**还同时跑着 7 个角色的进程** —— 一张 400 MP 的图足以把整台机器拖垮，连带让 6 个已过审 Agent 一起不可用。新增 100 MP 闸门，且检查必须在 `load()` **之前** |
| ⑨ | 断言脚本自身的两处不稳 | 缓存键用 64 位 `hash()`（撞一次就会让某条断言拿到**另一个样本的报告**）；第 7 节依赖 `EVIDENCE_IMAGE_ALLOW_FILE` 未被设置（环境变量会把它变成环境依赖的断言） |

### 6.3 这一轮真正的教训

**"全绿"证明的是"我想到的性质没被破坏"，而不是"代码是对的"。**

缺陷 ① 特别值得记下来：它漏了**四种**输入，一次都没被抓到，
因为原来的断言只覆盖了"策略拒绝"这一条路径。
**一条只测成功路径的断言，看起来和"整个边界都验过了"一模一样。**

所以这一轮的每处修复都配了**元验证用例**（元验证从 7 条增至 11 条）：

| 用例 | 退回的旧形态 | 要求哪条断言响 |
|---|---|---|
| ⑧ | `except (ValueError, OSError)` → `except ()` | "四种畸形输入全部返回结构化结果" |
| ⑨ | `elif gated:` → `elif False:` | "给主控的那句话不得出现「均未提示异常」" |
| ⑩ | `return MIME_ALIASES.get(base, base)` → `return base` | "MIME 常见别名不算不符" |
| ⑪ | `return w * h > MAX_IMAGE_PIXELS` → `return w * h > 10 ** 18` | "超大图报的是像素数过大" |

> 顺带一个方法论：**测试自己必须先站得稳**。
> 缺陷 ① 的断言最初是"裸着调 `outcome()`"的 —— 一旦回归真的发生，
> 它会带着 traceback 让**整个脚本崩掉**，而"崩掉（少打几行）"和"通过"在日志里几乎分不出来，
> 元验证还会把这种崩掉误判成"这条断言是空转的"。
> 现在所有相关调用都走 `_probe()`：**把"抛出来的异常"也折成一个可断言的返回值**。

### 6.4 验证与同步

- `tools/verify_evidence.py`：**8 节 68 条断言，exit 0**
- `run/meta_verify_evidence.py`：**11 用例全部触发并干净复原**（本地 + 服务器各跑一遍）
- 样例输出文档改为**由脚本生成**（新增 `run/gen_evidence_samples_md.py`）——
  文档里写着"自动生成，请勿手改"，但**生成它的东西此前并不存在**，
  于是这轮代码一改行为，那份文档立刻变成过期事实而看起来毫无异样。
  一句话：**"请勿手改"必须配一个"可以重跑"。**

## 7. 入站附件通道（2026-10-01）：把"用户上传的图"接进来

### 7.1 补的是哪个缺口

用户在对话里上传一张图，问"这图有没有被改过"—— 在这之前，系统**做不了**。
原因不是检测不行，而是**字节根本递不进去**：

- 工具只认 `image_uri`（模型工具层只暴露 uri，这是 AIP 的约束）；
- 模型拿不到字节（它既转述不了几十万 token 的 base64，也不该经手证据字节）；
- 而用户上传的图是以 `FileDataItem.bytes` 下发的，**字节其实已经躺在
  `state.messages` 里**，代码伸手就能拿 —— 只是没有任何人去拿。

一句话：**字节在，但谁都递不进去。**

### 7.2 实测出来的四条通道（入站附件有两种形态）

⚠️ **入站附件不是一种，是两种** —— AIP 允许调用方二选一，wit 把它们变成两种不同的
`ContentPart`。只接一种，另一种就会**静默消失**：

| 通道 | 调用方给的 | wit 交到我们手上 | 现状 |
|---|---|---|---|
| ① **入站附件 · 内联字节** | `FileDataItem(bytes=…)` | `ImagePart(data=<原始字节>)` | ✅ 收进收件箱 → 发句柄 |
| ② **入站附件 · 仅有地址** | `FileDataItem(uri=…)` | `ImagePart(uri='https://…')` | ✅ **如实转述地址**，不自动去取 |
| ③ 模型给出的 URI | 模型往 `image_uri` 里写的字符串 | —— | ✅ 本来就有（但模型几乎拿不到可用 URI —— 见 §1.2 补正） |
| ④ 本机文件 `file://` | 本机磁盘 | —— | ⚠️ 有开关、默认关，且**只能由入口代码显式打开** |

关键实测（都不是推断）：

- `FileDataItem(bytes=base64)` → `ImagePart(data=<原始字节>)`，**字节原样保留在
  `state.messages`**，hook 在 `on_run_start` 就能取到（实测 46 B 一字节不丢）。
- `FileDataItem(uri='https://…')` → `ImagePart(uri='https://…', data=None)`，
  **同样进 `state.messages`** —— 只是它没有字节。
- `runtime.aip_delegate(state, partner_aic=…, request=ContentInput)` 的 `request`
  **可以带 `ImagePart(data=…)`** ⇒ 字节能跨进程交给 Partner。
  这条走的是**代码 API**，不受模型工具层"只认 uri"的限制。
- 模型工具层 schema 原文：*"Attachments use URI references; inline Base64 is not
  accepted by this model-facing tool."* ⇒ 模型那条路永远给不了字节。

### 7.3 做法：让调用方**引用内容**，而不是引用位置

新增 `legal_acps/evidence/inbox.py`（收件箱）与 `legal_acps/evidence_hooks.py`（Hook）：

```
用户上传 → 平台 FileDataItem(…) → leader 的 state.messages 里有一个 ImagePart
   │
   ├─ 【形态一 · 内联字节】Hook 把字节收进收件箱（文件名 = sha256，内容寻址）
   │      ↓  system 提示里给出短句柄 inbox:<sha256>（模型只需照抄一个 token）
   │  模型把它写进 acps_delegate 的请求文本
   │      ↓  由代码把句柄换回真实字节，走 aip_delegate(request=ContentInput) 送出
   │
   └─ 【形态二 · 仅有地址】Hook **只把地址转述**给模型（不自动去取、不代它决定）
          ↓  模型把地址原文填进 image_uri；能否取到由出网白名单决定
   evidence-image 侧 → 模型调 inspect_image → 确定性代码算出线索
```

⚠️ **句柄不是路径，是内容哈希**，这是整个设计的安全依据：

- 文件名由 `inbox` 从 sha256 拼出（纯十六进制 + 固定后缀）⇒ 结构上不可能越出目录；
- `resolve()` **只认 64 位小写十六进制**，其余一律拒绝；
- 模型无论写什么，要么命中"本来就登记在这台机器上的那份字节"，要么什么也命中不了。

> 为什么不直接把路径发给模型：那等于顺手造出一个**任意的本地文件读取原语** ——
> 在 7 个角色共处的那台机器上，`.ssh/acps-hk-key.pem`（我们自己的 mTLS 私钥）也在射程内。
> 这与 §5.2 里 `file://` 的取舍是同一件事的两个面。

### 7.4 两条路，各走各的

- **路一（本角色自己收到附件）**：`on_run_start` 扫 `state.messages`，**两种形态分别处理** ——
  内联字节落盘换句柄，只有地址的原样转述。适用于"任何调用方把图连同任务直接发给
  `evidence-image`"。
- **路二（主控转发给下游）**：模型只能在 `acps_delegate` 里给字符串，所以让它在请求文本里
  **照抄句柄**，由 Hook 在 `wrap_tool_call` 里替换成真实字节。

⚠️ 路二刻意做成**句柄驱动**而不是"有图就自动附带"：一旦改成后者，
煽动性识别、危害评估这些与图像无关的 Partner 也会收到几 MB 字节 ——
既浪费通道，也让"谁看过这张图"变得说不清。**传不传，由请求内容里有没有句柄决定。**

### 7.5 三条必须守住的性质（都已配断言）

1. **纯文本任务零注入**：没有附件时 `context()` 一个字都不加、`wrap_tool_call` 不干预。
   这是"对已过审的纯文本链路零影响"的**可验证**说法，不是口头保证。
2. **`file://` 服务模式结构上不可达**：开关从环境变量改成进程内 `enable_local_file()`，
   且规则收在一个**纯函数** `resolve_local_file_flag(requested, serving)` 里
   —— 写在 `run_agent.py` 的 if 里就只能靠人工 review，抽出来才能被断言钉住。
   另加一条**静态断言**：`enable_local_file(` 不得出现在会被服务加载的模块里。
3. **Hook 挂载用关系断言**：`EvidenceInboxHooks` 里有一段"接管 `acps_delegate`"的逻辑，
   挂在没有这个工具的角色上就是死代码。所以断言的不是"挂了没有"，而是
   **"有 `acps_delegate` ⇔ `delegate_tool` 非空"**
   （`DebateChainGuardHooks` 曾在没有该工具的辩手身上空转过一整轮）。
4. **入站附件两种形态都接，且第二种不许自动出网**（本轮新增）：uri 形态**只转述地址**，
   由上层决定取不取 —— 一张入站图片里塞个 URL，不该等价于一次自动出网。
   配套断言：真跑一次 `WitRuntime`，断言地址出现在 system 提示里、
   且提示中写明"没有字节 / 不会自动去取 / 取不到要如实说"。
   ⚠️ 这条断言在补齐之前是**空转**的：`image_attachments()` 只认 `.data`，
   而带 `data` 的 part 天然没有 `uri` —— 删掉"跳过"规则它照样通过。
   元验证第 ⑲ 条就是这样把它抓出来的，现在改用绕开 wit 校验的 duck-typed 输入。

### 7.6 验证

- `tools/verify_evidence.py` 扩到 **10 节**：
  - 第 9 节「附件通道」：真跑 `WitRuntime`（不是自己拼 ctx —— 这条链的价值就在于
    "wit 真的会把附件放进 `state.messages`"），覆盖两种形态、纯文本零注入、
    委派接管 / 放行两侧、句柄伪造与穿越、收件箱字节上限；
  - **第 10 节「委派两条链的等价性 + 字节保真」**（本轮新增）：用记录调用的假
    coordinator 把两条链都跑一遍，断言参数逐项对齐；再用覆盖全部 256 种字节值的
    样本做线格式往返。
- `run/meta_verify_evidence.py` 从 11 用例增至 **20 用例**（新增 ⑫–⑳），
  退回旧形态全部报失败。
- ⚠️ 其中 ⑫ 特意选了**唯一真能穿透**的用例：`inbox:../secret`
  （解析出的路径是收件箱的**上一级**，那里确实放着一个文件）。
  别的伪造句柄（穿越到 `/etc/passwd`、编一个未登记的哈希）在两种写法下都会被拒，
  **只能证明"没读到"，证明不了"为什么没读到"** —— 那种断言是空转的。
- ⚠️ 第 10 节的两条断言**不参与元验证**，理由写在元验证脚本的 docstring 里：
  它们测的是 **wit 框架的事实**（框架是字节码分发，改不动），没有"退回旧形态"
  可言。证据强度是"对框架的实测"，不是"我们的决定被钉住" —— 两者别混为一谈。

### 7.7 上一轮标成"必须真机验"的两点：已全部离线解决

上一轮把下面两条记成"只能等真机"。复盘下来，**是问法本身错了** —— 问错了，
答案自然一直够不着。

#### ① 「平台下发用户上传图时用 `bytes` 还是 `uri`」—— 这是个错问题

- **附件下发不是 ADP 的职责**：`acps_sdk/adp/` 里只有 Discovery 的模型与校验器
  （`models.py` 里全是 `DiscoveryRequest/Response`，没有任何附件构造）。
  附件属于 **AIP 任务**。
- **AIP 两种形态都允许**，用哪一种是**调用方的选择**，不是平台的固定行为。

实测（`wit.acps.aip.data_item_to_content_part`，逐条跑过）：

| 调用方给的 DataItem | wit 交到我们手上 |
|---|---|
| `{'type':'file','bytes':<base64>}` | `ImagePart(uri=None, data=<原始字节>)` |
| `{'type':'file','uri':'https://…'}` | `ImagePart(uri='https://…', data=None)` |

⇒ **"验一次然后假设恒定"从来不是可行方案**：只要有一个调用方用另一种形态，
那条路就静默失效。对**可变输入**的唯一正确做法是**两种都接、各自说明**。

**本轮补的就是这个**：

- `inbox.image_references()` —— 挑出"只有地址、没有字节"的附件（与 `image_attachments()`
  互斥，有字节的一律归那边）；
- `EvidenceInboxHooks.context()` 把它**如实转述**给模型（提示里的「形态二」），
  并**明确写出"系统不会自动去取"** —— 即**不把"入站图片里塞个 URL"变成"一次自动出网"**。
  取不取、能不能取，交给上层的白名单策略，地址原样交出去。

⚠️ **补之前的行为是静默丢弃**：`image_attachments()` 只认 `.data`，uri 形态的附件
一个字都不会出现在提示里。而"没收到图"与"收到了但没人理"在结论里**长得一模一样**。
这是最难被注意到的那类缺陷：它不报错，只是少说了一件事。

#### ② 「`aip_delegate` 与原生 handler 的返回结构是否一致」—— 已离线证明

不用真机，因为两条链**本来就是同一个实现**（反汇编 + 行为实测双向确认）：

```
原生 acps_delegate 的 handler（AipDelegationHooks.on_run_start 里注入的工具）：
    A = ctx.runtime._ensure_aip_coordinator()
    return await A.delegate(state, partner_aic, request, delivery=…, notify_on_states=…)

runtime.aip_delegate：
    A2 = self._aip_delegation_hook(); coord = self._ensure_aip_coordinator()
    return await coord.delegate(state, partner_aic, request,
                                delivery=str(A2.delivery), notify_on_states=A2.notify_on_states)
```

同一个 `coordinator.delegate`、同一组参数语义 ⇒ 返回**必然是同一个 dict**。
而且 `acps_delegate` 这个工具本就是 `AipDelegationHooks` 在 `on_run_start` 里加的，
所以 `self.delivery` 与 `A2.delivery` 也是同一个值。

行为验证（`verify_evidence.py` 第 10 节）：用一个**记录调用的假 coordinator** 把两条链
都跑一遍，断言 `partner_aic` / `delivery` / `notify_on_states` **三项逐一对齐**、
返回 dict 形状相同，并明确断言**两条链唯一的差别就是入参能力**
（工具层只能给字符串或 uri，代码层能给字节）—— 那正是本分支存在的理由。

#### ③ 顺带把"路二"钉死：字节经线格式往返无损

`ImagePart(data=768 B)` → `FileDataItem(bytes=base64)` → `ImagePart(data=768 B)`，
用**覆盖全部 256 种字节值**的样本实测，一字节不差，`mimeType` 与 `name` 一并保住。
这是"跨进程传字节"在**协议层**的证明（网络那一段是框架既有能力，纯文本委派已在跑）。

### 7.8 仍然真正未知的一点（但已不阻塞）

**具体调用方**会选哪种形态 —— 这确实只能等真机（或等对方文档）。
但它**已不再是阻塞项**：两种形态现在都进链路，各自有断言。真机跑起来后只需看一件事：

- 若对方发 `uri` 且主机不在 `EVIDENCE_IMAGE_ALLOWED_HOSTS` 里 ⇒ 会看到一个
  可解释的拒绝（`fetch` 的错误信息本来就带补救建议）。
  **这是配置问题，不是代码缺陷** —— 而且它会被如实报成"未能取得该图片"，
  不会被含糊成一句"没问题"。
